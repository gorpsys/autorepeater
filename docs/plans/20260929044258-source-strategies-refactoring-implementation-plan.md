# Выделение стратегий автоследования

## Цель и согласованные решения

Подготовить приложение к добавлению алгоритмов автоследования отдельными
модулями с регистрацией в одном месте. Сейчас реализовать только рефакторинг
повторения счёта. Пользователи изменения: разработчики новых стратегий и
оператор существующих локального и облачного запусков.

Согласовано с пользователем:

- Параметр `src` сохраняется. Номер счёта выбирает существующий алгоритм.
- Именованное значение, например `IMOEX`, в будущем выбирает отдельную стратегию.
- Граница стратегии: целевые количества инструментов и источник событий.
  Переход на целевые веса сейчас не выполняется.
- Неподдерживаемый `src`, включая `IMOEX` до его реализации, вызывает понятную
  ошибку до создания SDK-клиента. Передавать такое имя как `account_id` нельзя.
- Новые алгоритмы, источники индексных данных и расписания пока не добавляются.
- `TargetPortfolio` содержит целевые количества и обязательную оценочную цену
  каждого инструмента цели, не только планируемых покупок. Цены используются
  для threshold; заявки BESTPRICE не содержат цену исполнения.
- Пустой `src` означает ошибку, а не режим просмотра портфелей.

Статус: пользователь поручил выполнить весь план, включая описанные границы
слоя вывода и контракт цели с ценами, создать PR и добиться зелёных GitHub
workflows. Task 1–6 выполнены в новой ветке `feature/source-strategies`
от `origin/master` (`15a5e1f`); локальные проверки и проверка архива завершены.
Публикация PR и проверка GitHub workflows ещё ожидают основного агента;
удалённые проверки не объявляются пройденными. План сохраняется по исходному пути.

## Контекст

- `autorepeater/repeater.py`: `AutoRepeater` объединяет чтение обоих счетов,
  формирование цели, расчёт и отправку заявок, подписку на события.
- `autorepeater/runner.py`: оба режима напрямую создают `AutoRepeater`,
  дублируют настройку параметров и требуют `src`/`dst`.
- `autorepeater/orders.py`: оценка покупок зависит от `src_positions`.
- `autorepeater/triggers.py`: чистая, но специфичная для повторения счёта
  проверка событий источника и назначения.
- `main.py`, `autorepeater/serverless.py`, `handler.py`: уже передают строковый
  `src`. Новый параметр выбора алгоритма не требуется.
- `test/test_autorepeater.py`: 108 тестов; последний подтверждённый прогон
  дал 100% линейного покрытия. Это исходная точка, не результат этого плана.
- CI: Python 3.12, pytest, pylint, flake8, общее и diff-покрытие не ниже 90%.
- `Makefile`: копирует `autorepeater/*.py` в облачный архив. Новые модули
  оставляем непосредственно в этом каталоге.

## Границы работ

Без новых зависимостей, SDK-обновлений, сетевых запросов к индексам, БД,
плагинного загрузчика, новых пакетов и нового планировщика. Использовать
небольшие классы с документированными методами и один простой DTO, без
иерархии наследования, обязательного ABC или универсального контейнера DI.

Существующие правила расчёта, цены оценки и округления сохранить. Не исправлять
попутно оценку объёма заявок в лотах, валютную конвертацию, нулевую стоимость источника,
повторные заявки, reconnect/backoff или обработку произвольных SDK-ошибок.
Такие изменения требуют отдельной задачи и собственных ожидаемых результатов.

Стабильный внешний контракт: имена параметров CLI, query string и переменных окружения,
`Runner`/`RunnerParams`, `Runner.run()`/`run_sync()`, `handler.handler`.
Внутренние методы `AutoRepeater`, расчётные функции и импорты тестов можно
изменить согласованно. Старый фасад и лишние совместимые обёртки не возвращать.
Имя `postiton_to_string` сохранить при переносе, константы не переименовывать.
Согласованное исключение совместимости: пустой/отсутствующий src отклоняется;
облачный запуск больше не использует зашитый номер источника. Перед деплоем
потребуется передать src в запросе либо настроить `SRC_ACCOUNT`.
Дополнительно вводится строгая проверка полноты цен всей цели, включая debug.
На корректных данных арифметика и решения о заявках остаются прежними.

## Решение

### Ответственность модулей

| Модуль | Ответственность |
| --- | --- |
| `portfolio.py` (новый) | Общее чтение портфеля; DTO `TargetPortfolio` с количествами и ценами, проверка полноты цен |
| `reporting.py` (новый) | Просмотр счетов, форматирование позиций, пользовательские сообщения о портфелях, заявках и событиях |
| `account_strategy.py` (новый) | Источник-счёт: снимок источника, ratio и целевые количества, интерпретация событий двух счетов |
| `strategies.py` (новый) | Проверка `validate_src(src)`, селектор `create_strategy(src)`, реестр, ошибка пустого/неподдерживаемого источника |
| `repeater.py` | Общая ребалансировка назначения, заявки, параметры риска и общий цикл запусков |
| `orders.py` | DTO заявки и оценка объёма по явным картам цен |
| `runner.py` | Выбор стратегии до SDK, жизненный цикл SDK, единая сборка `AutoRepeater` для двух режимов |
| `triggers.py` | Существующая проверка событий счёта; вызывается только стратегией счёта |

`portfolio.py` не занимается выводом. Оставить чтение обычной функцией с явно
переданным клиентом, без нового класса репозитория. Фильтрация валют источника
остаётся правилом стратегии, резерв назначения остаётся правилом движка.
`money.py` сохраняет чистые функции.

Согласованный слой вывода `reporting.py` состоит из обычных функций, без шины
событий и иерархии классов. Перенести туда `postiton_to_string`,
`get_instrument`/`GetInstrumentException`, `print_portfolio_by_account`,
`print_all_portfolio` и формирование пользовательских сообщений о расчёте,
заявках и пропущенных событиях. `Runner.run()` вызывает просмотр всех счетов
напрямую; `run_sync()` его не вызывает. Методы движка/стратегии передают
отчётным функциям уже полученные данные и рассчитанные итоги, не вычисляют
итоги повторно ради вывода. Для сохранения порядка сообщений допустимы отдельные
функции заголовка, позиции и итога. Отчётный код не определяет цели, бюджет,
порог или решение о торговле и не отправляет заявки.

В этом простом слое допустимы явно переданные read-only SDK-запросы: просмотр
счетов и поиск названия инструмента, как сейчас. Во время синхронизации повторно
загружать портфель ради вывода нельзя. Не вводить новые перехваты ошибок вывода:
существующий проброс SDK-ошибок и ошибки поиска инструмента сохраняется.
Чистое форматирование денег остаётся в `money.py`, настройка логирования и
JSON-форматтер в `logging_config.py`, технические `RequestError` логируются
там, где перехватываются. Перенос метода и обновление его вызывающего кода
выполняются одним шагом, без промежуточно сломанного Runner.

Зависимости направлены от `Runner` к селектору и движку; селектор знает
реализации стратегий. Движок не импортирует `AccountStrategy`, селектор или
специфичный `check_triggers`. Общие модули и reporting не импортируют
стратегии/Runner/движок. Стратегия не вызывает методы движка.

### Контракт стратегии

Конструктор `AccountStrategy(src)` только сохраняет идентификатор. Контракт
следующий, без требования наследоваться от общего базового класса:

```python
strategy.load_snapshot(client)                  # данные конкретного источника
strategy.build_target(snapshot, budget)         # TargetPortfolio
strategy.events(client, dst_account_id)         # Iterable[bool]
```

- `load_snapshot` вызывается заново перед каждой синхронизацией. Снимок локален
  одному запуску; движок передаёт его обратно, не разбирая его устройство.
  Стратегия счёта хранит в снимке позиции без валют и их суммарную стоимость.
- Затем движок загружает назначение и вычисляет бюджет с резервом. Это сохраняет
  прежний порядок запросов: сначала источник, затем назначение.
- `build_target` не отправляет заявки и не обращается к SDK. Для счёта порядок
  вычислений строго прежний: `ratio = budget / total_src`, затем
  `quantity = ratio * source_quantity`. Не переставлять операции ради формулы
  через веса: при точности Decimal 28 результаты могут отличаться.
- `events` представляет одну подписку/один проход источника событий. `True`
  запрашивает пересчёт, `False` означает отсутствие действия. Движок ничего
  не знает об SDK-типах событий и о том, есть ли у стратегии брокерский источник.
- Для счёта `events` вызывает прежний `positions_stream(accounts=[src, dst])`
  и `check_triggers`; неподходящий ответ логируется прежним способом.
- Создание первой цели не зависит от наличия событий: начальная синхронизация
  выполняется движком перед подпиской, как сейчас.
- Общий цикл при завершении итератора или `RequestError` открывает следующую
  подписку; ошибки первоначальной синхронизации и итерации логируются как
  раньше. Терминальное тестовое исключение не перехватывается.
- `run_sync` не вызывает `events`. Иное расписание позже можно реализовать
  внутри нового источника событий, не меняя этот цикл; сейчас его не создавать.

`TargetPortfolio` содержит только:

```python
quantities: dict[str, Decimal]  # UID -> целевое количество штук, не лотов
prices: dict[str, Decimal]      # UID -> оценочная цена штуки для threshold
```

Это полный целевой портфель, не дельта. Отсутствие UID означает нулевую цель
для имеющейся позиции. Успешно возвращённая пустая цель означает ликвидацию
позиций согласно общим правилам; сбой источника должен быть исключением,
а не пустым DTO. Расчёт разницы и лотов зависит от количеств, не от цен цели.

### Цены и проверка цели

Цена исполнения BESTPRICE не задаётся. Однако денежный `threshold` требует
оценить объём рассчитанных заявок. Для счёта `build_target` заполняет цены
из `current_price` того же снимка источника. Движок оценивает продажи по ценам
назначения, покупки по `target.prices`.
Карты не объединяются: один UID может иметь разные цены на src/dst. Порядок
и количество запросов не меняются. Цены не передаются в `post_order`.
Новая стратегия может загрузить оценки в свой snapshot без создания фиктивных
SDK `PortfolioPosition`; отдельный метод получения цен в контракте не нужен.

Добавить простую функцию `validate_target(target)` в `portfolio.py`. Движок
вызывает её сразу после build_target, до расчёта продаж и покупок, независимо
от debug. Для каждого UID в quantities обязателен ключ в prices и конечное
значение Decimal: отсутствие ключа, None, другой тип, NaN и Infinity дают
ValueError с указанием UID. Проверка не зависит от торгового статуса,
нулевой цели, уже имеющегося количества или наличия рассчитанной покупки.
Не вводить проверку строго положительной цены: ноль не равен отсутствию цены,
а изменение допустимого диапазона цен не входит в эту задачу.

Лишние ключи prices не используются и не запрещаются. Пустая цель с пустой
картой цен допустима. Для продажи позиции, отсутствующей в цели, цена берётся
из назначения, добавлять её в TargetPortfolio не требуется. При невалидной
цели не отправляется ни одной заявки, включая продажи; не подставлять ноль
или цену назначения вместо отсутствующей цены цели. В debug проверка цели
обязательна, но денежная оценка объёма и отправка по-прежнему пропускаются.

Это локальная проверка DTO без новых запросов или зависимостей. Она строже
прежней проверки цен только при оценке покупок и является согласованным
изменением контракта. Текущую оценку не заменять рыночными котировками:
это могло бы изменить решения threshold и требует отдельной задачи.

### Выбор по src

`create_strategy(src)` работает без SDK и сетевых вызовов:

1. `None`, пустая строка или строка из одних пробелов вызывают
   `UnsupportedSourceError(ValueError)` с сообщением `src is required`.
   Режима без источника больше нет, отказ до создания Client и просмотра счетов.
2. Непустая строка только из ASCII-цифр выбирает `AccountStrategy(src)`.
   Не преобразовывать в `int`: ведущие нули сохраняются. Не вводить проверку
   длины или существования счёта, отсутствующую в текущем коде.
3. Иначе искать точное имя в `NAMED_STRATEGIES`. Значения реестра: фабрики
   с контрактом `factory(src) -> strategy`, также без SDK в конструкторе.
4. Неизвестное значение вызывает `UnsupportedSourceError(ValueError)` с
   сообщением вида `unsupported src: IMOEX`. Не использовать `eval`, импорт
   по пользовательскому пути или fallback на номер счёта.

`validate_src(src)` выполняет те же проверки пустоты и допустимого номера/имени,
не создавая стратегию; `create_strategy` использует её перед вызовом фабрики.
Проверка пробельной строки не означает нормализацию: ` 123 ` не принимается.
Не добавлять нормализацию регистра/пробелов в рамках рефакторинга. Реестр
изначально пуст: ни `IMOEX`, ни его заглушки в рабочем коде не регистрируются.

`Runner.__init__` вызывает селектор и сохраняет стратегию. Оба режима используют
один приватный метод сборки `AutoRepeater(client, strategy)` с применением
`RunnerParams`. Стратегия обязательна; движок не выбирает источник сам.
При корректном src и отсутствии `dst` методы синхронизации по-прежнему не
вызываются; поведение dst не расширять в этой задаче. Проверки параметров сохранить.
Внутренние `sync_accounts` и `mainflow` получают только `dst`; `src` остаётся
в конфигурации `Runner` и конкретной стратегии.

CLI и serverless передают исходный `src` в Runner. Оба вызывают `validate_src`
до чтения токена: отсутствие токена не должно скрывать ошибку src. Runner
также проверяет src через селектор для прямых вызовов. Саму стратегию создаёт
только Runner. Ошибка распространяется до вызывающего кода; отдельный
HTTP-формат ошибок/код 400 пока не добавляется.

Для облака: если ключ `src` есть в query string, брать его значение, включая
пустое, и валидировать без fallback. Если ключа нет, читать `SRC_ACCOUNT`.
Если итог пустой, отказ; `DEFAULT_SRC_ACCOUNT` удалить. Это трактовка
«пустой src — ошибка», при которой запуск по триггеру с настроенным окружением
остаётся доступным. Общий `get_param` для dst/token не менять: их fallback,
включая `DEFAULT_DST_ACCOUNT` и `t_token`, сохраняется. Формат успешного ответа
остаётся прежним, при невалидном src ответа об успешной синхронизации нет.

### Как позже добавить IMOEX

Добавить `autorepeater/imoex_strategy.py` с указанными тремя методами и
зарегистрировать фабрику под `IMOEX` в `strategies.py` (импорт и запись реестра).
Дополнить её тесты и необходимые настройки источника данных. CLI, обработчик,
Runner, общий движок и расчёт заявок для этого не редактируются.

Этот план доказывает такую возможность тестовой регистрацией именованного
источника, а не добавлением второй рабочей стратегии.

## Инварианты и проверка

- `Decimal`, точность 28, текущие quantize и порядок вычисления ratio.
- Валюты исключаются из стоимости источника, учитываются у назначения;
  reserve применяется ровно один раз к назначению.
- Лотность, round и фильтр торгового статуса остаются в общем расчёте.
- До расчёта заявок проверяется цена каждого UID цели, в том числе в debug;
  отсутствие покупки не освобождает стратегию от этого контракта.
- Сначала полностью вычислить продажи и покупки, затем проверить порог,
  затем отправить продажи перед покупками. Debug ничего не отправляет.
- Сохранить строгое сравнение `volume > budget * threshold`; равенство
  не приводит к заявкам. Сохранить текущую формулу объёма без исправления лотов.
- SDK-ошибка при расчёте цели/покупок не должна приводить к частичной отправке
  ранее рассчитанных продаж. Ошибка продажи прерывает отправку покупок.
- Пустой и неподдерживаемый `src` отклоняется до создания `Client` в обоих
  режимах, даже если `dst` отсутствует.
- Не маскировать нулевую стоимость источника пустой целью: сохранить ошибку
  и отсутствие отправки. Новую политику для нулевых портфелей не определять.

Тесты остаются в `test/test_autorepeater.py`. SDK-сервисы подменять существующим
autospec с unwrap; DTO задавать явно. Для подставной стратегии использовать
стандартный `Mock(spec_set=['load_snapshot', 'build_target', 'events'])` и
явный `TargetPortfolio`, без ручного fake-класса. Go-скилл `mock-generator`
для этого Python-проекта неприменим.

Работать последовательно, обычная разработка с тестами в каждом шаге.
Не переходить дальше при падающих тестах. Отмечать выполненные пункты,
фиксировать изменения объёма работ и ограничения. Одного процента покрытия
недостаточно: сравнивать точные параметры, последовательность и число заявок.

## Приёмка и внешние действия

Рефакторинг принят, когда числовой источник сохраняет расчёты и заявки,
пустой src и неизвестное имя не доходят до SDK, а тестовый именованный источник проходит
через оба режима и обе точки входа без изменений их бизнес-логики. Отдельный
модуль плюс запись в селекторе достаточны для новой совместимой стратегии.
Все проверки проходят, оба порога покрытия не ниже 90%, архив самодостаточен
по коду и содержит новые модули.
TargetPortfolio содержит цены всех UID цели; неполная или невалидная карта
отклоняется до расчёта/отправки заявок, независимо от debug и торгового статуса.
Пользовательское представление отделено от расчётов и не управляет заявками.

Пользователь запросил коммиты, push, новый PR и зелёные GitHub workflows
по всему плану. Публикацию и проверку GitHub Actions выполняет основной агент
после завершения шагов; исполнитель каждого Task делает только свой коммит.
Реальные сделки и облачный деплой не нужны для
приёмки рефакторинга. Источник данных, расписание и правила IMOEX остаются
отдельной будущей задачей.
Перед будущим облачным деплоем настроить SRC_ACCOUNT либо передавать src
в запросах: прежний неявный источник намеренно больше не поддерживается.
