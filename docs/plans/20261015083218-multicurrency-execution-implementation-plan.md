## Цель и границы

Владелец брокерского счёта может повторять смешанный портфель: рассчитывать
доли и бюджет в RUB, покупать бумаги за их валюту расчётов, автоматически
обменивая деньги только при необходимости. ACCOUNT, INDEX и COMPOSITE
сохраняют существующие правила владения и разрешений на продажи;
назначение резерва уточнено в V4: он покрывает в том числе комиссии.

Согласовано пользователем:

- Пересчитывать валютные оценки в RUB, а не просто отклонять их.
- Поддерживать прямые валютные пары к RUB; не строить цепочки через третью валюту.
- Сначала использовать доступный остаток нужной валюты, докупать только дефицит.
- Обратно обменивать валюту в RUB только по потребности, не всю выручку подряд.
- Покупки валюты служат финансированию бумаг, не отдельной спекулятивной стратегии.
- Курс оценки — середина bid/ask; допустимый возраст котировки до 60 секунд.
- Валютные заявки — BESTPRICE, без добавления лимитного режима.
- При наличии в плане BUY или SELL валютной бумаги до первой заявки проверить
  доступность торговли соответствующей валютой, даже если обмен не требуется.
- Резерв — суммарные денежные остатки разных валют по рублёвой оценке.
- Резерв покрывает в том числе брокерские комиссии; это не неприкосновенная
  сумма, которую комиссия не вправе уменьшить. Покупки самих бумаг резерв
  не расходуют. Отдельный дополнительный процент на комиссии не вводится.
- Продавать валюту только при нехватке RUB для покупки рублёвых бумаг.
  Не продавать валюту ради рублёвого резерва или покупки другой иностранной валюты.
- Покупать валюту только при её нехватке для покупки бумаг за эту валюту.
- При необходимой покупке валюты сразу учитывать запас на комиссии
  из установленного резерва стратегии и округление до валютного лота.
  Не обменивать валюту отдельной заявкой только ради пополнения запаса.
- Минимизировать количество валютных операций и комиссионные издержки,
  зачитывая остатки/потребности и объединяя совместимые обмены без нарушения
  прав владельцев денег.
- Для INDEX явно указывать валюты справочных данных, сохраняя методику
  выбранного реального индекса, а не приписывая всем справочным ценам RUB.
- Сохранить обратную совместимость конфигов: отсутствующая валюта справочных
  данных означает RUB. Поля справочных курсов обязательны только при явно
  указанных нерублёвых справочных валютах.

Не входят: исправление дубликатов UID, маржинальная торговля, новые стратегии,
постоянный межзапусковый денежный реестр, сторонние источники курсов,
обход блокировки иностранных бумаг и расширение типов торговых заявок.
Ограничение цены лимитными заявками и новый обязательный процентный запас
на проскальзывание не вводятся: пользователь выбрал BESTPRICE.

- `account_strategy.py`: `load_snapshot` суммирует числовые цены без валютного

- `tinvest_strategy_data.py`: адаптер сохраняет валюту `current_price`,
  которая может отличаться от валюты номинала и расчётов инструмента.
- `tinvest_execution_data.py`: `_portfolio_state` отклоняет нерублёвые оценки

- `purchase_plan.py`: `cash_bound` и `_candidate` разрешают только RUB.
- `repeater.py`: полный план строится до эффектов, затем исполнитель читает
  свежую доступность и подтверждает каждую заявку.
- `execution.py`: денежные пулы и права передачи выручки привязаны к path.
  SDK-квитанция оставляет `ExecutionReceipt.cash` пустым: чистая выручка
  не доказана. Глобальная разница остатков не заменяет атрибуцию выручки.
- SDK 1.51.0 содержит `GetOrderPrice`, но его комиссионные поля требуют
  различения назначения, единиц и пересечений. Опыт с этим RPC сохранён
  в отчёте; по уточнению пользователя рабочий BESTPRICE-путь его не требует.

## Согласованные решения

### V1. Курс оценки

Середина актуальных bid/ask прямой пары для оценки в RUB;
ask для расчёта расхода при покупке валюты, bid для ожидаемой выручки продажи.
Курс оценки фиксируется на расчётный проход для всего дерева стратегий;
исполнение использует свежие котировки и неизменные разрешения/денежные потолки.
Не использовать курс 1, номинал облигации или итог GetPortfolio как курс позиции.

Допустимый возраст котировки — не больше 60 секунд, по времени рыночных
данных, а не только получения ответа. Нет действительного bid/ask или время
данных неизвестно — не подставлять последнюю сделку, старый курс либо 1.
Перечитать данные перед отправкой при превышении срока; если актуальных
данных нет, отложить зависимый торговый проход без заявок.

### V2. Тип валютных заявок

BESTPRICE, как в успешном диагностическом опыте. Перед заявкой проверяются
API/BESTPRICE-разрешения, собственные немаржинальные лимиты и доступность
денег. Цену в BESTPRICE-заявку не задавать; обязательный GetOrderPrice
для её подготовки не нужен. Оценка стоимости для расчёта лотов и валютной
потребности не является параметром цены заявки и не фиксирует цену сделки.
Риск изменения цены принят выбором BESTPRICE; гарантии точного расхода по
предварительному курсу не заявляются. Комиссии учитываются отдельно от этого риска.

Сохранить существующий контракт подтверждения заявок: FILL с правильными
UID/side/broker ID/лотами, ограниченное ожидание там, где оно предусмотрено
исполнителем. Не добавлять лимитную цену, автоматическую отмену или повторную
отправку неопределённого обмена. Частичное/неподтверждённое исполнение не
разрешает зависимую покупку; следующий проход читает фактические остатки.

### V3. Проверка валютных торгов до исполнения

Если план содержит покупку или продажу бумаги с нерублёвой валютой расчётов,
проверить торговую доступность прямой пары этой валюты к RUB до первой
заявки всего прохода, включая рублёвые заявки. Для COMPOSITE проверить
объединение нужных валют всех ветвей. Проверка нужна и при достаточном
валютном остатке, и при продаже без последующего обмена.

Использовать валюту расчётов бумаги, не валюту её номинала. Рублёвые
замещающие облигации с номиналом USD сами по себе не требуют проверки USD/RUB.
Учитывать планируемые валютные покупки с будущим финансированием, а не
только очередь, уже обеспеченную исходным валютным остатком.
Если валютных BUY/SELL бумаг нет, но запланирован обмен для покупки RUB-бумаги,
его торговая доступность также проверяется до первой заявки.

При недоступности валютных торгов отложить весь проход без заявок;
независимые рублёвые ветви отдельно не исполнять. Для чистого no-op без
валютных BUY/SELL эту торговую проверку не требовать. Свежесть курса для
оценки валютного капитала проверяется независимо от наличия заявок.
После начала исполнения сохранять свежие проверки доступности. Если
проблема возникла после подтверждённых эффектов, остановить оставшиеся
заявки, без отката, повторной отправки и расширения торговых прав.

### V4. Многовалютный резерв и причины обмена

У конечной стратегии `cash_floor` задаёт целевой денежный резерв в RUB-оценке,
учтённый при расчёте целевых количеств бумаг и бюджета их покупки.
Резерв предназначен в том числе для комиссий: их фактическое списание
может уменьшить остаток ниже рассчитанного до сделок floor.
При проверке доступных денег и собственных денежных лимитов не вычитать
`cash_floor`: ни исходный, ни пересчитанный после комиссий. Это повторно
ограничивало бы покупки, для которых резерв уже учтён в целевом плане.
Отдельный счётчик уменьшаемого floor для допуска заявок не требуется.
Не запрещать исполнение только потому, что комиссия расходует часть
резерва, и не восстанавливать его отдельным FX.
НКД относится к стоимости покупки облигации, а не к комиссии из резерва.
Физически держать весь резерв в RUB не требуется. Учитываются только
доступные и разрешённые соответствующей области деньги, не ожидаемая выручка.
Целевые количества, бюджеты и владение деньгами продолжают ограничивать
стоимость покупок; отсутствие вычета floor не разрешает превышать их.
Комиссия расходует деньги своего владельца, не резерв соседней ветви.

При обмене для валютных покупок к их финансированию добавляется валютный
запас из существующего резерва стратегии; применяются установленный reserve
и бюджет, а не новый произвольный процент. Учесть уже имеющуюся валюту
и округлить только дефицит вверх до целого валютного лота. Лотный излишек
остаётся деньгами и покрывает запас; второй резерв поверх него не создавать.
Оценочную комиссию будущей покупки не прибавлять поверх запаса повторно:
она оплачивается из него, при этом доступных денег должно хватать на сделку.

Резерв распределяется по валютам только внутри каждой конечной стратегии
(ACCOUNT/INDEX). Родительский cash_floor COMPOSITE включает резервы детей
и нераспределённый бюджет; целиком считать его комиссионным резервом нельзя.
Нераспределённые деньги COMPOSITE не входят в расчёт валютного запаса,
не передаются детям для комиссий и не обмениваются ради их запаса.
Правило действует на любом уровне вложенности.
Для смешанной конечной стратегии её резерв распределяется пропорционально
целевой стоимости бумаг в каждой валюте расчётов, без увеличения общего reserve.
Доли определяются по целевым стоимостям в общей RUB-оценке, а не по числу
бумаг или размеру очередной заявки. Валютная доля резерва переводится
в единицы этой валюты по общему FxSnapshot.
Для стратегии с одной валютой бумаг валютный запас соответствует её резерву.
Уже имеющийся доступный и разрешённый остаток валюты, включая ранее
купленный и лотный излишек, покрывает и покупки, и валютную долю резерва.
При необходимом обмене дефицит равен max(0, стоимость планируемых покупок
с НКД + валютная доля резерва - имеющаяся разрешённая валюта);
комиссия покрывается резервом, а округление до FX-лота применяется после
вычитания остатка. Одни и те же деньги не засчитываются дважды.
Эта формула задаёт размер уже необходимого обмена, а не создаёт причину
для отдельного восстановления валютной доли резерва.

RUB -> валюта разрешён только на дефицит финансирования покупки бумаги
за эту валюту с учётом описанного комиссионного запаса и лотности.
Валюта -> RUB разрешён только на дефицит RUB для покупки рублёвой бумаги.
Если имеющаяся валюта позволяет исполнить покупки с комиссиями, не запускать
обмен лишь потому, что её запас меньше целевого. Если на комиссию покупки
денег не хватает, это часть потребности покупки, не самостоятельное пополнение.
Само распределение денежного резерва между валютами и изменение курса
не являются причиной обмена. Не продавать валюту только для комиссий
или для её последующей замены другой иностранной валютой.
Если RUB-комиссию валютной покупки нечем оплатить в этих пределах,
покупку отложить, а не придумывать дополнительный маршрут обмена.
Защищённые деньги и бумаги не становятся доступными из-за потребности в FX.

### V5. Подтверждение заявки и денежная доступность без истории

Исполнение подтверждается ответом отправки и GetOrderState по фактическому
broker order ID: FILL, верные UID/сторона/лоты. Затем перечитываются доступные
остатки, блокировки и собственные немаржинальные лимиты. Не ждать историю
операций, не связывать operation.id с заявкой и не добавлять эти RPC в рабочий путь.
Инициировать обмен можно только по двум причинам V4; наличие валютного
остатка или техническая доступность брокерского метода сами по себе не повод.

При уточнении оставшихся покупок сохранить действующие проверки готовности,
позиций, торговых разрешений, собственных немаржинальных лимитов, лотности,
целевых количеств, бюджетов и владения. Исключение одно: доступные деньги
и денежные лимиты проверять без вычитания `cash_floor`. То же правило
действует до первой покупки, после SELL/BUY/FX и для RUB и валютных ветвей.
Реально списанные комиссии уже отражены в свежих остатках; повторный вычет
резерва не нужен. Недостаточная фактическая доступность по-прежнему
ограничивает исполнимый размер либо откладывает покупку.

Свежая доступность отвечает на вопрос, позволяет ли брокер потратить деньги
сейчас, а не является ли заявка расчётной TOM по названию. При положительных
разрешениях и достаточных собственных лимитах не ждать календарной даты TOM.
При блокировке/недостаточных лимитах отложить зависимую покупку, без маржи.
Не смешивать этот технический допуск с бизнес-разрешением на валютный обмен.

GetOrderPrice не включать в обязательный рабочий путь BESTPRICE.
Для оценки стоимости бумаги и расчёта валютной потребности использовать
середину актуальных bid/ask её стакана в валюте расчётов, отдельно от
валютного курса. Итоговая оценка портфеля после сделки использует фактические
количества и midpoint стакана, не цену исполнения заявки; валютный пересчёт
использует midpoint соответствующей прямой FX-пары по V1.
Для облигационной котировки в процентах номинала перевод в денежную оценку
и однократный учёт НКД остаются размерной арифметикой, не заданием цены
BESTPRICE. Проверять номинал/валюту/единицы; не получать торговую цену
делением брокерской RUB-оценки на собственный FX-курс.
Целевые количества и права текущего прохода не перестраивать только ради
послесделочной отчётной оценки. Эти оценки не гарантируют будущую цену
BESTPRICE и не являются основанием для дополнительного процента запаса.

Не считать total_order_amount безусловно чистой выручкой. Пока семантика
включения комиссии неоднозначна, неотрицательная комиссия может использоваться
для консервативной верхней оценки расхода (сумма плюс комиссия) и нижней
оценки выручки (неотрицательная сумма минус комиссия), только при проверенных
назначении полей, полноте ответа и совпадении валют суммы и комиссии.
Разновалютные поля нельзя складывать напрямую. Это границы, а не точное списание;
в DTO и логах они отделяются от фактов исполнения и фактической комиссии.
НКД второй раз не добавлять. Фактическую доступность всегда читать заново.

Владение деньгами в COMPOSITE сохраняется: общий остаток не разрешает одной
ветви расходовать чужую выручку. Прямые проверенные факты заявки достаточны
без истории; при их неполноте не заполнять ExecutionReceipt.cash выдуманной
точной суммой. Сохранить существующую отсрочку зависимых изолированных
покупок и разрешённый общий пул. Недостаток денежных фактов ограничивает
конкретный поток, а не запрещает всю разработку и валютные покупки
из уже имеющихся разрешённых средств.

## Архитектура решения

Стратегии остаются чистыми, без SDK и отправки заявок. Курс, исходная валюта
оценки и валюта расчётов передаются через собственные DTO/порты.
Рекомендуемые новые модули: `fx_data.py` (DTO и read-only порт),
`tinvest_fx_data.py` (SDK-чтение), `fx.py` (чистая арифметика),
`fx_funding.py` (валютные потребности и денежные пулы).
Окончательное разбиение проверить по реальному объёму, без пустых обёрток.
Новые зависимости, сервисы, базы, endpoints и фоновые процессы не нужны.

Данные расчётного прохода:

- `FxQuote`: UID валютной пары, base/quote, номинал котировки, лот,
  bid/ask, время данных и получения, разрешения и собственные лимиты.
  Один курс означает RUB за единицу валюты, не за торговый лот.
- `FxSnapshot`: неизменные курсы оценки всех используемых валют; RUB = 1.
- Исходные цены и валюты сохраняются рядом с рублёвыми marks. Приведение
  существующих `PortfolioEntry` к RUB не должно уничтожать исходные факты.
- Для денежных позиций отдельно сохраняются фактическая валюта денег
  и количество её единиц: `current_price.currency` не устанавливает эту валюту.
- Денежные пулы хранят суммы по валюте и владельцу/path. Стоимостный потолок
  ветви и `cash_floor` выражены в RUB; они не являются физической валютой.
- FX-intent содержит направление, пару, целое число лотов, разрешённых
  владельцев средств, зависимые покупки и предельные расходы по валютам.
- FX-квитанция подтверждает UID, сторону, broker ID, запрошенные/исполненные
  лоты; денежные дебеты, кредиты и комиссии требуют доказанного контракта.

Расчёт оценки бумаги: стоимость позиции = количество * денежный midpoint
бумаги * курс валюты этой оценки к RUB, с Decimal и проверенным
nano-округлением. Исходную портфельную цену брокера сохранять отдельно,
не подменять ею midpoint отчётной оценки. Для RUB
сохранить прежнее округление каждой позиции до суммы, не менять поведение
только ради общей формулы.

Денежный остаток оценивается отдельно: количество единиц его фактической
валюты * midpoint этой валюты из общего FxSnapshot. Например, 100 CNY при
midpoint 12 дают 1 200 RUB и для капитала, и для денежных пулов, и для резерва,
даже если брокер показывает для этого остатка 1 000 RUB. Брокерская цена
сохраняется как исходный факт, но не подменяет выбранный курс. Не умножать
её RUB-оценку повторно на курс и не добавлять GetPositions.money к B второй раз.
Без фактической валютной идентичности/количества или свежего midpoint
не выводить их из произвольной брокерской RUB-цены. Денежные позиции
назначения входят в капитал один раз, но не в состав целевых бумаг.
К уже выраженной в RUB оценке не применять FX-курс второй раз.

### Справочные валюты INDEX

Валюта счёта RUB не определяет валюты исходных данных поставщика индекса.
Справочные цены сохраняются в валюте предоставленных цен, капитализации —
в единой валюте и общей шкале предоставленных капитализаций. Для IMOEX
это RUB. Для другого индекса единицы определяются по его данным и методике.
Валюта расчёта/публикации самого индекса также не устанавливает автоматически
валюту цены каждой входящей бумаги.

Предлагаемые поля схемы:

- `reference_price_currency` у каждой бумаги — валюта `reference_price`;
  при отсутствии поля справочная цена выражена в RUB.
- `reference_capitalization_currency` у состава индекса — единая валюта
  всех `reference_index_capitalization`. Масштаб, например миллионы единиц
  этой валюты, должен быть одинаковым для всех бумаг. При отсутствии поля — RUB.
- `reference_fx_rate` у бумаги — единиц валюты справочной капитализации
  за единицу валюты справочной цены на дату соответствующего справочного
  снимка. Обязателен только если валюта справочной цены или справочной
  капитализации этой бумаги явно задана отличной от RUB. При совпадении
  валют равен 1. Для RUB/RUB поле необязательно, отсутствующий курс равен 1.
  Это историческое исходное данное, не сегодняшний midpoint.
  Дату/источник снимка сохранить в справочном описании состава.

Правило отсутствующих полей действует для любого конфига, не только
встроенного: нерублёвая валюта торгов бумаги сама по себе не меняет валюту
её справочной цены и не делает поля справочных курсов обязательными.
Например, у торгуемой за CNY бумаги при пропущенном reference_price_currency
справочная цена всё равно задана в RUB. Для текущей CNY-цены потребуется
рыночный FxSnapshot, но не исторический курс в рублёвом справочном конфиге.
Нерублёвая справочная цена одной бумаги не делает обязательным справочный
курс другой бумаги с RUB/RUB. Встроенные конфиги при обновлении получают
явные валюты без изменения числовых исходных данных.
Пустая/NULL/неизвестная валюта не равнозначна отсутствующему полю;
это ошибка до торговли. Отсутствие обязательного справочного курса при
явно заданной нерублёвой справочной валюте также ошибка, без fallback на 1.

Для существующей капитализационной модели INDEX размерно согласованный
расчёт задаётся так:

```text
reference_price_in_cap_currency = reference_price * reference_fx_rate
adjusted_quantity = reference_index_capitalization / reference_price_in_cap_currency
current_capitalization_rub = adjusted_quantity * current_price_rub
```

`adjusted_quantity` — коэффициент индексного объёма в общей шкале исходных
капитализаций, не число физических бумаг счёта. Не применять free_float
или weight_limit повторно, если они уже учтены в справочной капитализации.
Существующий RUB-случай алгебраически совпадает с прежней формулой;
при реализации сохранить также прежний порядок Decimal-операций для RUB.
Для текущей рублёвой стоимости использовать общий FxSnapshot, а для
справочного знаменателя — только сохранённый справочный курс. Не получать
исторический курс из текущего рынка и не фиксировать текущие веса навечно.
Рубли здесь служат общей валютой оценки текущих капитализаций; они не
меняют исходный состав, коэффициенты и правила выбранного индекса.
Другие методики индексов автоматически поддерживаемыми не объявлять.
Существующие рублёвые JSON и способы запуска сохраняются.

## Денежные правила

1. Потребность рассчитывается для допустимых покупок бумаг, с ценой,
   НКД и комиссионным запасом по V4, без двойного добавления комиссии.
   Не покупать валюту, если ни один целый
   лот зависимой бумаги нельзя разрешённо профинансировать. Нулевой текущий
   GetMaxLots из-за отсутствия её валюты не равен отсутствию потребности:
   отличать условную покупку после обмена от заявки, исполнимой прямо сейчас.
   Собственные лимиты будущей покупки не выдумывать; читать их заново после FX.
2. Дефицит = потребность минус доступная и разрешённая к расходу валюта.
   Общий остаток счёта не доказывает право конкретной ветви его тратить.
3. FX-лот округляется вверх только в пределах денежного потолка и доступных
   собственных средств; валютный запас относится к единому многовалютному
   резерву по RUB-оценке, а комиссия может уменьшать его по V4.
   Если минимальный FX-лот слишком дорог, зависимая покупка откладывается.
   Нельзя нарушить предел ради покупки «всего одного лота» валюты.
4. Лотный валютный остаток сохраняется на счёте как деньги; не становится
   позицией стратегии и не вызывает немедленный обратный обмен.
5. Общая FX-заявка возможна лишь с точной атрибуцией расходов и валютного
   кредита владельцам. Никакой передачи выручки в обход дерева разрешений.
6. Сначала зачесть потребности в той же валюте. Не продавать CNY в RUB,
   чтобы в том же проходе купить CNY обратно для уже известной потребности.
   Если для покупки USD-бумаги не хватает RUB, но есть лишние CNY, не строить
   цепочку CNY -> RUB -> USD: продажа CNY разрешена только для рублёвых бумаг.
   RUB от обратного обмена в этом проходе закреплены за такими покупками;
   лотный излишек остаётся денежным остатком, а не финансирует другой FX-маршрут.
7. После FILL нужны свежие деньги, собственные caps и readiness, без истории.
   Только подтверждённая доступность финансирует следующую заявку; номинальная
   выручка, расчётная рыночная оценка и изменение общего баланса не дают права
   приписать деньги конкретной продаже/ветви.
8. Комиссия и НКД не суммируются повторно, если уже входят в итог цены.
   Оценку до сделки отделить от фактического списания. Комиссию оплачивать
   в том числе из резерва своего владельца по V4, не из чужих денег.
   Если доступных средств не хватает на покупку с комиссией, уменьшить
   исполнимое число лотов либо отложить зависимую покупку. Не делать
   дополнительных обменов вне двух разрешённых причин.
9. После состоявшегося обмена менять только доступность и исполнимый размер
   дальнейших покупок, не расширять права на SELL и не перекраивать владение.
   Новый запуск читает фактическое состояние и не пытается откатить прошлый.
   Если после FX лимиты/цена уже не позволяют купить бумагу, валюта остаётся
   на счёте: это возможный частичный результат, не повод обменивать её обратно.

## Поток выполнения

Подготовка конфигов -> чтение исходных/целевых позиций и курсов -> единая
RUB-оценка -> профили/владение/полное дерево планов -> проверка валютных
маршрутов, торгов всех нужных валют и стоимостных ограничений -> разрешённые продажи бумаг ->
подтверждение доступных денег -> зачёт валютных остатков/потребностей ->
обмен только дефицита -> FILL и доступность -> зависимые покупки -> отчёт.

Обратный обмен обслуживает только разрешённую покупку рублёвой бумаги,
не восстановление физического RUB-остатка резерва. Комиссии и спред уменьшают
стоимость денежных остатков; комиссия оплачивается в том числе из резерва.
Целевой резерв не является гарантией неизменного остатка после комиссий.
Предварительная проверка выполняется до эффектов; свежие проверки перед
отправкой сохраняются, поскольку рынок и собственные лимиты меняются.
Источник ACCOUNT остаётся read-only: валютные операции только на назначении.
Debug выводит оба вида цен, курсы и FX-зависимости, ничего не отправляет.

## Подход к разработке

Отдельная рабочая копия/ветка от актуального master, не диагностические PR #37/#38.
Чужие незавершённые документы основной копии сохраняются. TDD RED -> GREEN,
порты через autospec(spec_set=True), SDK через autospec(inspect.unwrap(...)).
Каждый шаг заканчивается зелёными относящимися к нему тестами; перед следующим
шагом исправить обнаруженные регрессии. Менять план при изменении объёма.
Код до завершения интеграции не выпускается частями с включённым FX.

Существующие offline- и E2E-тесты сохраняются для регресса; валютные
сценарии добавляются к ним, а не заменяют их. Менять старый тест можно
только если он проходил при конкретном согласованном к исправлению баге
и его проверка закрепляла это ошибочное поведение. Для такого изменения
указать баг, прежнее ошибочное ожидание и новое согласованное поведение;
все остальные проверки теста сохранить. Не удалять/пропускать сценарии,
не расширять допуски и не ослаблять assertions ради зелёного прогона.
Обобщение общих helpers должно сохранять прежние проверки старых случаев;
само появление валютной поддержки не является основанием их переписать.
