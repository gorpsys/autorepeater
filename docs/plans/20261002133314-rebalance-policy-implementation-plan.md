## Согласованные требования

- Снизить частоту торговли и расходы на комиссии без отказа от следования цели.
- При появлении лишних денег направлять их на покупку недовешенных позиций.
  Само наличие денег не разрешает продажи; независимые внутренние критерии
  детей COMPOSITE продолжают действовать.
- Продажи для переноса капитала между частями COMPOSITE разрешать только при
  превышении его собственного порога; внутренние продажи части — по её критерию.
- Денежный сигнал пополнения разрешает только покупки, включая доступный хвост.
  Принят риск, что рост полного бюджета переведёт IMOEX в диапазон с меньшим
  порогом и прежнее отклонение разрешит продажи; это явное исключение, а не
  обещание отсутствия продаж при любом пополнении.
- Разделить проверку денежного остатка и проверку пропорций бумаг.
- Удалить общий торговый `threshold`, а не оставлять его вторым ограничителем.
- Допуск конкретного состава хранится внутри конфига стратегии, а не в общей
  таблице исполнителя. Общий денежный порог и отдельный JSON для него не нужны.
- COMPOSITE сначала проверяет соотношение частей. Его отдельный конфигурационный
  порог `component_drift_limit` равен `"0.20"`: максимальное относительное
  отклонение фактической доли любой части от целевой, не 20 процентных пунктов.
  При ровно 20% межкомпонентные продажи не разрешены.
- Стоимость портфеля B включает бумаги и деньги. При W = сумме weights
  общий полный бюджет детей равен B * W; B * (1 - W) не распределяется.
  Доли детей оценивать по стоимости их бумаг с поправкой на норму резерва.
  Выше порога распределять по целевым весам, ниже — направлять новые деньги
  в недовесы. Текущие скорректированные доли не становятся новой целью стратегии.
- Покупать всегда, когда доступных денег в бюджете конкретной стратегии
  хватает на исполнимый лот, уменьшающий недовес её основной цели.
  Лимита cash_excess_limit, общей суммы 1000 рублей и отдельного сигнала
  пополнения больше нет. Резерв и целевые количества по-прежнему ограничивают покупки.
- Если новый бюджет стратегии меньше старого из-за перераспределения или
  сокращения капитала, она обязана рассчитать ребалансировку независимо от
  собственного допуска. Исключение: ниже/на пороге COMPOSITE нехватка только
  расчётного резерва не разрешает продажи. Собственный критерий ребёнка
  сохраняется в обоих случаях; при совпадении цели и факта сделок нет.
- Отдельный общий порог отклонения 3%/5% не добавлять: для INDEX порог
  непосредственно задаёт обязательная таблица собственного конфига.
- Для IMOEX использовать согласованное построение строго убывающих верхних
  границ по числу бумаг, объединение по максимуму при одинаковом бюджете
  и максимум в диапазонах по 10000 рублей. Итог сохранён в его JSON.
  Каждое значение итоговой таблицы умножено на `1.1`; повторно умножать
  при загрузке или применении не нужно.
- Проверять ежемесячные пополнения не менее 2000 рублей на разных размерах счёта.
- Резерв остаётся внутренним понятием листовой стратегии; исполнитель не читает его.
- Для оценки текущей доли листа учитывать резерв через восстановленный
  капитал C = стоимость его бумаг / (1 - reserve), а не прибавлением процента
  к стоимости. Для вложенного COMPOSITE использовать нейтральную долю
  инвестируемого капитала из профиля, не читать конфиги/резервы его детей.
- Текущий капитал детей оценивать по составу инструментов; пересекающиеся
  позиции распределять виртуально по произведению доли ребёнка и внутреннего
  веса инструмента. Не считать весь общий инструмент капиталом каждого ребёнка.
  Неоднозначность исторического владения принять как риск, без хранения истории.
- Стратегия сообщает минимальный сохраняемый денежный остаток, не включая
  случайные остатки округления лотов. COMPOSITE добавляет намеренно
  нераспределённый бюджет.
- Основная цель рассчитывается от полной стоимости счёта; контрольная для
  разрешения внутренних продаж листа — от его вложенной части, по тому же снимку.
  В COMPOSITE бюджет ребёнка зависит от режима распределения между частями,
  а не всегда равен `budget * weight`, как в текущем коде.
- Покупки не должны превышать доступный бюджет и целевые количества.
  Принят критерий наибольшего уменьшения денежного недовеса до основной цели
  после покупки одного лота. Нормировка только по вложенной части для этого
  не применяется; правило разрешения продаж остаётся отдельным.
- При полном пересчёте бюджет равен стоимости всех бумаг и денег по оценкам
  снимка, как сейчас. Рассчитать цель и торговать только разницу с ней;
  не продавать весь портфель и не прибавлять предполагаемую выручку повторно.
- После каждой отправленной продажи проверять полное исполнение по ответу SDK.
  При отсутствии полного подтверждения остановить текущий торговый проход,
  не отправлять оставшиеся продажи и покупки, сообщить ERROR. Уже совершённые
  сделки не отменяются; следующий запуск начинает свежую проверку.
- Новый режим рассчитан на длинные позиции. Короткие позиции пока не
  поддерживаются; их поддержка потребует отдельной доработки исполнителя.
  Общий validate_target не менять ради ограничения режима.
- Локальный таймер не добавлять: начальный пересчёт и дальнейшие проверки
  по подходящим позиционным событиям. Проверку изменения только котировок
  откладывать до следующего события или перезапуска; это ограничение CLI.
- Сохранить одинаковую работу CLI и облака, независимость стратегий и их событий.
- ACCOUNT выбирается по name JSON, как INDEX. Номер исходного счёта, reserve
  и собственный допуск хранятся в выбранном конфиге; src больше не номер счёта.
- У INDEX таблица обязательна: первый диапазон начинается с нуля,
  последний не имеет конечной верхней границы. Нулевой бюджет ребёнка — ошибка
  всего пересчёта до любых заявок, а не основание пропустить его.
- Основная цель без количеств или только с нулевыми количествами — ошибка
  всего пересчёта до любых заявок. Это заменяет прежний защитный INFO/возврат.
  Пустая контрольная цель отключает только её внутренний сигнал продаж,
  не вызывает отказ основного пересчёта и не отменяет обязательное сокращение
  капитала, если оно разрешено отдельно от восстановления резерва.
- Неприписанные позиции считать денежной частью при экономическом
  распределении бюджета. Выше порога и при первом заполнении распределять по
  конфигурационным долям; ниже или на пороге — в денежные недовесы.
  Их оценочная стоимость не является доступными для покупок рублями.
  Их продажа разрешена независимо от порога COMPOSITE, но выручка
  финансирует покупки только после подтверждения полного исполнения.

## Конфигурация стратегий

Общий конфиг политики, REBALANCE_POLICY_PATH и cash_excess_limit не вводить:
после отказа от денежного лимита они не содержат согласованных параметров.
Порог внутренних продаж относится к самой стратегии, резерв — к листу,
порог межкомпонентного перераспределения — к соответствующему COMPOSITE.
Переопределений этих значений через CLI/query не добавлять.

### Именованные настройки ACCOUNT

Изменить `autorepeater/account_config.py:10` и
`autorepeater/account_strategy.py:24`: вместо единственного reserve и
проверки src как ASCII-номера читать выбранный по точному name JSON.
Схема: name, source_account_id, reserve, allocation_drift_limit.
source_account_id — непустая строка ASCII-цифр, ведущие нули сохраняются;
reserve — конечная Decimal-строка в [0, 1), допуск — конечная Decimal-строка
в [0, 1). Имя непустое, без пробелов; значения не нормализуются.

Каталог ACCOUNT_CONFIG_DIR либо встроенный configs/account/; совместимый
ACCOUNT_CONFIG_PATH выбирает один файл, но не заменяет выбор по name.
Одновременно обе переменные запрещены. Для обнаружения и изоляции повреждённых
чужих файлов использовать config_catalog, как INDEX/COMPOSITE; подготовка
выбранного документа один раз до Client. При импорте I/O нет.

Реальный номер источника теперь берётся только из выбранного конфига.
Старого автоопределения по цифрам нет, но само name может быть цифровой строкой.
Исторический облачный источник — `2193248994`: коммит `1f60ffb`,
`autorepeater/serverless.py:7` и выбор этого значения при отсутствии параметра
на строке 36. В `e509d71:autorepeater/serverless.py:36` этот fallback уже удалён:
восстанавливается значение для встроенного ACCOUNT-конфига, не поведение
облачного обработчика. Его нынешний выбор COMPOSITE/BALANCED не меняется.

Для встроенного документа зафиксировать `source_account_id = "2193248994"`
и `reserve = "0.01"`. Последний подтверждён константой в
`821b9e2:autorepeater/autorepeater.py:14` и перенесён без изменения в
`e044bce:autorepeater/configs/account/account.json`. Предлагаемое новое
`name = "2193248994"` сохраняет прежнюю запись запуска
`--algoritm ACCOUNT -s 2193248994`, но теперь это точное имя документа,
а не непосредственный выбор любого счёта. Исторического поля name не было.

Исторического `allocation_drift_limit` также нет. Старый
`THRESHOLD = "0.004"` (`821b9e2:autorepeater/autorepeater.py:15` и
`3513aa6:autorepeater/constants.py:5`) ограничивает объём заявок, а не
отклонение состава: сравнение находится в
`3513aa6:autorepeater/repeater.py:246`. Нельзя объявлять 0.004 восстановленным
допуском отклонения. По отдельной офлайн-калибровке для реализации принять
`allocation_drift_limit = "0.0092"` (0.92%). Критерий подбора — минимизация
расхождений разрешения продаж со старым threshold=0.004, без изменения
его прежней оценки лотов. Проверено 24000 сценариев подбора и 24000 независимых
проверочных сценариев; совпадение на проверке 91.3375%. Цены и лотности реальные,
но составы ACCOUNT модельные, не снимок счёта 2193248994. Это стартовый
эмпирический параметр, не эквивалентность метрик и не гарантия для любого состава.
Подробности и ограничения:
[калибровка допуска ACCOUNT](20261002-account-drift-calibration.md).
В самом раннем `51e122f` резерв равнялся 0.005, threshold — 0.001;
текущим прежним резервом считать более поздний 0.01, не раннюю величину
из устаревшей CLI-справки. Подробности проверки истории приведены в
[уточнениях бюджета и конфигурации](20261002-rebalance-policy-budget-clarifications.md).

### Таблица допустимых ошибок IMOEX

В `autorepeater/configs/imoex.json` добавлено поле `allocation_drift_limits`:
95 диапазонов от 50000 до 1000000 рублей в текущем рабочем файле. Это данные для будущей политики,
не действующий торговый фильтр и не замена `max_lot_weight_error`.
В реализации расширить первый диапазон до нуля, последний до бесконечности,
сохранив числовые limit и промежуточные границы. Исходную калибровку не менять.

```json
{
  "budget_from": "150000",
  "budget_to": "160000",
  "upper_inclusive": false,
  "limit": "0.059242183"
}
```

`budget_from` — конечная неотрицательная Decimal-строка в рублях;
`budget_to` — конечная Decimal-строка либо JSON null только у последней строки,
что означает отсутствие верхней границы. Не использовать Infinity/NaN в JSON
или бесконечные Decimal-цены/бюджеты.
`limit` — конечная Decimal-строка в долях, не в процентах;
`upper_inclusive` — bool; в новой схеме false у всех строк: интервалы `[от, до)`,
последний `[от, +бесконечность)`. Значения равны точным результатам калибровки, умноженным на `1.1`
через Decimal без округления вниз: `0.05385653 * 1.1 = 0.059242183`.
Это увеличение на 10% от значения, а не на 10 процентных пунктов.
В исходном JSON результата калибровки сохранены значения до запаса;
в рабочем конфиге запас уже включён и не применяется второй раз.
Таблица относится к полному бюджету, выделенному IMOEX до его резерва,
при построении основной цели в калибровке. Для COMPOSITE это бюджет компонента,
не полный счёт. Согласовано выбирать диапазон по полному текущему бюджету
IMOEX с деньгами, до его резерва, как в калибровке. Допуск берётся из результата
основной цели, не из контрольной цели от вложенной части.
Риск перехода от пополнения в строку с меньшим порогом принят явно.

Методика, исходные сценарии и ограничения:
[калибровка верхних границ](20261002-imoex-drift-envelopes.md);
[точный результат и хеши исходных данных](20261002-imoex-drift-envelopes-table.json).
На проверенных точках все 37 границ строго убывают и не ниже исходных ошибок.
Объединение имеет 17 подъёмов из-за появления других групп; таблица тоже
не обязана быть монотонной. Эмпирическая граница не является гарантией для
произвольных цен или промежуточных бюджетов вне проверенного шага 1000 рублей.
Вне калибровочного диапазона применять явно расширенные крайние строки.
Это экстраполяция прежних limit, а не гарантия точности вне проверенных бюджетов;
описать ограничение и проверить малые/большие бюджеты отдельно.

При реализации загрузчик INDEX должен проверить и сохранить таблицу в
`IndexConfig`: обязательный непустой массив, строгие поля строк, допустимые
границы, `от < до` для конечного интервала, конечный `limit` в `[0, 1)`, bool,
порядок и отсутствие разрывов/перекрытий; первый budget_from равен нулю,
budget_to=null допустим и обязателен только у последней строки.
Отсутствие/повреждение таблицы — ошибка выбранного конфига до API,
с изоляцией ошибок чужих файлов. Добавить таблицы всем встроенным INDEX,
включая одноинструментные; конкретные limit не подменять общим порогом.
Стратегия преобразует свои настройки в нейтральное решение StrategyPlan;
COMPOSITE и исполнитель не читают конфиг INDEX и не распознают классы детей.
Контракт результата определён ниже. Пороги детей не усредняются
в единый порог COMPOSITE: у него отдельная межкомпонентная проверка.

### Порог соотношения частей COMPOSITE

При реализации добавить в корень конфига COMPOSITE поле:

```json
{
  "name": "BALANCED",
  "component_drift_limit": "0.20",
  "components": [
    {"algoritm": "INDEX", "src": "IMOEX", "weight": "0.684210526"},
    {"algoritm": "INDEX", "src": "OBLG", "weight": "0.210526316"},
    {"algoritm": "INDEX", "src": "GOLD", "weight": "0.105263158"}
  ]
}
```

Поле — обязательная конечная Decimal-строка в `[0, 1)`. Имена алгоритмов,
источников и доли сохраняются. Это не резерв и не торговый threshold объёма.
Вложенный COMPOSITE имеет собственный порог и применяет тот же алгоритм
в пределах выделенного ему бюджета. Само поле пока не добавлено в рабочий
BALANCED: текущий загрузчик отклонит его как неизвестное. Изменение JSON,
CompositeConfig, PreparedCompositeSource и валидатора выполнить атомарно.

Максимальное относительное отклонение доли части согласовано. Для расчёта долей
учитывать норму резерва, а не сравнивать чистую стоимость бумаг с gross-weights.
После виртуальной атрибуции оценивать стоимость V_i бумаг каждого ребёнка.
Для листа восстановленный капитал C_i = V_i / (1 - reserve_i), затем
текущая доля p_i = C_i / sum(C). Целевая доля t_i = weight_i / sum(weights).
Для вложенного COMPOSITE использовать C_i = V_i / f_i, где f_i — сумма
exposures его нейтрального профиля: она учитывает резервы листьев и намеренно
нераспределённую внутреннюю долю. Это не раскрывает конфиги детей исполнителю.
Резерв не появляется физически от такого деления; C_i — оценка капитала,
не доступные деньги. Случайные остатки лотности этим не восстанавливаются.

Согласован общий баланс: W = sum(weights), B_children = B * W,
нераспределённая часть = B * (1 - W). После уточнения пользователя:
выше порога новый бюджет B_i = B * weight_i, ниже — сохранять капитал
детей и направлять доступное пополнение пропорционально денежным недовесам.
Формулу B_children * p_i не применять ко всем режимам: она закрепляла бы перевес.
Для первого заполнения, когда sum(C)=0, использовать B_i = B * weight_i.
Только ниже или на пороге при B_children < sum(C) пропорционально сократить бюджеты:
B_i = B_children * C_i / sum(C). Числовое сокращение из-за одной лишь нехватки
резерва не обязывает продавать; сокращение капитала обязывает. Причину
классифицировать по нейтральному профилю, как описано в приоритетах ниже.
Старый бюджет — оценка C_i текущего снимка, не сохранённое значение прошлого запуска.
Проверять sum(B_i) = B_children с детерминированной коррекцией Decimal-остатка.
Не прибавлять оценочную выручку повторно и не вычитать резерв здесь второй раз.

## Оценка текущего капитала детей COMPOSITE

### Профиль состава через общий контракт

Тикер конфига сопоставляется с инструментом при загрузке снимка самого ребёнка.
Далее позиции назначения сопоставляются по UID: текущий PortfolioEntry содержит
UID, но не тикер (`autorepeater/strategy_data.py:20`). Нельзя объединять разные
UID только из-за одинакового тикера: это могут быть разные инструменты/режимы.
Если выбранный UID изменился, старую позицию нельзя незаметно приписывать новому.

Добавить всем стратегиям одинаковый чистый метод
`allocation_profile(snapshot) -> AllocationProfile`. Он возвращает карту
`exposures: dict[str, Decimal]`: UID -> идеальная доля стоимости бумаги в единице
полного бюджета стратегии, до округления лотов и исключения хвоста. Коэффициенты
только конечные неотрицательные Decimal, UID — непустые строки; их сумма
не больше 1. Общий DTO может представлять профиль с нулевой суммой,
но рабочий финансовый расчёт требует f > 0 для восстановления капитала.
Непригодный профиль вызывает ошибку до торгов, не деление на ноль или fallback.
Профиль содержит также UID с нулевым коэффициентом и оценки prices из того же
снимка, чтобы собрать общую карту цен без повторного I/O. Он не является целью
или разрешением торговли.
Остаток до 1 описывает идеальную денежную долю, а не фактически доступные деньги.
Отдельный коэффициент reserve_fraction описывает только денежную долю резервов
листьев, без намеренно нераспределённых долей COMPOSITE и лотного остатка.
У листа он равен собственному reserve; у COMPOSITE — сумме
weight * child.reserve_fraction. Проверять конечность, неотрицательность и
sum(exposures) + reserve_fraction <= 1 с принятой Decimal-коррекцией.
Это нейтральное число для чистого распределителя стратегии, не конфиг или
правило резерва в исполнителе. Оно позволяет отличить нехватку резерва от
сокращения капитала и не принять всю денежную долю вложенного узла за резерв.

- INDEX сам получает внутренние денежные веса из тех же текущих капитализаций,
  которые использует `_capitalizations` (`autorepeater/index_strategy.py:147`):
  `reference_index_capitalization * current_price / reference_price`, затем
  нормировка на их сумму. Не использовать неизменные справочные проценты
  reference_weight вместо текущих расчётных весов. Коэффициент UID равен
  внутреннему весу, умноженному на `(1 - reserve)` самого INDEX.
  Остаток Decimal-нормировки корректировать детерминированно, чтобы сумма
  коэффициентов равнялась `(1 - reserve)` и не стала больше 1 от округления.
- ACCOUNT сам рассчитывает веса по стоимости позиций собственного снимка,
  исключая валюты, затем умножает на `(1 - reserve)`. Сохранять принятую
  nano-квантизацию стоимости источника; проверка пригодности данных профиля
  не меняет арифметику обычного build_target. Для нулевой/непригодной стоимости
  источника профиль не вычислять делением на ноль: явная ошибка до торговли.
- COMPOSITE возвращает по каждому UID сумму
  `component.weight * child.exposures[uid]`. Собственного резерва нет;
  вложенные веса и резерв листа входят в коэффициент ровно один раз.
  Повторные вхождения одного ребёнка остаются отдельными областями.

Метод работает по уже загруженному снимку, без нового I/O. Снимок по-прежнему
непрозрачен для родителя и исполнителя. COMPOSITE не читает JSON детей,
не распознаёт ACCOUNT/INDEX по классу/имени и не разбирает их снимки.
Стратегия сама раскрывает нейтральный профиль, общий чистый помощник проверяет
и распределяет его. Мигрировать Protocol, validate_strategy, встроенные
алгоритмы, тестовые реализации и фикстуры вместе. Для других алгоритмов это
тот же API; SDK и конфигурационные схемы в AllocationProfile не входят.

### Виртуальное распределение имеющихся позиций

У каждого вхождения ребёнка есть стабильный в пределах подготовки путь
индексов компонентов; одинаковые algoritm/src не объединяются. Для текущего
узла и каждого UID:

```text
Q(uid) = фактическое количество штук, выделенное этому узлу родителем
a(child, uid) = weight(child) * exposure(child, uid)
S(uid) = сумма положительных a(child, uid)
Q(child, uid) = Q(uid) * a(child, uid) / S(uid)
V(child) = сумма Q(child, uid) * общая цена оценки(uid)
```

Если положительный кандидат один, вся позиция относится к нему независимо от
его weight. При нескольких кандидатах распределять по формуле. Делить не
целые торговые лоты, а виртуальное количество штук через Decimal: округление
владения до лотов создаёт ненужные ступени в оценке бюджета и порога.
Остаток арифметического деления детерминированно отдать кандидату с наибольшим
коэффициентом, при равенстве — первому в порядке компонентов; проверить
неотрицательность и точное сохранение количества способом из раздела
«Decimal-коррекция». Реальные заявки по-прежнему
только целыми лотами, после объединения и ограничений общего плана исполнения.

Пример без резервов: доли детей A/B = 0.6/0.4, внутренние веса общего
инструмента X = 0.5/0.25. Претензии 0.30/0.10, поэтому 10 имеющихся лотов X
виртуально распределяются как 7.5/2.5 лота, а не как 10/10 или 8/2.
Для остальных инструментов применяется тот же независимый расчёт.

Каждый уровень делит только полученное от родителя количество, не перечитывает
полный dst. Общая цена UID на всём дереве одна: цена назначения для имеющейся
позиции, как в разделе оценок ниже. Цены разных детей не должны создавать
разную стоимость одного и того же фактического количества. Сумма стоимостей
всех конечных областей и неприписанных позиций равна `sum(Q * mark)` при точном
суммировании конечных Decimal. Это не тождество с отдельно nano-квантованной
оценкой каждой исходной позиции для B: B сохраняет прежнюю арифметику,
а атрибуция сохраняет количества и их стоимость в общей карте marks;
денежные позиции в это распределение не входят и не дублируются между детьми.

UID без положительного кандидата относится к явной неприписанной области,
а не к первому ребёнку и не исчезает из общей стоимости счёта. Согласовано
считать её денежной частью экономического бюджета и распределять между
детьми с соблюдением выбранного режима родителя. Оценочная стоимость U
входит в B ровно один раз. При weights 0.6/0.3 в пул детей входит U * 0.9;
при первоначальном/целевом распределении для U=10000 выделяется 6000/3000,
остальные 1000 сохраняются. В денежном режиме ниже порога пополнение
распределяется в недовесы, как дополнительно уточнил пользователь.
Для превращения такой бумаги в рубли требуется продажа, разрешённая независимо
от порога COMPOSITE. Не выдавать U за доступные деньги до полного исполнения.
Сначала проверить все основные цели; ошибка ребёнка запрещает и эти продажи.
Обрабатывать UID, известный только с нулевыми коэффициентами,
тем же способом. Старую бумагу, отсутствующую только в исполнимой цели из-за
хвоста/лотности, профиль полного состава продолжает распознавать.

### Риск оценки и отсутствие круговой зависимости

Профиль строится до выбора адаптивных бюджетов, без вызова build_target с ещё
неизвестным бюджетом. Используется полный теоретический состав, а не состав
покупок после усечения хвоста: иначе владение зависело бы от бюджета, который
сам рассчитывается из владения. Лотность не округляет профиль.

Доступны только совокупные позиции счёта, а не история их распределения между
стратегиями. Поэтому для общих UID нельзя однозначно восстановить, какой
ребёнок фактически покупал бумагу. Одинаковые позиции могут возникнуть из разных
историй. Приняты риски: виртуальная атрибуция может скрыть или преувеличить
отклонение частей, меняться с котировками/конфигом без сделки и отличаться от
состава усечённого хвоста. Дробное распределение уменьшает дополнительную
ошибку округления, но не доказывает меньшую ошибку относительно неизвестной
истории. Без пересечений распознавание принадлежности точно по выбранным UID.

Не добавлять оптимизацию с подбором скрытой истории, хранилище сделок или кеш
владения. При пересечениях писать WARNING с UID, путями кандидатов, коэффициентами
и распределёнными количествами; без секретов. В README указать оценочный
характер долей. Калибровка должна отдельно оценивать ложные сигналы при общих
UID, изменении цен, усечении хвоста и повторных проверках без сделки.

Эта атрибуция определяет стоимость бумаг, восстановленный капитал и доли.
Общий бюджет детей, режимы и сокращение дефицитного пула описаны выше.
Слияние ограниченных планов сохраняет принадлежность денег областям.
Виртуальные количества
не являются физически раздельными позициями: запрещено продавать и покупать
один UID между детьми ради изменения одного только виртуального владельца.
Внешняя заявка — чистая разница общей позиции после проверки ограничений.

## Границы слоёв

- Стратегии строят цели и объявляют решение о необходимости ребалансировки,
  но не отправляют сделки. Механизм исполнения не выбирает вместо них алгоритм.
- `TargetPortfolio` оставить чистым результатом расчёта количеств и цен,
  без cash_floor, режима торговли и денежных разрешений. Эти данные хранит
  отдельный StrategyPlan: cash_floor обязателен, конечен и неотрицателен.
  Это минимальный остаток денег, не процент резерва и не ссылка на конфиг.
  Рабочий валидатор плана отвергает пустую/полностью нулевую основную цель
  до любых заявок; общий validate_target сохраняет прежнюю область значений.
- ACCOUNT и INDEX сообщают сумму, сохраняемую по собственному резерву
  от выделенного полного бюджета. Не вычитать стоимость цели из бюджета:
  случайные остатки лотного округления не входят в `cash_floor`.
- COMPOSITE складывает `cash_floor` детей и добавляет нераспределённую долю бюджета;
  вложенность и повторные компоненты обрабатываются тем же способом.
- Сохраняемый остаток COMPOSITE нельзя заново вычислять через объединённые цены:
  для одинакового UID они могут отличаться от оценок отдельных детей.
- Чистая политика получает собственные DTO назначения и цели, возвращает
  разрешения `BUY_ONLY` или `REBALANCE` для соответствующего уровня
  с причиной и рассчитанными метриками, а не один безусловный флаг продажи всего.
  Итоговый SKIP при отсутствии исполнимых заявок определяет планировщик.
  Политика не импортирует SDK, реестр или конкретные стратегии и не выполняет I/O.
- Допуск конкретного состава приходит через нейтральный результат стратегии.
  INDEX сам выбирает строку своего конфига; исполнитель не знает имени IMOEX,
  количества бумаг, схем таблиц или внутренних резервов.
- Вход расчёта стратегии дополнить нейтральным контекстом назначения и
  выделенного бюджета: единый build_plan(snapshot, context),
  где context содержит новый/старый budget и собственные DTO позиций/денег;
  SDK DTO и торгового клиента в нём нет. Все алгоритмы мигрируют одинаково.
- Результат сохраняет основную цель, cash_floor, решение стратегии о продажах,
  бюджет денег и путь области. Для COMPOSITE — также упорядоченные результаты
  детей, до объединения UID. cash_floor хранится только в StrategyPlan,
  не дублируется в TargetPortfolio. Детализация нейтрального DTO ниже.
- При уменьшении нового бюджета, требующем сокращения капитала, стратегия
  обязана объявить ребалансировку; несоблюдение обязательства является ошибкой
  контракта. Одно сравнение budget < previous_budget недостаточно: причина
  передаётся нейтральным budget_reduction_requires_rebalance, без разбора
  конфигов исполнителем. Нехватка только резерва ниже/на пороге его не включает.
  Старый бюджет — оценённый по текущему снимку капитал с поправкой на резерв,
  нулевой допустим при первоначальном заполнении. Новый — положительный конечный.
- COMPOSITE должен знать границы портфеля детей через нейтральные данные,
  не разбирать их непрозрачные снимки и не определять тип по имени/классу.
  Получать allocation_profile и применять описанную виртуальную атрибуцию;
  нельзя дважды учитывать полную позицию в капитале двух детей или денежный остаток.
- Разрешение внутренней продажи IMOEX не разрешает продажу GOLD ради покупки
  IMOEX, если родитель не разрешил межкомпонентный перенос. Нейтральный план
  должен сохранять количественные/денежные ограничения областей до объединения,
  а исполнитель применять их без чтения стратегических конфигов.
- Отдельный чистый планировщик ограничивает покупки доступным бюджетом и лотами.
- Оркестратор собирает данные и план; отправка выполняется только после всех
  проверок. Исполнитель не читает резерв или конфиги стратегий.
- События и таймер лишь инициируют проверку: само событие не разрешает сделки.

## Решение политики

### Между частями COMPOSITE

Для каждой части сначала оценить текущий капитал и целевую долю. Выбранный
критерий — `max(abs(actual_share - target_share) / target_share)`.
actual_share считается по восстановленному капиталу с резервом, не только V_i.
При целевой доле 10% и фактической 12% ошибка 20%, не больше порога;
при 13% ошибка 30%, разрешено межкомпонентное перераспределение.
В пустом первоначальном портфеле доли не вычислять делением на ноль:
первоначальное распределение использует конфигурационные weights и доступность денег.
Покупочный сигнал теперь означает наличие доступного исполнимого лота,
а не превышение денежного лимита.

Общий бюджет детей B_children всегда равен B * sum(weights).
Выше порога B_i = B * weight_i; ниже порога направлять новые деньги в недовесы,
не финансировать их продажей перевеса соседа. При sum(C)=0 распределять по weights.
Конкретные формулы ниже порога, если B_children >= sum(C):
F = B_children - sum(C), D_i = max(0, B * weight_i - C_i),
Delta_i = F * D_i / sum(D), B_i = C_i + Delta_i.
Проверять денежные ограничения, отсутствие двойного резерва и sum(B_i).
При F=0 не делить на sum(D)=0. Только ниже или на пороге при B_children < sum(C) применять согласованное
пропорциональное сокращение B_i = B_children * C_i / sum(C). Оно вызывает
обязательную ребалансировку только при сокращении капитала, не при одной лишь
нехватке резерва; собственный критерий ребёнка действует независимо.
После любого распределения проверить положительность
всех новых бюджетов; нулевой ребёнок отменяет весь пересчёт до любых торгов.

Логика долей проверяется до выбора бюджетов детей. В каждом дочернем портфеле
затем применяются его внутренние критерии: INDEX — своя таблица, вложенный
COMPOSITE — собственное соотношение частей, ACCOUNT — допуск своего конфига.
Если новый бюджет ребёнка меньше старого и требуется сокращение капитала,
обязательный пересчёт имеет
приоритет над внутренним допуском: GOLD не может отклонить уменьшение
бюджета только потому, что внутри него всегда одна бумага.
Продажи и покупки ребёнка могут
произойти даже без внешнего межкомпонентного разрешения, но не для вывода
капитала в другой ребёнок. Проценты порогов детей не усредняются.

Использовать общий баланс и восстановление капитала выше. Распределение
реально доступных денег и оценочной неприписанной части не смешивать.
Не вычитать общий
cash_floor перед распределением и затем повторно резервировать те же деньги
в листьях. Двойное применение резерва проверяется отдельными тестами.

### Внутри отдельной части

Для положительно оцениваемой вложенной части:

```text
вес имеющейся бумаги = стоимость позиции / стоимость вложенной части
вес целевой бумаги = стоимость целевой позиции / стоимость целевых бумаг
отклонение = сумма модулей разниц весов по объединению UID / 2
бюджет покупок = доступные рубли области после блокировок и её cash_floor
возможность покупки = есть целый исполнимый лот, уменьшающий недовес,
                     укладывающийся в бюджет покупок и целевые количества
```

Деньги не входят в формулу отклонения пропорций. Один UID оценивается одинаковой
ценой в фактической и контрольной целевой позиции. Методика выбора общей карты
оценок должна быть явной и детерминированной; не смешивать цену исполнения с
оценкой для решения политики.

Если budget_reduction_requires_rebalance=true, стратегия обязана рассчитать
`REBALANCE`. При false одного budget < previous_budget недостаточно:
резервный дефицит ниже/на пороге не разрешает продажу.
Иначе при строгом превышении её допуска выбирается внутренний `REBALANCE`.
Для IMOEX это значение выбранной строки таблицы с уже включённым запасом;
дополнительного общего лимита нет. Выбор строки — полный бюджет IMOEX с
деньгами. Проверка COMPOSITE выше независима от этой внутренней метрики.
Иначе стратегия объявляет `BUY_ONLY`, без денежного порога. Планировщик
проверяет наличие исполнимой покупки; если её нет, итог прохода `SKIP`.
Равенство порогу отклонения само по себе не разрешает продажи,
но не отменяет обязательный пересчёт при требуемом сокращении капитала.
Внутреннее REBALANCE
ребёнка не переводит остальных детей в режим разрешённых продаж.
Для BUY_ONLY использовать весь реально доступный бюджет области после
сохраняемого остатка. Оценочные деньги от непроданных бумаг не расходовать.

При пустом вложенном портфеле нельзя делить на ноль: первоначальные покупки
проверяются доступностью лота, без автоматического разрешения продаж.
Пустая/полностью нулевая основная цель — ERROR и исключение без любых заявок,
включая продажи неприписанных бумаг и debug. Любой такой ребёнок отменяет
пересчёт всего COMPOSITE, без частичного продолжения.
Повреждённые данные остаются исключением, а не пустой целью или сигналом покупки.

## Технические решения и условия их проверки

### 1. Контрольная цель, независимая от пополнения

Построить две цели из одного свежего снимка, без повторного I/O.
Основная цель использует полную стоимость счёта и предназначена для сделок.
Контрольная цель использует стоимость уже вложенной части и предназначена
только для проверки отклонения. Изменение свободных денег тогда не меняет
контрольный бюджет, но может снизить порог из таблицы по основному бюджету;
такое разрешение продаж согласовано как допустимый риск.

Новая бумага из хвоста основной цели может быть куплена без продаж, если
доступных денег хватает на лот с сохранением `cash_floor`. Для внутренних
продаж нужен критерий стратегии либо обязательное сокращение капитала;
уменьшение только расчётного резерва таким основанием не является.

Обязательно проверить повторное
применение внутренних резервов к контрольному бюджету, границы лотного
округления, пустую контрольную цель листа внутри COMPOSITE и отсутствие продаж из-за
контрольной цели на уже правильно собранном портфеле. Калибровка уже выявила
ненулевое ложное отклонение. Согласован путь эмпирического допуска IMOEX,
но пока не проверено, что рабочая база выбора диапазона и композиция допусков
покрывают калибровочные ошибки при согласованном выборе полного бюджета.
Переход в диапазон с меньшим порогом после пополнения допускается как принятый
риск. Проверять денежный режим без продаж в неизменном диапазоне отдельно
от этого исключения; не заявлять безусловную защиту от продаж при пополнении.
Пустая/полностью нулевая контрольная цель не позволяет оценить отклонение:
сообщить INFO, отключить только этот внутренний сигнал и оставить возможность
покупок по основной цели. Ошибка основной цели остаётся фатальной.
Обязательное сокращение капитала не зависит от контрольной метрики;
сокращение только расчётного резерва не является таким основанием.
При пустой вложенной части контрольную цель не строить с нулевым бюджетом.
Локальное состояние облачной функции не использовать.

### 2. Минимальный сохраняемый остаток и оценки

`cash_floor` считается от обновлённого бюджета. Это не препятствует обнаружению
избытка денег: при условном резерве 1% и пополнении с 100000 до 102000 рублей
остаток повышается с 1000 до 1020, доступные деньги с 1000 до 3000,
а избыток становится 1980 рублей. Пополнение не объявляется доказанным фактом:
деньги могли прийти также дивидендами или купонами.

Для листа `cash_floor = budget * reserve`; исполнитель получает только сумму.
Для COMPOSITE `cash_floor = сумма cash_floor детей + нераспределённый бюджет`.
Вложенные доли учитываются на каждом уровне, без повторного резерва композиции.
Не учитывать случайный остаток от недоступного лота как обязательный запас.
Он может финансировать другие недовешенные позиции в пределах выделенного
бюджета; принадлежность денег детям сохранять по правилам родителя.

Обязательность cash_floor относится к StrategyPlan, включая сторонние
реализации. Отсутствие поля не подменять нулём. TargetPortfolio и его
позиционные аргументы quantities/prices/empty_reason не менять: чистый
calculate_index_target получает уже инвестируемый бюджет и не знает резерв.
Это устраняет необходимость протаскивать gross-бюджет и исполнительные
параметры в чистый индексный расчётчик и существующий калибратор.

Проверки нормировки принадлежат политике, а не общему `validate_target`:
отрицательные количества и конечные неположительные цены не запрещать в
общем контракте. Согласовано ограничение нового режима длинными позициями:
при отрицательном фактическом или целевом количестве отказ до отправки заявок.
Поддержка коротких позиций — отдельная будущая доработка исполнителя.
Неположительная оценка ненулевой позиции не позволяет безопасно считать
денежный недовес/доли: понятная ошибка данных до заявок без fallback на старый
порог. Это проверка нового финансового расчёта, не сужение validate_target.
Основная цель без количеств или только с нулями вызывает ошибку до торгов,
как согласовано. Индивидуальные нули в непустой ненулевой цели сохраняют
смысл удаления отдельной позиции. Обычный первоначально пустой портфель
проверяется по доступности покупок, не по общему денежному порогу.
Для одинакового UID использовать цену назначения, если позиция там есть,
иначе максимум оценок этого UID из свежих allocation_profile всего дерева.
Профили собираются до решений политики, поэтому нет зависимости общей карты
цен от уже принятого решения или порядка обхода детей.
Отсутствующую оценку не восстанавливать скрытым дополнительным I/O.

### 3. Распределение бюджета покупок

Покупки всех недовесов могут требовать денег от запрещённых продаж перевесов.
Поэтому недостаточно удалить продажи из старого списка заявок.
Распределять доступный избыток между недовесами основной цели. Прежнее правило
строгого уменьшения нормированного отклонения бумаг не использовать:
при A=40/B=40 и цели A=50/B=50 оно не разрешает ни одной покупки,
а у одноинструментного состава доля всегда 100% независимо от недовеса.
Согласованный критерий:

```text
недовес = сумма max(0, целевое количество - текущее количество) * цена
приоритет лота = недовес до покупки - недовес после покупки
```

Выбирать исполнимый лот с наибольшим положительным уменьшением недовеса,
не делить приоритет на стоимость лота. При равенстве использовать порядок UID.
После покупки обновлять виртуальный портфель и деньги, пересчитывать
приоритеты. Цены фиксированы для одного плана и одинаковы с обеих сторон
сравнения. Деление на неизменный полный бюджет не изменяет порядок выбора
и для этого денежного критерия не требуется. Пустой портфель и единственный
тикер обрабатываются той же формулой, без искусственного начального отклонения.
Объединять выбранные лоты одного UID в одну заявку.
Не округлять покупку сверх денежного бюджета или целевого количества.
Если нет доступного лота по согласованной метрике, завершить план с INFO.
Это детерминированный пошаговый выбор, не обещание глобально оптимального
решения для всех комбинаций лотов. Закрепить критерий примерами и тестами.

### 4. Общая цель и фактические деньги после продаж

Согласована прежняя схема полного пересчёта: оценить весь портфель с деньгами,
получить новую основную цель и продавать/покупать только разницу с ней.
Оценка «если всё продать» не требует фактической продажи всего портфеля;
предполагаемая выручка уже включена в стоимость бумаг и не добавляется к бюджету.

Изменение относится не к этой арифметике, а к SDK-исполнению. В текущем
`post_orders` продажа отправляется перед покупками, но возвращение order_id
не проверяется как подтверждение полного исполнения. При 1000 свободных рублей,
продаже на 5000 и покупке на 5500 покупка обеспечена только после фактического
поступления выручки. Частичное исполнение и комиссия тоже меняют доступную сумму.

Согласовано: после каждой продажи проверять подтверждение полного исполнения
в ответе SDK. В установленном SDK PostOrderResponse содержит
execution_report_status, lots_requested и lots_executed; полный статус —
EXECUTION_REPORT_STATUS_FILL. Требовать одновременно этот статус и равенство
обоих чисел лотов количеству отправленной заявки. Один order_id недостаточен.

При NEW, PARTIALLYFILL, REJECTED, CANCELLED, UNSPECIFIED, повреждённом ответе
или транспортной ошибке остановить текущий торговый проход и сообщить ERROR
с order_id, UID, статусом и запрошенными/исполненными лотами без секретов.
Оставшиеся продажи и все покупки не отправлять. Не добавлять бесконечное
ожидание, автоматический повтор той же заявки или скрытую отмену принятой заявки.
На следующей проверке получать свежие позиции, блокировки и активные заявки:
остановка не означает, что заявка NEW никогда не исполнится позже.

После полного подтверждения всей фазы продаж перечитать доступные деньги и
ограничить покупочный план ими с сохранением cash_floor. Оценочную выручку
не использовать вместо фактической; бюджет основной цели не увеличивать
повторно на сумму продаж. Получение свежих денежных данных находится на
границе исполнения с таймаутами и переводом транспортных ошибок.
Уже исполненные сделки не откатываются, остановка относится к текущему проходу,
а не к постоянной блокировке следующих запусков.

### 5. Локальные инициаторы без таймера

Текущий `mainflow` сначала выполняет пересчёт, затем читает `position_events`
по объявленным стратегиями счетам и вызывает пересчёт при `should_rebalance=True`.
INDEX принимает непустые события назначения без блокировок денег и бумаг;
COMPOSITE объединяет решения детей. ACCOUNT сейчас принимает пополнение
назначения только без бумаг: это условие доработать для непустого dst.

Новый таймер не вводить. Подходящие события запускают проверку политики,
а не сами сделки. Изменение одних котировок не является таким событием:
при отсутствии событий новая оценка откладывается до следующего события или
перезапуска CLI. Облачный внешний таймер остаётся без изменений.

## Уточнённый контракт и денежные ограничения

### Общий API стратегий

Итоговый Protocol содержит пять методов, без обязательного наследования:

```python
load_snapshot(data) -> object
allocation_profile(snapshot) -> AllocationProfile
build_plan(snapshot, context: StrategyContext) -> StrategyPlan
event_accounts(dst_account_id) -> tuple[str, ...]
should_rebalance(event, dst_account_id) -> bool
```

load_snapshot выполняет только чтение через StrategyData. Снимок принадлежит
стратегии; родитель передаёт его обратно, но не разбирает. Профиль и план чистые:
не читают конфиги повторно, не вызывают SDK, не отправляют заявки.
should_rebalance сохраняет имя, но означает только необходимость проверки.
Реальную подписку открывает движок, методы событий её не открывают.

Точки изменения: [Strategy:37](../../autorepeater/strategy_contract.py#L37),
[validate_strategy:53](../../autorepeater/strategy_contract.py#L53),
[общий вызов:179](../../autorepeater/repeater.py#L179).
На финальном переключении заменить build_target в Protocol на build_plan
и добавить allocation_profile в callable-проверку. Проверять возвращаемые
DTO после реального вызова, не вызывать методы из validate_strategy до Client.
Циклы, фабрики, фиксация конфигов и порядок подготовки остаются прежними.

Чистые расчётчики целей листов не становятся исполнителями. Существующие
[ACCOUNT:57](../../autorepeater/account_strategy.py#L57) и
[INDEX:107](../../autorepeater/index_strategy.py#L107) можно оставить внутренними
помощниками build_target(snapshot, budget), вызываемыми из build_plan дважды.
Это используемый расчёт, не совместимая обёртка общего контракта. Прежний
фиксированный builder [COMPOSITE:53](../../autorepeater/composite_strategy.py#L53)
после переключения заменить новой композицией планов, не оставлять второй
рабочий способ распределения бюджета.

### Нейтральные модели

Создать strategy_plan.py; модели не импортируют SDK или конкретные стратегии.

| Модель | Поля и смысл |
| --- | --- |
| AllocationProfile | exposures и prices по UID; reserve_fraction: идеальная денежная доля резервов листьев; состав до округления и хвоста; без ссылок на конфиг или стратегии |
| StrategyContext | path: tuple индексов компонентов; budget: новый полный бюджет; previous_budget: оценка C; budget_reduction_requires_rebalance: bool, отдельное основание обязательного сокращения капитала; positions: только выделенные узлу PortfolioEntry; marks: общая карта оценок |
| StrategyDecision | разрешение BUY_ONLY/REBALANCE, redistribution_allowed: bool, причина, числовая метрика или None, допуск или None; режим родителя не стирает решения детей |
| StrategyPlan | path, budget, target: TargetPortfolio, cash_floor, decision, children: упорядоченный tuple планов; unassigned: неприписанные количества этого узла |

Контрольную цель лист строит внутри build_plan только для расчёта decision;
исполнитель её не получает и не строит. COMPOSITE не строит дополнительную
контрольную общую цель: его критерий — доли восстановленных капиталов;
внутренние решения уже представлены детьми. Это исключает повторную композицию
резервов и таблиц при контрольном пересчёте.

Стратегия объявляет разрешение продаж и основную цель; окончательный SKIP
при отсутствии исполнимого лота определяет планировщик. Доступность конкретной
сделки не требует SDK-клиента внутри стратегии. В StrategyContext не включать
торговые сервисы и фиктивную выручку; реально доступные деньги относятся к
ExecutionSnapshot и однопроходному исполнению.

redistribution_allowed является явным денежным разрешением, не выводится
исполнителем из строки причины или общего режима REBALANCE. У листа false;
у COMPOSITE true только при строгом превышении его порога частей. Обязательное
REBALANCE при сокращении капитала ниже порога не разрешает перенос между
соседями: оно сокращает их капитал согласно выбранным новым бюджетам.
Капитал сверх уменьшенного бюджета возвращается родителю в рамках этого
сокращения, а не выдаётся ребёнку как деньги сверх лимита. Исключение продажи
неприписанных бумаг также представлено отдельной областью, не требует
redistribution_allowed=true для всей композиции.

cash_floor хранится только в StrategyPlan. Для листа это budget * reserve,
для композиции — сумма детских floor плюс budget * (1 - sum(weights)).
Проверять 0 <= cash_floor <= budget, соответствие path/budget переданному
StrategyContext. budget_reduction_requires_rebalance имеет строго bool-тип;
true допустимо только при budget < previous_budget и требует REBALANCE.
Обратное неверно: уменьшение только расчётного резерва не требует REBALANCE.
Проверка финансового плана отдельно
от [validate_target:14](../../autorepeater/portfolio.py#L14): основная цель
непуста и имеет положительное количество хотя бы одного UID, отрицательные
количества нового режима запрещены, оценки ненулевых позиций положительны.
Пустая контрольная цель допускается и отключает только внутренний сигнал.
Нулевое старое C допустимо; новый бюджет каждого узла строго положителен.

Вложения и повторные компоненты различаются по path, не по строке имени.
Бюджет каждого узла и все основные цели проверяются до первой заявки,
включая продажи неприписанных бумаг и debug. Суммы сохраняются с принятой
Decimal-коррекцией; нельзя молча округлять плохой отрицательный остаток к нулю.

### Приоритет бюджетных правил

Правила применяются строго в следующем порядке:

1. Непригодные профили, отрицательные позиции и неверные цены — ошибка.
2. Если sum(C)=0, бюджеты детей B * weight, без вычисления долей.
3. Если максимальная относительная ошибка строго выше component_drift_limit,
   бюджеты B * weight, даже при M < sum(C). Это последнее подтверждение пользователя.
4. Иначе при M < sum(C) бюджеты M * C_i / sum(C): пропорциональное сокращение.
   Если дефицит только резервный, обязательные продажи не разрешать.
5. Иначе сохранить C_i и распределить M - sum(C) в денежные недовесы.
6. Проверить положительность каждого бюджета и его сохранение в общем пуле.

Для B=100000, weights=0.6/0.3, C=80000/20000 ошибка доли второй части 40%:
выбрать 60000/30000, не 72000/18000. Для C=67000/33000 ошибка меньше 20%,
при том же дефиците выбрать 60300/29700; при нулевых резервах оба ребёнка
обязаны пересчитаться. Для ненулевых резервов сначала классифицировать дефицит.
При F>0 сумма D не может быть нулевой в точной арифметике, поскольку
sum(D) >= M - sum(C). Если проверка с Decimal выявила существенное нарушение,
отклонить данные; исправлять только арифметический остаток установленным способом.

Классификация ниже/на пороге выполняется внутри стратегии, не исполнителя:
R = sum(C_i * profile_i.reserve_fraction), A = sum(C) - R.
При A <= M < sum(C) пул покрывает капитал без расчётных резервов: дефицит
только резервный, budget_reduction_requires_rebalance=false. При M < A
дефицит затрагивает капитал: для уменьшенных бюджетов флаг true.
Намеренно нераспределённая доля вложенного узла входит в A, а не в R.
Выше порога используется целевое распределение; уменьшенному ребёнку флаг true.
Если родитель уже требует сокращения капитала, резервное исключение вложенного
узла не отменяет это требование для его уменьшенных дочерних бюджетов.
Классификация использует уже принятые Decimal-правила, без нового epsilon.

Точная формула после выбора и коррекции всех B_i, именно итоговых бюджетов:

```text
S = sum(C_i); W = sum(weight_i); M = B * W
R = sum(C_i * rho_i); A = S - R; rho_i = profile_i.reserve_fraction
parent_force = context.budget_reduction_requires_rebalance
above_limit = S > 0 and component_drift > component_drift_limit
capital_shortfall = S > 0 and M < A
force_i = (B_i < C_i) and (parent_force or above_limit or capital_shortfall)
```

`force_i` передаётся как budget_reduction_requires_rebalance ребёнка.
Нельзя вычислять `(parent_force or local_force) and not reserve_shortfall`:
так локальное исключение погасит уже обязательное сокращение предка.
При A=M и parent_force=false ниже/на пороге force_i=false; при M<A
уменьшенный ребёнок получает true. При S=0 C_i=0, первоначальные положительные
B_i не включают force. Выше порога уменьшенные бюджеты требуют REBALANCE
даже при A<=M. Неизменный/увеличенный B_i сам по себе force не получает.
Собственный сигнал ребёнка проверяется независимо от этого флага.
REBALANCE узла не является безусловным разрешением SELL всем потомкам:
каждый уменьшенный потомок наследует требование по этой же формуле,
а неуменьшенный сохраняет свой критерий. redistribution_allowed вычисляется
отдельно по собственному строгому превышению порога, не из parent_force.

Пример наследования: вложенному узлу уже передан parent_force=true;
у него S=100, R=10, A=90, M=95 и B_i<C_i. Локально дефицит только резервный,
но force_i=true. При тех же числах без parent_force будет false.
Числовые бюджеты и cash_floor одинаковы; различается основание SELL.

Корневой StrategyContext имеет path=(), budget=B,
previous_budget=C_root и budget_reduction_requires_rebalance=false.
C_root восстанавливается по профилю из распознанных бумаг корня;
неприписанные позиции входят в B и отдельную область, не в C_root.
Корню флаг родительского сокращения не задаётся: он сам применяет свой критерий;
COMPOSITE классифицирует дефицит своего пула указанным способом. У листового
корня C > B из-за одного резерва не разрешает продажи. previous_budget остаётся
оценкой C; не подменять его фактическими деньгами и не хранить историю запусков.
При резервном исключении основная цель и cash_floor считаются по новому бюджету,
но SELL-дельты исполняются только при собственном сигнале ребёнка. Имеющиеся
бумаги могут временно превышать рассчитанную цель; это не ошибка плана.
Физически недостаточный резерв ограничивает покупки, а не ликвидирует бумаги:
остаток восстанавливается последующими поступлениями, без гарантии наличия
полного cash_floor на каждом снимке. Если покупать нечего, сообщить INFO.

### Decimal-коррекция

Точность обычных расчётов остаётся 28, как в
[constants:8](../../autorepeater/constants.py#L8). Сравнения метрик/порогов,
M<A и B_i<C_i строгие, без epsilon и без допуска в рублях/штуках.
Коррекция предназначена только для построенных здесь пропорциональных
разбиений; повреждённые входные суммы/отрицательные значения не исправлять.

Для распределения известного конечного X выбрать получателя остатка заранее:
наибольший коэффициент разбиения, затем порядок компонентов; для UID-профиля
при равенстве лексикографический UID. Остальные части вычислить обычной
Decimal-арифметикой, получателю назначить `X - exact_sum(остальные)`.
Суммирование и это вычитание выполнять в локальной точности, достаточной для
точного сложения конечных десятичных операндов, определяемой их разрядами и
числом слагаемых. Проверить exact_sum(части)==X и допустимые границы;
не повторять проверку округлённым sum при prec=28. Если получатель стал
отрицательным или нарушил свой предел, пересчитать само разбиение с большей
локальной точностью; нельзя обнулить остаток или ослабить денежный предел.
Не менять глобальный Decimal-контекст и чистый calculate_index_target.

Для пополнения распределяется X=F по D_i, затем B_i=C_i+Delta_i;
для сокращения X=M по C_i; для первоначальной/целевой ветки сохраняется
пул M и пропорции weight_i с коррекцией только остатка произведений.
Сохранять также точные суммы exposures до заданного f, атрибуцию Q(uid)
и ограниченный покупочный пул. Сложение C_i+Delta_i и проверку суммы B_i
выполнять без потери уже сохранённого остатка. Верхние пределы областей
не нарушать; нераспределимый покупочный остаток остаётся деньгами.
R/A вычисляются из исправленных профилей и C, затем force_i из исправленных B_i;
нельзя отдельно округлить A к M ради выключения force. Коррекция не меняет
бизнес-границы A=M, равенство допуску или сохранённые коэффициенты JSON.

### Физические деньги и области исполнения

Создать execution_data.py с ExecutionSnapshot: уже загруженный портфель,
свободные деньги по валютам после блокировок, доступные количества бумаг,
активные заявки и готовность лимитов. Источники — портфель, get_positions
и get_orders. StrategyData не получает торговых методов; отчётность не
инициирует дополнительные запросы в расчёте.

Минимальный read-only Protocol ExecutionData:
get_destination(account_id) -> ExecutionSnapshot и
get_trade_rules(account_id, uids) -> dict[str, TradeRules]. Второй результат хранит лотность,
валюту, доступность API/BESTPRICE и собственные немаржинальные BUY/SELL caps
GetMaxLots вместе с доступной суммой в native currency инструмента, не SDK enums.
account_id обязателен: собственные лимиты зависят от счёта. Свежий статус проверять по
market_data.get_trading_status и полным данным инструмента; не возвращать
в рабочий выбор жёсткий фильтр режима TQBR/TQTF или только NORMAL_TRADING.
После продаж тот же get_destination используется повторно; источник стратегии
не перечитывается, основная цель не меняется. Не нужны разные похожие DTO для
каждого этапа чтения и расширение StrategyData исполнительными методами.

Граница отправки: OrderExecutor.submit_order(account_id, intent) -> ExecutionReceipt.
Квитанция содержит нейтральные UID/сторону/order_id, статус, оба числа лотов и
фактические денежные данные по валюте. Семантику денежных полей ответа SDK
подтвердить до преобразования, не считать price полным поступлением по имени.
Транспортные ошибки сохраняют cause; OrderExecutionError обозначает остановку
текущего прохода. Repeater не импортирует SDK или конкретный адаптер.

Создать order_plan.py для чистой сборки количественных/денежных ограничений
из StrategyPlan и ExecutionSnapshot. Внутри одного пересчёта вести простой
словарь денег областей; не хранить его между запусками и не вводить отдельную
систему бухгалтерии или внешний кеш. Для листа предел вложенной стоимости
H_i = budget_i - cash_floor_i. Потенциальный денежный недовес
P_i = max(0, H_i - V_i), но P_i ещё не является доступными рублями.

Из фактически доступных денег сначала сохранить весь корневой cash_floor;
покупочный остаток распределить между P_i пропорционально денежным недовесам,
не более каждого P_i, с детерминированной коррекцией. Если доступного остатка
меньше суммарного P, часть покупок откладывается. Если остатка нет, покупки
не создавать; это не ошибка непустой основной цели. Резервы листьев
не вычитать второй раз после корневого cash_floor.

Выручка внутренней продажи закреплена за её областью, пока родитель не
разрешил межкомпонентный перенос. При redistribution_allowed=true действует выбранное
распределение бюджетов этого родителя; вложенные запреты сохраняются.
Неприписанная выручка распределяется по текущему режиму своего узла.
До подтверждения продажи выручка только условна; она не пополняет денежный
словарь. После подтверждения использовать нормализованный фактический результат
SDK и свежий глобальный остаток, не оценку цены из target. При расхождении
ограничивать деньги областей фактически доступной суммой, не увеличивать их
из соседней области без разрешения. Избыточные покупки откладывать с INFO.

Для общего UID сохранить намерения областей до netting. Отмена встречных
количеств не создаёт выручку: зачёт допустим только при сохранении денежных
ограничений всех затронутых областей. Иначе отложить неподкреплённые покупки,
а не отправлять реальные встречные сделки ради смены виртуального владельца.
Суммарная заявка SELL ограничена свободным физическим количеством;
ни одна область BUY_ONLY не может стать источником проданных бумаг.

Количество заявки целое только на физической границе. В распределении
OrderIntent по путям хранить Decimal-штуки, не требовать целого числа лотов
от каждого виртуального владельца. Их точная сумма равна `lots * lot_size`.
Атрибуция снимка фиксируется на весь проход: после планирования/продажи нельзя
заново поделить остаток по профилю и этим уменьшить защищённую долю BUY_ONLY.
Свежие данные после продажи проверяют физические лимиты, а не переписывают
владение остальных областей. Новый независимый проход атрибутирует снимок заново,
с ранее принятым риском отсутствия истории владения.

Для SELL отдельно проверить свободное физическое количество и сумму
виртуальных количеств областей, разрешивших продажу данного UID.
После ближайшего округления общей разрешённой SELL-дельты число лотов
ограничено `floor(free_quantity / lot_size)` и
`floor(sum(sell_owner_quantity) / lot_size)`. Списание с каждой области
не больше её владения, с BUY_ONLY равно нулю; неприписанная область имеет
собственное разрешение. Нельзя сначала round по детям, а затем сложить лоты.
При lot_size=10, Q_A=7.5 штук и Q_B=2.5 штук, A=REBALANCE с целью 0,
B=BUY_ONLY: продажа одного лота запрещена, хотя физически лот свободен.
Если обе области разрешили полную продажу, один лот допускается с
дробным списанием 7.5/2.5. Невместившаяся дельта откладывается с INFO;
force означает обязательный расчёт, а не возможность нарушить лотность.

Для BUY можно собрать один физический лот из дробных недовесов нескольких
областей одного UID: проверить их денежные лимиты и целевые количества,
затем общую лотность. Например, недовесы 7.5/2.5 штук при lot_size=10
и достаточном финансировании обеих частей допускают один лот, хотя ни один
ребёнок не может самостоятельно купить лот. Детерминированный порядок UID,
затем path сохраняется; нельзя выдать всю покупку первому ребёнку сверх цели.
После ограничений и netting проверить также совокупную основную цель UID:
существующий защищённый перевес не финансирует и не разрешает перепокупку
общего количества. Если допустимого распределения лота нет, отложить покупку.

Netting работает по разрешённым и обеспеченным намерениям, не по сырым
дельтам объединённой main-цели. Зачёт не списывает владение BUY_ONLY, не
создаёт физическую выручку и не разрешает перенос через запрещённую границу
родителя. Отложив необеспеченную BUY-часть, пересчитать чистую дельту и все
пределы перед внешней заявкой. Для UID в одном проходе не отправлять обе
стороны ради смены виртуального владельца. Пределы проверяются до netting,
после него и после округления; суммы вкладов областей сохраняются точно.

Неприписанная область имеет отдельное разрешение SELL независимо от режима
родителя. Поэтому корректен случай «корень BUY_ONLY, продажа лишней бумаги».
Полностью продать нелотный остаток иногда невозможно: остаток сохраняется
в оценке B, но не считается физическими деньгами; сообщить INFO.

Покупки не округлять сверх основной цели. Для дробной цели ACCOUNT возможно
остаться менее чем на один лот ниже цели; это не ошибка и не повод перейти
к round, создающему перепокупку. Для продаж сохранить ближайшее округление
положительной дельты, но ограничить числом свободных лотов и запретить short.

### SDK-граница, таймауты и остановка

Установленный SDK проверен через сигнатуры и dataclass-поля без обращения к
API. GetPositions возвращает money/blocked/securities/limits_loading_in_progress;
GetOrders возвращает orders. PostOrderResponse содержит статус и оба числа лотов.
У unary-методов нет аргумента timeout. Client принимает interceptors и применяет
их через grpc.intercept_channel; добавить sync UnaryUnaryClientInterceptor
с конечным дедлайном, сохраняя меньший уже переданный timeout. Стримы не обрывать
этим дедлайном. Не объявлять timeout параметром SDK-сервисов, которого там нет.

Первичный SDK-аудит получен от независимого агента через пользователя:
официальный RussianInvestments/investAPI, коммит

[operations.proto](https://github.com/RussianInvestments/investAPI/blob/3eaf23a25f598fe483c913184acdbd9132bc68d2/src/docs/contracts/operations.proto)

это не доказывает формулу money-blocked. balance явно незаблокирован,

при любых блокировках. Кредит по свежей разнице cash не принят этой ревизией.
Нельзя закрыть gate предположением об эквивалентности money и cash или считать
конкурентное пополнение доказанной выручкой конкретной области.
Gate относится к преобразованиям/исполнению шага 3 и включению шага 7;
миграция конфигов шага 1 и нейтральные модели шага 2 могут выполняться отдельно.

Дополнение того же первичного аудита: GetMaxLotsResponse в

явно измеряется в штуках. GetPositions не включает обеспечение фьючерсов;
это нельзя объявлять полной кассой всех типов инструментов.
Следовательно, документированная доступность существует: шаг 3 может проверить
использование инструментальных собственных лимитов GetMaxLots и свежих денег

Gate требует корректного преобразования выбранного источника и защит средств,

после FILL. Неатомарность уже принята как ограничение. Пока преобразование
и защитные проверки не подтверждены, новый торговый путь не включать.

Неполностью загруженные лимиты, активные заявки, любая числовая блокировка
или depository/exchange blocking flags останавливают торговую фазу с INFO
до следующей проверки. После FILL перечитать availability; если поступление
ещё не отражено, отложить неподкреплённую торговлю с INFO. Не выводить settled
money из raw total_order_amount. Первичная проверка шага 3 доказывает безопасные
units/availability выбранного пути GetMaxLotsRequest(account_id, uid), а не
мгновенный атомарный settlement. Источник — тот же orders.proto, строки 243..258.

Собственные модели содержат валюту, не SDK MoneyValue. Пока калибровка и
исполнение рассматривают рублёвый бюджет. Не складывать разноимённые валюты
как одинаковые деньги и не запрещать нерублёвые стратегии в общей схеме:
для их исполнения нужны явные оценки/конвертация в валюту бюджета, а не
неявный курс 1. Расширение валютной арифметики не входит в этот план.

Отправку вынести из [post_orders:141](../../autorepeater/repeater.py#L141)
в order_execution.py; SDK enum/Client остаются на границе. Оркестратор получает
нейтральные ошибки и результат исполнения. Неполная продажа останавливает
весь текущий проход; CLI ловит эту остановку и продолжает ждать события,
облако пробрасывает её, не возвращая Success. Транспортную ошибку отправки
не повторять автоматически: результат заявки может быть неизвестен.
Последующий запуск сначала проверяет активные заявки и блокировки.

Покупочный план пересчитать после подтверждённых продаж по свежим деньгам,
не меняя основную цель и её полный бюджет. Перед дальнейшей покупкой при
изменении денежных лимитов снова уменьшить доступную сумму; неизвестный
результат предыдущей покупки не позволяет продолжать отправку по старому остатку.
Нет гарантии цены BESTPRICE или атомарности всего прохода.

### Закрытые решения

ACCOUNT: name="2193248994", source_account_id="2193248994", reserve="0.01",
allocation_drift_limit="0.0092". Источник восстановлен из истории,
имя выбрано для сохранения src, допуск — принятый пользователем результат
модельной калибровки, не историческое значение.

У одноинструментного INDEX использовать одну строку [0, +бесконечность)
с limit="0": нормированные доли одной и той же бумаги всегда совпадают.
Это не запрет продаж при сокращении бюджета и не порог недовеса по количеству.
Дополнительного запаса к нулю не нужно. Все INDEX требуют таблицу.

**Согласовано: не продавать только ради резерва.** Старый капитал
C = V / (1 - reserve) — текущая оценка, не исторический бюджет. Поэтому при
росте цены и неизменных деньгах новый полный B может стать меньше C без
изменения пропорций и без перераспределения капитала родителем.
Без исключения обязательное REBALANCE обошло бы внутренний допуск даже одноинструментного
состава. Теперь резервное числовое сокращение ниже/на пороге само по себе
не разрешает продажи; внутренние критерии стратегий продолжают действовать.

Воспроизведено существующим чистым IndexStrategy/build_index_target на GOLD:
budget=100000, reserve=0.006, цена=10, lot=1 -> 9940 штук, деньги=600.
При цене 10.5: V=104370, B=104970, C=105000. Основная цель теперь 9937 штук,
то есть прежнее безусловное правило дало бы продажу 3 лотов на 31.5 рубля. Внутренняя
композиционная ошибка равна нулю, старый threshold=0.004 тоже не разрешил бы
эту продажу. Цены и счёт модельные, API-запросов не было.

Пользователь подтвердил исключение: в этом примере продаж нет. Для COMPOSITE
с одинаковым резервом 1%, бумагами на 99000 и деньгами 1000, при одновременном
росте всех бумаг на 5% получаем B=104950, sum(C)=105000 и прежние доли детей.
Отклонение долей равно нулю; дефицит 50 не разрешает продажи. Если при этом
ребёнок превысил собственный допуск, его внутренние продажи всё ещё разрешены.
Произвольный epsilon, новый порог и историческое хранилище не нужны.

Исторические обзоры сохраняются как история решений, не актуальный перечень
требований. Итог этой ревизии:
[проверка непротиворечивости и архитектуры](20261002-rebalance-policy-final-review.md).

## После реализации

Облачный таймер продолжает запускать проверки; частота проверки не равна
частоте торговли. Промышленный запуск требует контроля причин решений и
фактических комиссий. Снимки источника и назначения не атомарны, а цена
BESTPRICE-исполнения не гарантирована оценкой: не обещать точный остаток денег.
Перекрывающиеся облачные вызовы и незавершённые заявки должны быть отдельно
проверены перед использованием частого таймера; данный план не вводит скрытый
локальный кеш, историю портфеля или новое внешнее хранилище.
