# План реализации стратегии следования за индексом IMOEX

## Цель

Добавить стратегию автоследования за индексом Московской биржи через `src=IMOEX`.
Состав задаётся локальным JSON-файлом с тикерами и параметрами исходной индексной
базы. Цены и лотность берутся из T-Invest SDK. Стратегия рассчитывает
`TargetPortfolio` из префикса по капитализации: сначала одноразовый минимум
целевой суммы по полному индексу, затем округление по бюджету и отсечение
хвоста при первом отказе. Порог ошибки применяется только к ideal_lots < 1.

Актуальное уточнение от 29 сентября 2026 года: пользователь согласовал
`min_position_value="3000"`, не 3800, и проверку ошибки только ниже одного
идеального лота (последнее уточнение заменяет прежнюю границу 2). Порог ошибки остаётся 5%.
Независимый офлайн-расчёт при бюджете 152460 дал начальный префикс 15,
итоговый 15, стоимость 152361.420, остаток 98.580. Ожидание 10–12 не
подтвердилось; не подгонять число бумаг и не менять порог скрыто.
Исторические записи задач и старого sandbox-прогона ниже сохраняются
как описание соответствующих этапов, не текущего алгоритма.

Сохранить локальный запуск и разовую синхронизацию в Yandex Cloud Functions.
Расчёт цели и события разместить в отдельном модуле стратегии, подключаемом одной
регистрацией в `strategies.py`. В общем движке добавить защиту от пустой цели:
записать причину пропуска в лог и завершить текущую синхронизацию без заявок.
Остальную общую ребалансировку и расчёты стратегии повторения счёта не менять.

## Проверенные исходные условия (исторический снимок до реализации)

План сверен с рабочим деревом 29 сентября 2026 года, включая незакоммиченные
правки облачного значения `src` по умолчанию.

- `autorepeater/strategies.py`: реестр `NAMED_STRATEGIES` пуст. Фабрика принимает
  исходный `src`. `validate_src` только проверяет строку, не создаёт стратегию
  и не обращается к SDK.
- `autorepeater/account_strategy.py`: контракт состоит из
  `load_snapshot(client)`, `build_target(snapshot, budget)` и
  `events(client, dst_account_id)`. Снимок передаётся движком без разбора,
  построение цели не выполняет запросов.
- `autorepeater/portfolio.py`: количества в `TargetPortfolio.quantities`
  выражены в штуках. Для каждого UID обязательна конечная цена `Decimal`
  в `prices`. Общая проверка допускает нулевую цену; индексная стратегия
  дополнительно требует положительные цены, поскольку делит на них.
- `autorepeater/repeater.py`: бюджет равен стоимости назначения после
  однократного применения `reserve`. Сначала рассчитываются все продажи,
  затем все покупки. Отсутствующий в цели UID означает продажу имеющейся позиции.
  Сейчас пустая цель допускает расчёт продаж всех позиций с учётом лотности,
  торгового статуса и порога. По новому требованию это поведение нужно заменить
  пропуском синхронизации с записью в лог; остальные правила продаж сохраняются.
- Движок самостоятельно проверяет торговый статус и округляет разницу между
  целью и назначением в лоты. Целое число лотов в цели индекса совместимо с этим
  контрактом; дробные остатки назначения сохраняют существующее поведение.
- `autorepeater/orders.py`: оценка для `threshold` использует цену штуки,
  умноженную на число лотов, без дополнительного множителя лотности. Это
  существующее ограничение; его исправление не входит в эту задачу. Проверка
  бюджета новой стратегии должна использовать настоящую стоимость лота.
- `autorepeater/runner.py`: стратегия создаётся до клиента SDK. `run()`
  дополнительно показывает все счета и запускает цикл событий; `run_sync()`
  выполняет один пересчёт и не подписывается на события.
- `autorepeater/serverless.py`: отсутствующий `src` берётся из `SRC_ACCOUNT`,
  затем из `DEFAULT_SRC_ACCOUNT`. Явно пустой источник отклоняется.
  Обработчик не принимает параметр `debug` и создаёт `Runner` с
  `debug=False`. Локальные правки этого поведения сохраняются.
- `autorepeater/triggers.py`: существующее условие для назначения требует
  отсутствия ценных бумаг. Для индексного портфеля оно не подходит.
- `Makefile` копирует только `autorepeater/*.py`. Каталог с JSON нужно
  добавить в архив явно.
- `test/test_autorepeater.py`: есть проверки пустого реестра и отказа для
  `IMOEX` в селекторе, Runner, CLI и облаке. Общая фикстура SDK разрешает
  только пять сервисов; для цен потребуется добавить `market_data`.
- В установленном SDK 1.51.0 проверено наличие методов
  `instruments.find_instrument`, `instruments.get_instrument_by` и
  `market_data.get_last_prices(instrument_id=[...])`.
- `.coveragerc` включает весь рабочий Python-код, поэтому новая диагностическая
  утилита тоже должна покрываться тестами. Пороги общего покрытия и покрытия
  изменённых строк остаются 90%.

## Порядок разработки

- Выполнять задачи последовательно; после каждого изменения кода добавлять
  или обновлять детерминированные тесты и запускать относящиеся к нему проверки.
- Сохранять поведение `src=<номер счёта>`, кроме общей защиты от пустой цели,
  контракты запуска и существующие локальные правки. Новые рабочие зависимости
  не требуются.
- Все денежные и количественные вычисления выполнять через `Decimal`.
  В JSON десятичные значения хранить строками.
- Использовать настоящие SDK DTO и
  `create_autospec(inspect.unwrap(Service), instance=True, spec_set=True)`.
- Отмечать выполненные пункты `[x]`; найденные задачи и препятствия записывать
  словами. Обновлять план при изменении требований.
- Реализацию и калибровку отмечать отдельно. До получения реальных данных
  порог 5% является предварительным.

## Методика расчёта весов

### Что означает исходная таблица

В предоставленном изображении есть цена, эффективное количество, полная
капитализация, free-float (доля бумаг в свободном обращении), коэффициент
ограничения веса, капитализация для индекса и вес.

Эффективное количество уже включает оба коэффициента. Например, для AFKS:

```text
1 958 950 000 × 7,079 = 13 867 407 050 рублей
```

Результат совпадает с колонкой капитализации, учитываемой в индексе.
Повторно умножать это количество на free-float и ограничивающий коэффициент
нельзя. Нули в этой колонке при ненулевой индексной капитализации не означают
исключение бумаги.

Для всей таблицы использовать один способ расчёта: исходную индексную
капитализацию и отношение текущей цены к исходной. Это устраняет смешение
абсолютных и относительных количеств и использует более точные данные, чем
округлённая колонка процентов.

```text
эффективное количество = исходная индексная капитализация / исходная цена
текущая индексная капитализация = исходная индексная капитализация
                                 × текущая цена / исходная цена
вес = текущая индексная капитализация / сумма текущих индексных капитализаций
```

Рабочая формула в терминах полей:
`reference_index_capitalization * current_price / reference_price`, затем
нормализация по всем бумагам. Порядок операций фиксируется тестами.
`effective_quantity`, `free_float`, `weight_limit` и `reference_weight`
сохраняются для проверки исходных данных и не применяются повторно.

Такой расчёт описывает изменение весов при фиксированной индексной базе.
Он не обновляет автоматически состав, коэффициенты и корпоративные действия.
После изменения базы, дробления или других изменений масштаба цены конфиг
нужно обновить согласованно. Это стратегия воспроизведения весов, а не расчёт
публикуемого значения IMOEX с делителем индекса. Актуальность состава изображения
и соответствие действующей официальной базе ещё предстоит проверить.

### Округление и исключение хвоста

`budget` уже учитывает резерв движка. Для неположительного или неконечного
бюджета выдавать понятную ошибку до расчёта заявок.

Ранжировать бумаги по убыванию текущей индексной капитализации, при равенстве
по тикеру. До любой перенормализации один раз оставить начальный префикс
с `budget * weight_in_FULL_INDEX >= min_position_value`, остановившись
на первой бумаге ниже минимума. Встроенное значение 3000 в валюте бюджета;
отсутствие поля в старом явном конфиге означает 0 и отключает этот фильтр.
Минимум не гарантирует фактическую стоимость после округления. Валютных
запретов и конвертации не добавлять.

Для текущего набора кандидатов нормализовать веса и вычислить:

```text
целевая стоимость = бюджет × нормализованный вес
стоимость лота = текущая цена × лотность
идеальное число лотов = целевая стоимость / стоимость лота
желаемое число лотов = округление идеального числа до ближайшего целого
фактический вес = выбранное число лотов × стоимость лота / бюджет
относительная ошибка = |фактический вес − нормализованный вес| / нормализованный вес
```

Для ближайшего целого использовать округление половины к чётному, как
`round(Decimal)` в существующем движке. Независимое округление всех бумаг вверх
может превысить бюджет даже после резерва. Поэтому определить единый порядок:

1. Начать с префикса после фильтра минимума. На каждом проходе нормализовать веса.
2. Каждой бумаге выделить ближайшее целое число лотов, половины к чётному.
3. При превышении бюджета отменять округления вверх по наименьшему увеличению
   относительной ошибки, при равенстве по тикеру, пока стоимость не уложится.
4. Проверить префикс в порядке рангов. Ноль фактических лотов всегда означает
   отказ; ошибка выше `max_lot_weight_error` означает отказ только при
   `ideal_lots < 1`. При `ideal_lots >= 1`, включая ровно один лот, порог не применяется.
5. При первом отказе отсечь эту бумагу и весь хвост; нормализовать оставшийся
   префикс и повторить. Исключённые бумаги не возвращать, предварительный
   фильтр не повторять. Следующий независимый вызов снова начинает с полного
   состава. Если отказов нет, вернуть результат.

Каждый неуспешный проход уменьшает число кандидатов, поэтому достаточно не более
числа исходных бумаг проходов. Если исключены все, вернуть пустой
`TargetPortfolio`: пригодную цель построить не удалось. Такой результат
не является командой продать имеющиеся бумаги.

Общий движок после `validate_target` и до расчёта любых заявок проверяет
`not target.quantities`. Для пустой цели записать через функцию `reporting`
сообщение о пропуске синхронизации с идентификатором назначения и причиной,
затем выполнить ранний возврат. Проверка действует для всех стратегий, в том
числе в `debug`, независимо от порога и торгового статуса. При непустом счёте
имеющиеся позиции сохраняются; при наличии только денег либо пустом счёте
заявки также не нужны. Не выбрасывать исключение: локальный цикл продолжает
слушать события, облачный вызов сохраняет текущий формат ответа.

Пустая цель здесь означает пустой словарь количеств, а не пустую разницу с
назначением. Непустая цель, уже совпадающая с портфелем, остаётся обычным случаем
без заявок и без сообщения о пустой цели. Явные нулевые количества в непустой
цели сохраняют существующий смысл. Ошибки источника по-прежнему пробрасываются
исключениями, а не преобразуются в пустую цель.

Для ideal_lots < 1 граница включения: вычисленная ошибка **не более** настраиваемого порога
`max_lot_weight_error`. Значение 5% предварительное и может измениться после
калибровки; не зашивать его в алгоритм. При точном равенстве вычисленных
Decimal-значений бумага допускается. Из-за конечной точности Decimal
математически граничное значение может оказаться чуть выше или ниже порога.
По решению пользователя специальную коррекцию этой погрешности не добавлять;
описать ограничение в README для любого значения порога. Решение на границе
может повлиять и на последующие исключения при перенормализации.
После исключений ошибка проверяется относительно перенормализованного веса
оставшегося набора. Отклонение от исходного полного индекса показывается отдельно.
Неиспользованный остаток остаётся деньгами; точное расходование всего бюджета
не требуется. Оценочная стоимость цели не превышает бюджет, но фактическую
стоимость исполнения BESTPRICE по изменившимся ценам это не гарантирует.

Начальный порог `max_lot_weight_error = 0.05`. Отбор гарантирует непрерывный
префикс по капитализации, но не заданную длину. Число бумаг не обязано монотонно
расти на каждом увеличении бюджета из-за округления. При достаточном бюджете
точность представления состава растёт; это проверяется отдельными сценариями.
При полной стоимости 154000, резерве 1%, минимуме 3000 и пороге 5%
эмпирически получены 15 бумаг на сохранённом снимке. Расхождение с ожиданием
10–12 зафиксировано; дальнейшие изменения требуют отдельного решения.

### Получение данных и ошибки

Конструктор принимает `src`, выбирает путь и читает конфиг без SDK-запросов.
Путь по умолчанию вычисляется относительно модуля:
`autorepeater/configs/imoex.json`. `IMOEX_CONFIG_PATH` позволяет задать другой
файл. Конфиг фиксируется на время жизни объекта стратегии; для обновления
долгоживущего процесса нужен перезапуск.

В `load_snapshot` на каждом пересчёте получать для всех тикеров точное соответствие
акции, её UID, лотность, валюту и текущую доступную цену. Использовать
`find_instrument`, затем `get_instrument_by` по UID и пакетный
`get_last_prices(instrument_id=[...])`. Совпадение тикера должно быть точным.
По согласованному 29 сентября 2026 года уточнению выбирать только
`instrument_type='share'` и `class_code='TQBR'` (основной режим торгов акциями
Московской биржи). После фильтрации по тикеру, типу и TQBR требуется ровно одно
совпадение; ноль или несколько совпадений являются ошибкой с указанием площадки.
Не использовать другие площадки как fallback и не фильтровать по
`api_trade_available_flag`. Метаданные по UID должны подтвердить тот же UID,
тикер, тип акции и TQBR; ошибки метаданных и лотности также указывают площадку.
Разные тикеры, разрешившиеся в один UID, отклонять.

Текущий сценарий предполагает рублёвые инструменты, цены и портфель назначения.
Специальные проверки, отклоняющие другие валюты, не добавлять ни в стратегию,
ни в общий движок. Валюту сохранять в снимке и диагностических данных.
Конвертация валют пока не реализована; это описать в README как текущую
предпосылку расчёта. Возможную поддержку валют оставить отдельной будущей задачей.

Отсутствие инструмента или цены, неположительная цена или лотность, неконечные
значения и неполный ответ котировок прерывают пересчёт. Не превращать их в
частичный или пустой портфель. Цены последних сделок могут относиться к прошлой
сессии; время котировок сохранять в снимке и показывать в отчёте калибровки.

Временное отсутствие торгов само по себе не исключает бумагу из состава и
не перераспределяет её вес: при наличии цены цель строится для неё тоже.
Исполнимость заявок проверяет существующий движок по актуальному торговому
статусу. Это означает, что рассчитанная цель может быть недостижима до
возобновления торгов.

В `build_target` нет SDK-запросов: только снимок и бюджет.
Возвращать `Decimal` количества штук, кратные лотности, и положительную цену
каждого включённого UID. Ошибки SDK передавать наружу как `RequestError`;
общий цикл уже обрабатывает их и переподписывается. Ошибки конфигурации и
некорректных данных не маскировать под сетевые ошибки.

### События и режимы запуска

`events(client, dst_account_id)` открывает одну подписку:

```python
client.operations_stream.positions_stream(accounts=[dst_account_id])
```

Событие вызывает пересчёт, если содержит позицию именно назначения, хотя бы
одну денежную или бумажную позицию, все бумаги разблокированы и у всех денежных
позиций заблокированная сумма равна нулю. Пустые служебные сообщения, чужой счёт
и блокировки дают `False`. Отсутствие бумаг не обязательно.
Реализовать это правило в модуле индексной стратегии; условие стратегии счёта
в `triggers.py` не менять. Пропущенные события выводить через существующий
`reporting.print_skipped_event`.

Общий движок выполняет начальный пересчёт, а затем реагирует на события.
Изменение котировок само по себе не создаёт событие назначения; отдельного
таймера для локального процесса в этой задаче нет.
В облаке периодичность обеспечивает внешний таймер, вызывающий `handler`;
`run_sync()` выполняет один пересчёт без подписки.

## Формат и исходные данные

Создать `autorepeater/configs/imoex.json`. Все десятичные значения хранить
строками, `instruments` — непустым массивом. Пример одной записи:


## Проверки и калибровка

Модульные тесты покрывают чтение конфига, формулу капитализации, бюджетное
округление, повторную фильтрацию, цель, ошибки данных, регистрацию и события.
Существующие проверки стратегии счёта сохраняются. Для SDK добавить
`MarketDataService` в общую фикстуру, не создавать ручные подмены сервисов.

Реальный запуск калибровки — отдельная явно вызываемая утилита. Она получает
`READ_ONLY_INVEST_TOKEN` из окружения, создаёт снимок и цель, но не создаёт
`Runner` или `AutoRepeater`, не вызывает отправку заявок. Само наличие токена
не запускает сетевой тест при обычном `pytest`.

154000 рублей трактовать как полную стоимость портфеля. При стандартном резерве
1% основной бюджет стратегии равен 152460 рублям. Дополнительно показать расчёт
для бюджета ровно 154000 рублей без резерва, чтобы разделить влияние резерва
и порога. Двойное применение резерва запрещено.

Отчёт содержит момент получения данных, время котировок, цены, лотность,
исходный и перенормализованный веса, выбранные лоты, ошибки, причину исключения,
суммарную стоимость и остаток. Сравнить несколько порогов, включая 5%, и бюджеты
меньше и больше основного. Показать не только количество бумаг, но и их места
в полном составе по весу. Ожидание первых 10–12 бумаг не должно подменяться
попаданием любых 10–12.

После предоставления токена выполнить проверку, сохранить обезличенный снимок
рыночных данных и воспроизводимые ожидания в тестовых данных, затем записать
выбранный порог и наблюдения. Не сохранять токен и данные счетов.
Если токена ещё нет, подготовить утилиту и тесты, явно оставить реальную
калибровку незавершённой. Текущее значение 5% не называть проверенным.
