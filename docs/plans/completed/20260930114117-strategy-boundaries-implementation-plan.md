Дать разработчикам и агентам возможность добавлять алгоритм отдельным модулем
и регистрировать его в одном месте, не меняя исполнительный код. Изолировать
стратегии друг от друга и от интерфейса SDK. Изменение SDK при сохранении
смысла предоставляемых данных должно требовать изменения адаптера, а не стратегий.

Согласованные решения:

- Сохраняем торговую арифметику, данные конфигов, локальный цикл и разовый
  облачный запуск. Новых алгоритмов и торговых возможностей нет.
- Алгоритм выбирается обязательным параметром `algoritm`, имя задаётся при
  регистрации. Начальные регистрации: `ACCOUNT` и `INDEX`. Автоопределения нет.
  `src` трактуется только выбранным алгоритмом: для ACCOUNT это номер счёта,
  для INDEX это значение поля `name` внутри JSON независимо от имени файла.
- Полная изоляция стратегий от SDK: собственные модели данных, общий интерфейс
  чтения и событий, адаптер SDK. SDK DTO и перечисления в стратегии не поступают.
- Ошибка чужого конфига вызывает предупреждение, но не блокирует выбранную
  стратегию. Ошибка выбранного конфига и неоднозначность выбранного имени
  останавливают запуск до создания SDK-клиента.
- Отрицательные конечные количества сохраняем допустимыми. Проверяем Decimal
  и конечность; это не добавление новой поддержки коротких позиций.
- Работа небольшими шагами через TDD: сначала падающий тест, затем код,
  затем полный успешный прогон перед переходом к следующей задаче.
- Python 3.12, существующий плоский пакет autorepeater, без новых зависимостей.

Изменения поведения: явный выбор алгоритма вместо маршрутизации по src,
отказ на некорректном контракте и изоляция ошибок конфигов. Старые команды
запуска требуют добавления algoritm. Резервы, составы и параметры существующих
JSON не менять; торговые решения для прежних входных данных сохранить.

## Исторический контекст исходной ревизии

Ниже зафиксировано состояние до рефакторинга, а не действующий API.
Текущие контракты описаны в README.md и AGENTS.md.

- `strategies.py`: числовой src выбирает AccountStrategy; все остальные сначала
  требуют успешной загрузки всех индексных конфигов, включая независимые фабрики.
- `index_config.py`: структурная проверка всего набора смешана с обнаружением имён.
  Файл определяется полем name, не именем файла. Есть INDEX_CONFIG_DIR и
  совместимый одиночный IMOEX_CONFIG_PATH; одновременно они запрещены.
- `AccountStrategy` и `IndexStrategy` не импортируют друг друга или движок.
  Методы load_snapshot и events получают полный SDK-клиент.
- `AccountStrategy` читает SDK-позиции; `IndexStrategy` напрямую использует
  InstrumentIdType и проверяет метаданные SDK. Оба используют reporting.
- `AutoRepeater` получает стратегию извне, не разбирает её снимок, но читает
  необязательный default_reserve через getattr без проверки.
- `portfolio.py`: TargetPortfolio уже общий, validate_target проверяет только
  конечные Decimal-цены, не количества. Нулевая цена допустима.
- `reporting.py` дополнительно запрашивает названия инструментов для вывода.
  Этот путь нельзя забыть при отделении SDK: он вызывается из AccountStrategy.
- `triggers.py` читает поля блокировок SDK, включая units/nano первой денежной
  позиции назначения. Индексная стратегия проверяет все блокировки назначения.
- `Runner` создаёт стратегию до Client; оба режима используют _create_repeater.
  main.py и serverless.py предварительно вызывают validate_src.
- `mainflow` восстанавливается после RequestError при чтении и пересчёте;
  нормальное завершение итератора также приводит к новой подписке.
- Калибровка напрямую создаёт IndexStrategy и передаёт ему SDK-клиент.
  Она требует обновления одновременно с изменением интерфейса стратегии.
- Makefile копирует все autorepeater/*.py и configs/*.json в облачный архив.
- Тесты используют autospec SDK-сервисов и настоящие детерминированные SDK DTO.
  Зафиксированы исторический снимок IMOEX и независимые ожидания расчёта.
- CI: Python 3.12, pylint, flake8, pytest; общее и diff-покрытие не ниже 90%.

## Границы работ

Не менять SDK, зависимости, workflow-триггеры, структуру конфигов, существующие
значения name, торговые статусы, BESTPRICE, threshold и алгоритм распределения.
Имена алгоритмов отделяются от имён источников; старый выбор по одному src
не сохраняется. Новое написание параметра именно `algoritm`, не `algorithm`.
Не вводить БД, динамическую загрузку плагинов, контейнер зависимостей,
обязательную иерархию наследования или собственный планировщик.

Изолируем от SDK именно стратегии, их модели и используемые ими функции.
Исполнитель заявок и создание Client могут продолжить использовать SDK:
переписывание торгового адаптера не требуется для поставленной цели.
При замене SDK может понадобиться изменить его использование исполнителем,
но не стратегии. Не обещать совместимость при изменении самой семантики API.

## Решение

### Направление зависимостей

```text
main / serverless -> prepare_strategy(algoritm, src) -> PreparedStrategy
                                                          |
                                                       Runner
                                                          +-> create_strategy(prepared)
                                                          +-> Client + TInvestStrategyData
                                                          +-> AutoRepeater(client, strategy, data)

стратегия -> StrategyData (Protocol) + собственные модели + общие функции
адаптер  -> StrategyData + собственные модели + SDK
движок   -> Strategy + TargetPortfolio + SDK исполнения
```

Стратегия не импортирует другую стратегию, реестр, адаптер, движок или Runner.
Общие модели и контракт не импортируют SDK или конкретные реализации.
Только сборка приложения выбирает конкретный адаптер. Движок не создаёт его
и не проверяет isinstance конкретных стратегий.

### Единый API

Регистрация и исполнение имеют разные контракты. В `strategy_contract.py`
описать небольшой `AlgorithmDefinition` с двумя вызываемыми полями:
`prepare_source(src)` и `create(prepared_source)`. Подготовка проверяет источник
и возвращает данные для фабрики, не создавая стратегию или SDK-клиент.
Тип подготовленных данных непрозрачен реестру и исполнителю.

В `strategies.py` хранить реестр `ALGORITHMS` и функцию
`register_algorithm(name, definition)`. Имя должно быть непустой строкой без
пробельных символов; повторная регистрация того же имени запрещена.
Сравнение точное, с учётом регистра, без автоматической нормализации.
Зарегистрировать ACCOUNT и INDEX импортом их функций подготовки и фабрик.
Никаких проверок номера счёта или чтения JSON в общем реестре нет.
Пространства имён алгоритмов и индексных конфигов независимы: совпадение имён
между ними допустимо. Импорт реестра не выполняет файловый или сетевой ввод-вывод.

Заменить старый validate_src на `prepare_strategy(algoritm, src)`: он проверяет
имя алгоритма и делегирует подготовку источника выбранной регистрации ровно
один раз, не вызывая фабрику. Результат — небольшой `PreparedStrategy` в
`strategy_contract.py`, содержащий выбранную фабрику и подготовленные данные
источника. Не хранить в нём SDK-клиент или отложенную повторную загрузку конфига.
`create_strategy(prepared)` вызывает сохранённую фабрику с этими данными и
проверяет контракт результата до Client. Функция не ищет регистрацию повторно,
не читает файлы и не повторяет предупреждения. Старые validate_src и
create_strategy(src) удалить без совместимых обёрток.

Граница однократности — один запуск приложения: подготовка в точке входа,
затем передача того же результата в Runner. Прямой пользователь Runner сначала
вызывает prepare_strategy. При новом запуске источник подготавливается заново,
глобального кеша нет. Изменение файла между подготовкой и созданием стратегии
не влияет на уже подготовленные данные; следующий запуск увидит изменение.
ACCOUNT проверяет непустую строку из ASCII-цифр в `account_strategy.py`, сохраняя
ведущие нули. INDEX разрешает имя через `index_config.py` из `index_strategy.py`.
Новый алгоритм определяет собственный смысл src, не меняя общий реестр.

Создать `autorepeater/strategy_contract.py` со стандартным typing.Protocol:

```python
class Strategy(Protocol):
    @property
    def default_reserve(self) -> Decimal: ...
    def load_snapshot(self, data: StrategyData) -> object: ...
    def build_target(self, snapshot: object, budget: Decimal) -> TargetPortfolio: ...
    def events(self, data: StrategyData, dst_account_id: str) -> Iterable[bool]: ...
```

Это структурный контракт, наследование от Protocol не требуется. Snapshot
непрозрачен исполнителю; каждая стратегия сама определяет его структуру.
Общий обязательный тип снимка или универсальную схему стратегий не вводить.
Идентичность конструкторов не требуется: фабрики скрывают различия аргументов.

Обе стратегии предоставляют default_reserve. AccountStrategy возвращает
Decimal(DST_MONEY_RESERVED), IndexStrategy — config.reserve. Удалить fallback
через getattr из движка после одновременного обновления реализаций и тестов.

Protocol не заменяет проверку значений. Добавить validate_strategy для наличия
вызываемых методов и корректного default_reserve; выполнять после фабрики до
Client и при прямом создании AutoRepeater. Сигнатуры проверять контрактными
тестами, не строить сложный runtime-анализ аннотаций.

Резерв стратегии: конечный Decimal в [0, 1). Явное переопределение CLI сохраняет
прежний приоритет, преобразование Decimal(str(value)) и допустимость 1, которая
уже есть в set_reserve; не превращать этот рефакторинг в изменение торгового
режима при нулевом бюджете. Bool, NaN, Infinity и отрицательные значения
отклонять явно. JSON и калибровка сохраняют существующий диапазон [0, 1).
Разные диапазоны исходного резерва и старого CLI описать и проверить отдельно.

### Параметры запуска и совместимость

- `main.py`: обязательный `--algoritm` и `-s/--src`; допустимые имена алгоритмов
  проверяет реестр, а не жёстко заданный список argparse. Проверка пары до токена
  и Client. Примеры: `--algoritm ACCOUNT -s 123456` и `--algoritm INDEX -s IMOEX`.
- CLI и облачный обработчик вызывают prepare_strategy до чтения токена,
  затем передают результат в `Runner(token, prepared_strategy, dst, params=...)`.
  Runner вызывает create_strategy с подготовленным результатом в конструкторе.
  Не передавать одновременно исходную пару и её подготовленную копию.
  Обязательность algoritm/src сохраняется на входной границе подготовки;
  Runner и движку не нужны правила разбора источника.
- Облако: query-параметр `algoritm`, при его отсутствии переменная `ALGORITM`.
  Значения по умолчанию нет. Переданный пустой параметр не заменять окружением;
  отсутствующее, пустое или неизвестное имя вызывает ошибку до SDK.
- Облачный `src`: query-параметр либо `SRC_ACCOUNT` при отсутствии параметра.
  Историческое имя переменной сохранить и для имён конфигов. Убрать встроенный
  DEFAULT_SRC_ACCOUNT: источник должен быть задан явно в запросе или окружении,
  иначе отказ. Это исключает подстановку номера счёта в INDEX. Пустое значение
  также не заменять запасным. Правила dst, token и t_token оставить прежними.
- Специализированный `check_imoex_strategy.py` остаётся калибратором INDEX,
  не универсальной точкой запуска: алгоритм задан назначением скрипта, отдельный
  флаг algoritm ему не нужен. Выбор src использует тот же индексный загрузчик.

Наличие цифрового src не выбирает ACCOUNT, а имя IMOEX не выбирает INDEX.
Например, ACCOUNT с src=IMOEX даёт ошибку счётного источника, не переключает
алгоритм. Для INDEX src=123456 ищет JSON с name="123456", не счёт.
Снять только прежний запрет цифрового name в индексном валидаторе: он был
нужен для старой маршрутизации. Остальные проверки name оставить прежними.

### Модели и интерфейс данных

Создать `autorepeater/strategy_data.py`. В нём только стандартная библиотека,
минимальные dataclass-модели, StrategyData Protocol и DataAccessError.

| Модель | Необходимые данные |
|---|---|
| PortfolioSnapshot | Упорядоченный список позиций |
| PortfolioEntry | UID, собственный тип инструмента, валюта, Decimal-цена штуки и количество; диагностический текст для неизвестных типов |
| InstrumentMatch | UID, тикер, название, собственный тип, режим торгов; результат поиска без валюты и лотности |
| InstrumentInfo | UID, тикер, название, собственный тип, режим торгов, размер лота, валюта |
| PriceQuote | UID, Decimal-цена штуки, время котировки |
| PositionEvent | Признак наличия позиции, ID счёта, упорядоченные блокировки бумаг и денег, диагностический текст |

InstrumentMatch и InstrumentInfo — отдельные небольшие модели без обязательного
наследования. Поиск возвращает только нужные для выбора и вывода поля; полные
метаданные загружаются отдельным get_instrument после выбора единственного UID.
Валюту оставить только в InstrumentInfo: сейчас IndexStrategy переносит её в
IndexQuote.currency, а калибровка сериализует снимок через asdict. Удаление валюты
из полного результата изменило бы отчёт. Не подставлять выдуманную валюту при
поиске и не делать дополнительных запросов ради заполнения поисковой модели.

Собственный тип инструмента: стабильные значения для акции, фонда, валюты,
прочих инструментов. Адаптер преобразует SDK-типы в них. Не передавать SDK-enum,
сырые DTO, callbacks SDK, client или raw_response внутри моделей.
Диагностический текст — только строка, не скрытый транспорт исходного объекта.
Порядок позиций и денежных блокировок сохранять: для счётной стратегии важна
первая денежная позиция. Служебное событие представлять явно, не терять его.

Минимальные методы StrategyData:

- get_portfolio(account_id) -> PortfolioSnapshot;
- find_instruments(query) -> список InstrumentMatch;
- get_instrument(uid) -> InstrumentInfo;
- get_last_prices(uids) -> список PriceQuote;
- position_events(account_ids) -> Iterable[PositionEvent].

Методов выставления заявок, доступа к клиенту и произвольного проксирования
атрибутов нет. Адаптер — архитектурная граница, не песочница для недоверенного
Python-кода. Новые источники можно реализовывать тем же интерфейсом;
новые принципиально необходимые данные потребуют осознанного расширения порта.

`TInvestStrategyData` в `autorepeater/tinvest_strategy_data.py` реализует порт.
В нём все обращения к сервисам и SDK-перечислениям для чтения стратегиями.
DTO создаются явно, конвертация денег строго units + nano / 1e9.
Получение портфеля не должно дополнительно получать котировки или перечень счетов.
Не добавлять кеш, повторы запросов или торговые фильтры внутри адаптера.

Сохранять точность и порядок операций: стоимость каждой позиции счётной
стратегии quantize(0.000000001) до суммирования; ratio = budget / total_src,
затем ratio * quantity. Перенос не должен использовать SDK total_amount
вместо прежней суммы позиций или менять формулу на предварительные веса.

Разрешение индексных тикеров, правила TQBR/TQTF и неоднозначности остаются
бизнес-логикой IndexStrategy над InstrumentMatch и InstrumentInfo.
SDK-способ получения инструмента
по UID скрывается в адаптере. Повторная проверка UID/тикера/типа/режима и лотности
сохраняется, как и свежий снимок перед каждым пересчётом.

### Ошибки, события и вывод

Адаптер преобразует RequestError в DataAccessError с прежним сообщением;
исходное исключение можно сохранить цепочкой для диагностики, но оно не является
частью публичного контракта. Не маскировать ошибки программирования.
Для генератора преобразование должно охватывать и открытие подписки, и ошибки
во время следующего чтения, а не только создание итератора.

Ошибки данных отделить от транспортных ошибок:

- Отсутствующий результат get_instrument и отсутствующая цена котировки —
  ValueError адаптера с UID и названием поля, не None вместо заявленного DTO.
- Ожидаемые ошибки преобразования units/nano (TypeError, ValueError,
  InvalidOperation) и неконечный результат — ValueError с контекстом поля/UID.
  Проверять отсутствующие значения явно, не перехватывать любой AttributeError
  или Exception. Не заменять ошибочные значения нулями или прошлым снимком.
- Адаптер не применяет индексное требование положительной цены к остальным
  алгоритмам. Проверки знака цены, лотности, совпадения UID/тикера/режима,
  неоднозначных и неполных наборов остаются в IndexStrategy как ValueError.
  Пустой поиск и неполный список котировок сами по себе допустимые ответы порта;
  стратегия определяет их пригодность. Сохранять порядок и дубликаты ответа.
- ValueError данных не превращать в DataAccessError и не перехватывать для
  переподписки: в mainflow и run_sync он завершает вызов. При ошибке снимка
  заявки текущей синхронизации не отправляются; заявки предыдущих успешных
  синхронизаций не отменяются.
  Для перенесённых в адаптер проверок тесты явно обновляют место возникновения
  и контекст диагностики (поле/UID вместо доступного только стратегии тикера),
  сохраняя тип ошибки, запрет торговли и отсутствие повторов.

Движок одинаково восстанавливается после DataAccessError чтения стратегией
и RequestError своего SDK-исполнения. Сохраняются первоначальный пересчёт,
переподписка после окончания итератора и ошибка пересчёта внутри события.
В run_sync ошибки пробрасываются. Стратегии используют DataAccessError и
ValueError данных, не импортируют RequestError. ValueError данных,
конфигурации/цели не становится retry.

events возвращает ленивый Iterable[bool]: рабочая подписка может оставаться
открытой неограниченно. Не исчерпывать и не материализовать поток для проверки
контракта. Конечность требуется только от тестовых последовательностей;
проверять также переподписку после штатного завершения и транспортной ошибки.

В reporting добавить отдельный путь для собственных моделей, используемый
стратегиями. Нынешний SDK-путь вывода назначения и просмотра счетов можно оставить.
Новый путь принимает StrategyData и PortfolioEntry, при необходимости ищет
название через find_instruments, не читает портфель повторно. Сохранить порядок
заголовка, позиций и итога, денежное форматирование и GetInstrumentException.
Стратегии и новые общие функции не читают units/nano или поля DTO SDK.
Для пропущенных событий выводить diagnostic_text из собственной модели.

`triggers.py` перевести на PositionEvent с сохранением условий счёта;
индексные условия по всем блокировкам назначения остаются в IndexStrategy.
Общий код выносить только при реальном совпадении, не объединять разные правила.

### Проверка цели

TargetPortfolio оставить в `portfolio.py`: модуль уже не импортирует SDK.
Усилить validate_target до начала расчёта любых заявок, в том числе debug:

- обе карты — словари, ключи quantities — непустые строковые UID;
- каждое количество — конечный Decimal, включая отрицательные и ноль;
- каждый UID количества имеет конечную Decimal-цену;
- нулевая и отрицательная конечная цена не запрещаются новым правилом:
  нынешний контракт не проверяет знак; индексный источник по-прежнему требует > 0;
- лишние ключи prices по-прежнему игнорируются;
- пустая корректная цель сохраняет логирование и ранний возврат без ликвидации.

Не округлять, не исправлять и не преобразовывать ошибочные количества молча.
Ошибки указывают поле/UID. Не требовать лотности от общей цели: стратегия счёта
сохраняет дробные количества, движок округляет разницу, как прежде.

### Изоляция конфигов внутри INDEX

Сохранить name внутри JSON единственным источником имени. Не вводить новый
manifest, привязку имени к пути или обязательное поле типа алгоритма.

Разделить обнаружение и валидацию в index_config.py:

1. Найти прежний набор путей, прочитать JSON структурным парсером один раз
   за операцию выбора; собрать доступные name, данные и ошибки по файлам.
2. Проверять индексные документы по одному чистым валидатором, сохраняя
   результат или ошибку каждого независимо, без общего отказа. Это позволяет
   предупредить и о неверных полях чужого конфига, не только о синтаксисе JSON.
   Файл с читаемым name, но ошибочным содержимым остаётся кандидатом этого
   имени, а не исчезает. Фабрики алгоритмов при обнаружении не вызываются.
3. Составить каталог кандидатов только из индексных конфигов, не смешивать
   его с ALGORITHMS. Для выбранного name требуется ровно один кандидат.
   Дубликат с ошибочным телом тоже считается дубликатом.
4. Если у выбранного конфига сохранена ошибка, поднять её до создания стратегии.
   Иначе передать его проверенные данные фабрике и проверить общий контракт.
   Ошибки других файлов вывести предупреждениями, не запрещая запуск.
5. При отсутствии выбранного имени и наличии непрочитанных файлов вернуть
   ошибку выбора с указанием проблемных путей, не выбирать единственный
   исправный конфиг автоматически и не трактовать имя как номер счёта.

Для синтаксически повреждённого JSON невозможно достоверно восстановить name.
Не использовать регулярные выражения или имя файла вместо парсера. Такой файл
считается неопознанным повреждённым кандидатом и получает предупреждение.
Рабочая однозначная стратегия продолжает запуск, как согласовано. Гарантия
обнаружения дубликатов распространяется только на читаемые имена; скрытый внутри
невалидного JSON дубликат выявить невозможно без изменения формата хранения.
Если повреждённый файл был единственным источником запрошенного имени, запуск
завершается ошибкой выбора, до SDK и без подмены другой стратегией.

ACCOUNT и остальные независимые алгоритмы вообще не читают индексные конфиги
или настройки их путей, даже для проверки совпадений имён. Проблемы пути/каталога
в INDEX не разрешают fallback на встроенную базу или другой алгоритм.
Решение читать конфиги зависит от algoritm, а не от вида src. Дубликат другого
имени не блокирует выбранное уникальное имя, но отражается предупреждением.
Ошибки не содержат полного JSON и секретов, только путь, имя при наличии и причину.

Сохранить отдельную строгую load_index_configs для явной полной проверки набора
и её тестов; не использовать её для обычного выбора src. Переиспользовать общий
парсер/валидатор, не копировать схему. Не создавать стратегии во время
prepare_strategy(algoritm, src); созданию передавать уже подготовленный конфиг.
Импорт реестра не читает файлы и не создаёт Client.

Калибровка с явным --src использует тот же изолированный выбор конфигурации.
Без --src автоопределение разрешено только при одном кандидате и отсутствии
ошибок/дубликатов: иначе явно потребовать имя, не угадывать выбор среди повреждений.
Фабрики других алгоритмов в индексной калибровке не создавать.
При выборе единственного кандидата использовать уже прочитанный документ,
не загружать его повторно по обнаруженному имени.

Обязательные результаты:

- стратегии и используемые ими модели/функции работают без установки SDK;
- замена реализации порта при тех же собственных моделях не меняет стратегии;
- исполнитель не знает конкретные алгоритмы, их конфиги и структуру снимков;
- обе реальные стратегии имеют одинаковый полный контракт;
- новый алгоритм подключается модулем и регистрацией без правок исполнения;
- algoritm обязателен в CLI и облаке; никакой формы автоопределения по src нет;
- ACCOUNT сам проверяет номер счёта, INDEX выбирает файл по полю name в JSON;
- пространства имён алгоритмов и конфигов независимы; прочие алгоритмы
  не читают индексные конфиги и не зависят от их валидности;
- источник подготавливается один раз за запуск; создание стратегии использует
  тот же результат без повторного чтения файлов и предупреждений;
- поисковые метаданные не требуют валюты; полный результат сохраняет валюту
  в индексном снимке и отчёте без дополнительных запросов;
- ошибки данных имеют тип ValueError и не вызывают повторы; транспортные
  ошибки порта обрабатываются как DataAccessError;
- рабочий поток событий ленивый и не обязан завершаться; конечность
  последовательностей — только требование к тестовым сценариям;
- ошибочные количества и резервы отвергаются на общей границе;
- отрицательные конечные количества и все принятые торговые решения сохранены;
- чужой повреждённый конфиг не блокирует однозначную рабочую стратегию;
- выбранный повреждённый/неоднозначный источник не запускает SDK или торговлю;
- локальный цикл, переподписки, serverless, калибровка и архив проходят проверки;
- общее и diff-покрытие не ниже 90%, новые рабочие модули не исключены из покрытия.

В тестах адаптера использовать существующий create_autospec(inspect.unwrap(Service),
instance=True, spec_set=True) и явные SDK DTO. В тестах стратегий использовать
autospec собственного порта и собственные DTO, без ручных Fake SDK-сервисов.
Порядок и отсутствие лишних вызовов проверять точными call_args_list.
UI и браузерных проверок у проекта нет; внешние интеграционные вызовы не нужны.

### 5. Алгоритм, источник и изоляция конфигов

**5.1. Тесты явного algoritm.**
Сейчас [исторически: _resolve_src](/home/kazakovaleksey/PythonProjects/autorepeater/autorepeater/strategies.py:14) выбирает алгоритм по
форме строки. Новые тесты сначала требуют обязательный ACCOUNT/INDEX,
отсутствие угадывания и независимость третьей регистрации от индексных файлов.
Старый [исторически: тест приоритета цифрового src](/home/kazakovaleksey/PythonProjects/autorepeater/test/test_autorepeater.py:1293)
нужно заменить: он закрепляет поведение, которое намеренно удаляется.

**5.2. Реестр и подготовленный источник.**
Вместо NAMED_STRATEGIES вводим ALGORITHMS с AlgorithmDefinition:
prepare_source и create. Имя алгоритма задаётся при регистрации.
PreparedStrategy сохраняет фабрику и подготовленные данные, чтобы конструктор
не перечитывал конфиги. [исторически: Текущая фабрика](/home/kazakovaleksey/PythonProjects/autorepeater/autorepeater/strategies.py:37)
будет заменена create_strategy(prepared). Номер счёта проверяет модуль ACCOUNT,
имя конфигурации разрешает модуль INDEX. Дубликат регистрации запрещён.

**5.3. Разделение обнаружения и проверки конфигов.**
[исторически: load_index_config](/home/kazakovaleksey/PythonProjects/autorepeater/autorepeater/index_config.py:70) сейчас совмещает чтение
и проверку документа; [исторически: load_index_configs](/home/kazakovaleksey/PythonProjects/autorepeater/autorepeater/index_config.py:102)
прерывает весь обход на первой ошибке. Выделяем чистый валидатор уже прочитанного
JSON и независимые результаты по файлам. Обычный запуск отказывает только
из-за выбранного источника или его неоднозначности. Строгий полный загрузчик
остаётся отдельной операцией для проверки всего набора.

**5.4. Имена, дубликаты и ошибки путей.**
Обновляем [исторически: проверку конфликтов имён](/home/kazakovaleksey/PythonProjects/autorepeater/test/test_autorepeater.py:2684):
два индексных файла с одинаковым name по-прежнему конфликтуют, но name
конфига может совпадать с именем алгоритма. В
[исторически: проверке name](/home/kazakovaleksey/PythonProjects/autorepeater/autorepeater/index_config.py:76) снимается запрет ASCII-цифр.
Повреждённое тело с читаемым name всё равно участвует в обнаружении дубликата.
[исторически: Ошибки путей](/home/kazakovaleksey/PythonProjects/autorepeater/test/test_autorepeater.py:2700) и конфликт переменных сохраняются
внутри INDEX, но больше не мешают ACCOUNT или независимому алгоритму.

**5.5. Предупреждения и однократное чтение.**
Для выбранного корректного конфига соседний повреждённый файл даёт предупреждение
с путём и причиной. Отсутствующий выбранный конфиг не подменяется единственным
исправным. За запуск каждый файл читается один раз.
Текущее [исторически: семейство тестов отказа до Client](/home/kazakovaleksey/PythonProjects/autorepeater/test/test_autorepeater.py:2764)
расширяется сценариями выбранного и чужого повреждения; появление любого
SDK-вызова до разрешения ошибки считается провалом.

**5.6. Атомарная миграция запуска.**
В [исторически: CLI](/home/kazakovaleksey/PythonProjects/autorepeater/main.py:10) и [исторически: облачном обработчике](/home/kazakovaleksey/PythonProjects/autorepeater/autorepeater/serverless.py:31)

**5.7. Подготовка и создание используют один снимок конфигурации.**

### 6. Архитектурные проверки

**6.1. Общие контрактные тесты.**
Одинаковый набор тестов выполняется для ACCOUNT, INDEX и третьей тестовой

**6.2. Сигнатуры, данные и ленивость событий.**
Контракт проверяет форму методов, но не вызывает events и не исчерпывает

[исторически: Пустой поток](/home/kazakovaleksey/PythonProjects/autorepeater/test/test_autorepeater.py:1434) и

В снимках нет SDK DTO; DataAccessError может сохранять исходную причину только
для диагностики, она не становится частью интерфейса стратегии.

**6.3. Третий алгоритм через все точки входа.**
Добавляем тестовую регистрацию и запускаем её через Runner.run/run_sync,
CLI, query и окружение облака. Текущие сценарии перечислены в
[исторически: test_named_strategy_launches](/home/kazakovaleksey/PythonProjects/autorepeater/test/test_autorepeater.py:2173).
Новая реализация самостоятельно трактует src, не читает индексные настройки

**6.4. Проверка направлений импортов.**
AST-проверки запрещают стратегиями импортировать SDK, конкретный адаптер,
движок, Runner или друг друга; движку запрещают знать конкретные стратегии.
Текущий [исторически: прямой импорт SDK](/home/kazakovaleksey/PythonProjects/autorepeater/autorepeater/index_strategy.py:6)

[исторически: исполнителе](/home/kazakovaleksey/PythonProjects/autorepeater/autorepeater/repeater.py:4) остаются допустимыми.
Проверяем относительные импорты и тестируем сам анализатор на допустимых
и запрещённых примерах, чтобы он не давал ложную уверенность.

**6.5. Исполнение без установленного SDK.**
Одного AST недостаточно: зависимость может прийти через общий helper.
Отдельный процесс с запрещёнными t_tech/grpc импортирует стратегии

[исторически: reporting](/home/kazakovaleksey/PythonProjects/autorepeater/autorepeater/reporting.py:1), который вызывается из стратегий.
Это не обещание запуска торгового приложения без SDK: Runner и исполнитель
по-прежнему требуют его.

**6.6. Полные проверки после фиксации границ.**
Запускаем pytest и линтеры. Не исправляем нарушения архитектуры исключениями
из теста импортов и не снижаем существующие
[исторически: пороги покрытия](/home/kazakovaleksey/PythonProjects/autorepeater/.github/workflows/python-app.yml:43).
Новая архитектура должна пройти те же регрессии, что и исходная,

### Что остаётся неизменным

- Цель строится до расчёта заявок; затем продажи, покупки и только после этого
  отправка: [исторически: sync_accounts](/home/kazakovaleksey/PythonProjects/autorepeater/autorepeater/repeater.py:146).

  [исторически: get_max_sum_positions_price](/home/kazakovaleksey/PythonProjects/autorepeater/autorepeater/orders.py:18).
- Debug не отправляет заявки, пустая цель не ликвидирует счёт.
- Резерв применяется один раз к стоимости назначения; валюты источника
  исключаются только алгоритмом ACCOUNT.
- Индексное распределение, отсечение хвоста, округления и лотность не меняются.
- Продолжительный локальный цикл и разовый serverless сохраняются;
  обязательные algoritm и явный источник являются изменением интерфейса запуска.
