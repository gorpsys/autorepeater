# План инфраструктуры проверок и e2e песочницы

## Цель и границы

Единые команды Make для локальных проверок и GitHub Actions. Настоящие e2e
создают счета в песочнице Т-Инвестиций и запускают приложение непосредственно
локально либо на GitHub Runner. Развёртывание Yandex-функции не входит в задачу.
Не менять торговую арифметику, пороги покрытия и архитектурную очередь задач.

Реализация в ветке `feature/test-infrastructure`, отдельный PR в `master`.
Чужие неотслеживаемые результаты архитектурного аудита не включать в этот PR.
Для каждого шага: сначала офлайн-тесты, затем реализация и проверки.

## Исходные точки

- `Makefile`: сейчас существует только `claude-yandex-archive`; `PYTHON ?= python3`.
- `.github/workflows/pylint.yml`: push запускает pylint прямой командой.
- `.github/workflows/python-app.yml`: pytest/flake8/coverage/diff-cover запускаются
  прямыми командами; Python 3.12, общее и diff-покрытие не менее 90%.
- `autorepeater/runner.py:40`: постоянный запуск с обычным SDK Client.
- `autorepeater/runner.py:51`: конечный `run_sync`, также с обычным Client.
- `autorepeater/runner.py:61`: соединение стратегии и реальных SDK-адаптеров.
- `autorepeater/order_execution.py:57`: настоящий BESTPRICE и проверка receipts.
- `test/conftest.py:8`: офлайн-фикстура обнуляет settlement timeout; e2e не должны
  наследовать её или фикстуры с подменой рабочих конфигов.
- `.coveragerc`: рабочие модули и scripts входят в покрытие; область не сужать.

## Согласованные решения

1. `make lint`, `make test`, `make coverage`, `make e2e` являются общими входами.
   Обычные test/coverage работают без сети и без sandbox-токена.
2. Песочница выбирается явно на границе создания SDK-клиента. Все её вызовы,
   включая установочные операции тестов, имеют unary timeout. Никакого fallback
   на production, production-токен или существующий пользовательский счёт.
3. В установленном SandboxService нет управления временем и рыночными ценами.
   Live-сценарии создают состав с перекосом, соответствующим результату движения
   цен. Сам переход из-за изменения цен, ночь и выходные проверяются офлайн.
   Не выдавать подготовленный перекос за настоящее движение рыночной цены.
4. Не запрещать live-запуск по календарю. Проверять настоящую доступность нужных
   инструментов. Невозможность выполнить обязательные сделки не даёт зелёного
   результата; не скрывать её через skip или тихую замену состава BALANCED.
5. Ручной запуск для PR, автоматический после merge в master. Отсутствие успешного
   прогона актуального SHA или его падение блокирует merge. Форкам секрет не
   предоставляется; отсутствие e2e показывается явно и не считается успехом.
6. Все GitHub sandbox-прогоны сериализуются общей группой concurrency, включая
   master. Не отменять текущий прогон. Использовать `queue: max`, если эта
   возможность доступна: очередь GitHub ограничена 100 ожидающими прогонами,
   порядок выполнения не обещать. Отменённый/не запущенный прогон не зелёный.
7. Между локальным запуском и GitHub общая блокировка не нужна. Документировать
   запрет их пересечения при общей песочнице и разные пространства имён счетов.
8. Каждый сценарий создаёт отдельные временные счета. Удалять только собственные
   тестовые счета. После сбоя сначала попытаться снять диагностику, затем
   очистить. Ошибка диагностики не должна отменять попытку удаления.
9. После получения GitHub-блокировки убирать счета прерванных прошлых тестов
   только из строго определённого пространства имён CI. Локальные счета имеют
   другое пространство имён. Не удалять счета по произвольному частичному имени.
10. Начальный предел live-прогона был 15 минут. После исчерпания этого окна
    в реальном прогоне 07.10.2026 текущий предел поднят до 30 минут. Его можно поднять,
    но не выше часа. Нужен внешний предел процесса: рабочий quota retry может
    продолжаться неограниченно, если весь прогон не ограничен отдельно.
11. Секрет `SANDBOX_TOKEN` уже создан пользователем в GitHub. Пользователь разрешил
    GitHub Secrets вместо Vault для этого личного проекта. Не хранить секрет в
    коде, артефактах, конфиге стратегии или командных аргументах.

Публичный конечный вход для e2e: `Runner(..., sandbox=True).run_sync()`.
`sandbox` принимает только bool и только именованным аргументом; без него
сохраняется production. `RunnerParams` содержит только `debug`. Клиент
создаётся при запуске, не при импорте или конструировании Runner.
Минимальная обвязка после подготовки конфигурации и создания тестового dst:

```python
import os
from autorepeater.runner import Runner
from autorepeater.strategies import prepare_strategy

prepared = prepare_strategy('INDEX', 'GOLD')
Runner(token=os.environ['SANDBOX_TOKEN'], prepared_strategy=prepared,
       dst=created_dst_account_id, sandbox=True).run_sync()
```

Runner получает токен явно и не выбирает его из окружения; вызывающая обвязка
использует обязательный `SANDBOX_TOKEN`, без fallback на `INVEST_TOKEN`.
CLI и облачный вход по-прежнему используют прежний production-режим.
`run_sync` не открывает поток событий и не просматривает все счета пользователя.

Офлайн изучены исходники установленного t-tech-investments 1.51.0:
`t_tech.invest.sandbox.client.SandboxClient` принудительно устанавливает
`INVEST_GRPC_API_SANDBOX` (`sandbox-invest-public-api.tbank.ru`), наследует
interceptors обычного Client. `Client.__enter__` передаёт один перехваченный
channel всем Services: instruments, market_data, operations, orders, users
и sandbox. Стандартные методы портфеля, позиций, заявок, статуса и GetMaxLots
используют этот channel; SDK помечает старые sandbox-аналоги как deprecated
и рекомендует методы SandboxClient. Setup open/close/pay-in в SandboxService
также использует этот channel и токен клиента. Установочные вызовы шага 4
должны создавать свой SandboxClient с UnaryDeadlineInterceptor; обвязка
жизненного цикла здесь не реализуется. Deadline всех unary-вызовов приложения
10 секунд, меньший существующий timeout сохраняется. Fallback отсутствует.

Первый санкционированный live probe подтвердил UUID песочницы. SDK DTO
`OpenSandboxAccountResponse.account_id` и официальный `Account.id` имеют тип
string, отдельного поля числового номера нет. Пользователь согласовал в шаге 4
строковый `source_account_id`: непустой, без пробельных символов, передаётся
API без преобразований. Числовые строки, ведущие нули и регистр сохраняются;
UUID не заменяется выдуманным числовым алиасом. Изменение не входит в шаг 3.
