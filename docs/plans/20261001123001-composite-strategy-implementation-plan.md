# Комплексный алгоритм и обновлённый контракт стратегий

## Цель и статус

Статус: реализация продолжается; этапы 1–2 завершены, этап 3 не начат.
Исходная ревизия: `origin/master` (`999f407`, то же дерево после squash merge).
Первичные источники проверены 1 октября 2026 года в текущей рабочей папке.
Ссылки на строки ниже относятся к этой ревизии, а не к будущей реализации.

Добавить алгоритм `COMPOSITE`, который распределяет стоимость одного счёта
назначения между другими стратегиями и объединяет их полные цели.
Дочерние стратегии не торгуют самостоятельно: общий исполнитель рассчитывает
единую разницу с назначением и отправляет единый набор заявок.

Одновременно перенести применение резервов внутрь стратегий и отделить
описание подписки от обработки событий. Существующие алгоритмы и новый
алгоритм должны пользоваться одним контрактом без зависимости от SDK,
исполнителя и конкретных реализаций друг друга.

## Согласованные решения

- Алгоритм называется `COMPOSITE`; его `src` выбирает JSON по полю `name`.
- Каждый компонент задаёт `algoritm`, `src` и долю выделенного бюджету родителя.
- Сумма долей не больше 1. Доли не нормализуются; остаток остаётся деньгами.
  Сумма вычисляется в порядке компонентов с точностью Decimal 28; результат
  ровно 1 допустим, в том числе если он получен округлением исходной суммы.
- Резерв принадлежит стратегии, применяется только ею и задаётся конфигом.
  У исполнителя нет свойства, метода или параметра резерва.
- У ACCOUNT появляется отдельный конфиг настроек. Его `src` остаётся номером
  счёта из ASCII-цифр, с сохранением ведущих нулей, не именем JSON.
  Резерв и событийный контракт обновляются, но проверка положительности
  бюджета в ACCOUNT не добавляется. В штатном запуске бюджет положительный;
  существующую расчётную допустимость нулевого и отрицательного бюджета
  ACCOUNT сохраняем.
- CLI `-r`/`--reserve` удаляется; переопределения резервов при запуске нет.
- `threshold` один для всего пересчёта, считается от полной стоимости `dst`
  до резервов и распределения между компонентами.
- Подписка и решение о пересчёте по событию разделяются.
- Пустая цель любого компонента означает пропуск всей синхронизации с записью
  причины. Частичная общая цель не отправляется.
- Количества одинаковых UID складываются. Их оценочная цена в общей цели
  равна максимальной из цен компонентов, содержащих этот UID в количествах.
- Вложенность COMPOSITE разрешена. Циклы запрещены и обнаруживаются до SDK.
- Любая ошибка выбранного компонента отменяет весь текущий пересчёт до заявок.
- Решение пользователя от 1 октября 2026 года: демонстрационный BALANCED
  содержит INDEX/IMOEX `0.684210526`, INDEX/BOND `0.210526316`, INDEX/GOLD
  `0.105263158`, именно в этом порядке. По новому запросу пользователя
  облачный default становится COMPOSITE/BALANCED на этапе 7 одновременно
  с регистрацией и встроенным balanced.json. До этапа 7 действует INDEX/TMON;
  локальный CLI сохраняет обязательные явные algoritm/src.
- Реализация идёт в отдельной ветке `feature/composite-strategy` от
  `origin/master`. Пользователь разрешил commit/push и отдельный PR;
  исполнитель этапа создаёт только локальный коммит, публикацию ведёт родитель.
  Завершённые исторические планы не переписываются.

## Подход к разработке

- Python 3.12, существующий плоский пакет, без новых зависимостей.
- Небольшие шаги через TDD: сначала тест нужного поведения, затем реализация.
- Изменения общего контракта переносить атомарно вместе со всеми потребителями,
  фикстурами и независимой тестовой стратегией. Не оставлять сломанный запуск
  или временные совместимые обёртки между этапами.
- Каждый этап заканчивается полным успешным `pytest`; следующий этап не
  начинать, пока весь набор не проходит. Новые и изменённые пути обязательно
  проверять на успешных сценариях, ошибках и границах.
- Чистую торговую арифметику ACCOUNT и INDEX сохранить. Единственное намеренное
  изменение порога отправки: база threshold теперь полная стоимость назначения.
- Изменения контрактов, отказ от старых флагов и обязательность reserve
  документировать явно, не выдавать их за полностью совместимый рефакторинг.
- Отмечать завершённые пункты немедленно; при изменении объёма работ обновлять
  этот план до продолжения реализации.

## Обновлённый контракт стратегии

```python
strategy.load_snapshot(data)                     # непрозрачный свежий снимок
strategy.build_target(snapshot, budget)          # полная TargetPortfolio
strategy.event_accounts(dst_account_id)          # tuple[str, ...]
strategy.should_rebalance(event, dst_account_id) # bool
```

1. Конструктор получает уже подготовленные параметры и не выполняет I/O.
   Стратегия не хранит SDK-клиент, порт данных или исполнитель.
2. `load_snapshot` читает через StrategyData, возвращает собственные данные
   для одного пересчёта. Одновременность котировок и счетов не гарантируется;
   композиция собирает отдельные свежие снимки в порядке компонентов.
3. `build_target` получает полный выделенный бюджет в виде конечного Decimal;
   в штатном запуске он положительный. INDEX сохраняет свою проверку
   положительности, COMPOSITE проверяет положительность своего бюджета,
   ACCOUNT новой проверки положительности не получает. Метод не читает
   файлы или порт, не открывает подписку,
   не отправляет заявки и не делает пользовательский вывод. Резерв и расчёт
   доступного бюджета находятся внутри реализации стратегии.
4. `event_accounts` возвращает упорядоченный непустой tuple номеров счетов
   без повторений, без чтения данных. Возвращаемые идентификаторы проверяет
   общий потребитель перед открытием подписки.
5. `should_rebalance` получает один собственный PositionEvent и возвращает
   строго bool. Не читает данные, не логирует пропуск и не открывает стрим.
6. ACCOUNT сохраняет нынешний предикат `check_triggers`, включая проверку
   первой денежной позиции назначения. INDEX сохраняет нынешнюю проверку
   всех блокировок назначения. Не унифицировать их торговые условия.
7. Композиция объединяет счета детей с удалением повторений и сохранением
   порядка первого появления. Событие вызывает пересчёт, если хотя бы один
   ребёнок требует его. Проверять тип всех решений детей, а не скрывать
   неверный bool позднего компонента ранним положительным решением.
8. Общий цикл один раз логирует пропущенное событие, открывает один поток
   StrategyData.position_events и сохраняет порядок начального пересчёта,
   подписки и восстановления после транспортных ошибок.
9. Проверка стратегии проверяет четыре вызываемых метода без их вызова.
   `default_reserve` не является частью контракта и не проверяется.

Движок остаётся общим координатором пересчёта и исполнения. Данный план
не выделяет отдельную систему исполнения заявок: он удаляет знание о резервах,
видах алгоритмов и составе композиции, но сохраняет чтение назначения,
вычисление общей стоимости, порог, события и существующие методы торговли.

### Результат и безопасный пропуск

TargetPortfolio сохраняет `quantities` и `prices`, добавляет
`empty_reason: str | None = None`. Это только диагностическое поле:
непустая причина допустима при пустой карте количеств; для непустой цели
причина должна отсутствовать. Прежние двухаргументные конструкторы продолжают
работать. Типы и конечность количеств/цен, допустимость отрицательных,
нулевых и дробных значений сохраняются. Не вводить новую поддержку шортов.

COMPOSITE сначала получает и проверяет цели всех компонентов. Даже при раннем
пустом компоненте нельзя скрывать ошибочную цель последующего компонента.
Если ошибок нет, но хотя бы одна цель пустая, результатом будет пустая общая
цель с причиной, указывающей цепочку алгоритмов/источников. Исполнитель
логирует назначение и причину и возвращается до любых расчётов заявок.
Вложенная композиция распространяет причину вверх. Исключения источников
не превращаются в пустой результат.

Явные нули в непустой карте не являются пустой целью. Отсутствующий UID в
непустой итоговой карте сохраняет смысл нулевой цели для имеющейся позиции.

## Конфигурация

Разделить схемы по каталогам, сохранив текущие индексные пути:

```text
autorepeater/configs/*.json              существующие INDEX
autorepeater/configs/account/account.json настройки ACCOUNT
autorepeater/configs/composite/*.json     именованные COMPOSITE
```

ACCOUNT использует один конфиг настроек для всех своих источников:

```json
{
  "reserve": "0.01"
}
```

Путь задаётся `ACCOUNT_CONFIG_PATH`; без переменной используется встроенный
файл относительно модуля. Относительный явно заданный путь считается от
рабочего каталога. Пустой путь, отсутствие файла, повреждённый JSON или
неверный reserve приводят к отказу до SDK, без fallback на константу.
ACCOUNT не читает индексные или комплексные конфиги. Существующий CLI
`--algoritm ACCOUNT --src 001234` сохраняется.

COMPOSITE использует следующий формат. BALANCED с этим порядком и долями
становится облачной стратегией по умолчанию на этапе 7:

```json
{
  "name": "BALANCED",
  "components": [
    {"algoritm": "INDEX", "src": "IMOEX", "weight": "0.684210526"},
    {"algoritm": "INDEX", "src": "BOND", "weight": "0.210526316"},
    {"algoritm": "INDEX", "src": "GOLD", "weight": "0.105263158"}
  ]
}
```

- `name`: непустая строка без пробельных символов; точное имя выбора.
  Цифровое имя допустимо. Уникальность внутри каталога COMPOSITE; совпадение
  с именем INDEX или алгоритма допустимо.
- `components`: обязательный непустой список; порядок задаёт порядок
  подготовки, чтения снимков и объединения. Повтор одной ссылки в разных
  компонентах допустим, каждая получает отдельную долю.
- `algoritm`: точное непустое зарегистрированное имя, включая COMPOSITE.
  Не определять алгоритм по форме src.
- `src`: обязательная непустая строка, которую проверяет выбранный алгоритм.
  Для ACCOUNT номер счёта, для INDEX и COMPOSITE поле name их конфигов.
- `weight`: обязательная конечная Decimal-строка в `(0, 1]`. Нулевые компоненты
  не допускаются: для отключения компонент удаляется из конфигурации.
  JSON-числа, bool, NaN и Infinity запрещены. Сумма весов вычисляется обычным
  сложением Decimal в порядке компонентов, начиная с Decimal(0), с точностью
  28. Полученный результат должен быть не больше 1. Результат ровно 1
  допустим и при округлении математической суммы к 1. Повышенную точность,
  отдельную проверку точной суммы, нормализацию и epsilon не добавлять.
- Полей `reserve`, `threshold`, `debug`, `dst` и токена в COMPOSITE или его
  компонентах нет. Такие поля отклоняются, а не молча игнорируются.
  COMPOSITE распределяет бюджет, а каждый конечный алгоритм применяет
  собственный резерв из своего конфига. Параметры исполнения общие.

Каталог задаётся `COMPOSITE_CONFIG_DIR`, по умолчанию встроенный каталог
относительно модуля. Читаются только непосредственные нескрытые `*.json`.
Выбор по name, не по имени файла; регистр и пробелы не нормализуются.
Ошибка или неоднозначность выбранного имени останавливает запуск; повреждённый
или дублированный чужой конфиг даёт предупреждение и не мешает выбранному.
Ошибка любого конфига, используемого компонентом, останавливает подготовку
всей композиции до обращения к SDK. Предупреждение об этом конфиге при
подготовке предыдущего компонента не отменяет последующего отказа.

У INDEX сохраняются INDEX_CONFIG_DIR и совместимый IMOEX_CONFIG_PATH,
их взаимное исключение, изолированный выбор и отдельная строгая проверка
всего набора. Reserve становится обязательным; значения существующих
встроенных JSON не меняются. В старые внешние конфиги без reserve потребуется
добавить поле. Min_position_value остаётся необязательным с прежним нулём.

Конфиги фиксируются при подготовке запуска, не перечитываются конструкторами
и при событиях. Изменение файлов требует нового запуска. Глобального кеша нет.
Не вводить транзакционное чтение нескольких файлов или обновление на лету.

## Подготовка дерева без взаимных импортов

Добавить в нейтральный strategy_contract Protocol `PreparationContext` с
методом `prepare(algoritm, src) -> PreparedStrategy`. Обновить определение
подготовки в AlgorithmDefinition на `prepare_source(src, context)` для всех
алгоритмов. ACCOUNT и INDEX не обязаны использовать context; COMPOSITE
вызывает через него подготовку детей. Публичный вызов приложения
`prepare_strategy(algoritm, src)` остаётся двухаргументным.

Конкретный контекст принадлежит слою сборки в strategies.py и хранит стек
активных пар `(algoritm, src)`. Повтор пары в текущем пути означает цикл,
выдаёт понятную ошибку с полной цепочкой до SDK. Повтор пары в соседних ветвях
не является циклом. Проверять и прямую самоссылку, и многозвенный цикл.
Не использовать один глобальный набор посещённых узлов вместо стека пути.

Подготовленный источник COMPOSITE содержит конфиг и упорядоченные
PreparedStrategy детей. Фабрика создаёт детей из сохранённых фабрик и данных,
не обращаясь повторно к реестру или файлам. Вынести небольшую общую функцию
создания и validate_strategy в нейтральный контракт, чтобы слой сборки
и композиция не дублировали проверки и не импортировали друг друга.
Для повторных компонентов создавать отдельные объекты стратегий.

Не гарантировать единственный проход индексного каталога на всё дерево:
каждая подготовка выбранного INDEX сохраняет действующее правило одного
прохода его каталога. В Runner всё готовое дерево используется без повторной
подготовки. Импорт модулей по-прежнему не читает конфиги и не открывает SDK.

## Распределение и объединение

Пусть V — полная текущая стоимость назначения. Для каждого ребёнка:

```text
выделенный бюджет ребёнка = V * weight
доступный бюджет конечной стратегии = выделенный бюджет * (1 - reserve)
нераспределённая часть родителя = V * (1 - сумма weight)
```

COMPOSITE не вычитает дополнительный резерв. При вложенности передаваемый
бюджет умножается на долю каждого уровня, резерв применяется только конечной
стратегией. Не перераспределять резервы, остатки лотов и неиспользованные доли
в другие компоненты, не выполнять дополнительную перенормализацию.

Для 100000 и примера BALANCED дети получают 68421.0526, 21052.6316
и 10526.3158 (IMOEX, BOND, GOLD). При текущих резервах их доступные
бюджеты равны 67736.842074, 21042.1052842 и 10521.0526421;
сумма долей равна 1, нераспределённого остатка нет,
700.0000007 составляют резервы до округления лотов.
Это демонстрация передачи бюджета, не обещание фактической суммы исполнения.

В общей цели суммировать количества каждого UID в порядке компонентов,
цену брать через max только среди компонентов, имеющих этот UID в quantities.
Лишние записи prices не учитываются. Не округлять сумму повторно до лотов,
не отбрасывать нулевую сумму или отрицательные количества и не объединять
цену назначения с ценой цели. Исходные снимки и цели детей не изменять.

ACCOUNT сохраняет дробные количества и порядок Decimal-операций. INDEX
сохраняет прежний чистый расчёт по уже доступному бюджету, лотность,
минимум позиции, отбор префикса и порог ошибки малых позиций.
Комплексный алгоритм не исправляет прежнее округление заявок исполнителем.

Threshold сравнивается строго: `volume > V * threshold`. Сохранить нынешнюю
оценку объёма по числу лотов без дополнительного умножения на лотность,
max сумм покупок/продаж, раздельные карты цен и BESTPRICE без цены исполнения.
Не вводить постороннее исправление денежной оценки в рамках этой задачи.

Ограничения: Decimal-арифметика имеет точность 28; резерв и номинальные доли
не гарантируют покрытие комиссий, движения котировок или последствий
округления дельт ACCOUNT. Максимальная цена общего UID служит оценкой порога,
не единой котировкой и не ограничителем стоимости цели. Конвертации валют нет;
новых запретов валют в этот план не включать. Отправка заявок не атомарна,
сбой после успешной продажи не отменяет её и не обеспечивает откат.

## Команды итоговой проверки

Команды выполняются в активном окружении проекта с Python 3.12.
Новые Python-файлы также должны попасть в запуск pylint, даже если ещё
не добавлены в индекс Git; пример ниже перечисляет их через rg.

```bash
pytest --cov --cov-report=term-missing --cov-report=xml
coverage report --fail-under=90
git fetch origin master
diff-cover coverage.xml --compare-branch=origin/master --fail-under=90
pylint $(rg --files autorepeater scripts test -g '*.py') main.py handler.py
flake8 . --count --select=E9,F63,F7,F82 --show-source --statistics
git diff --check
make claude-yandex-archive
```

Покрытие включает рабочие модули, точки входа и новые исполняемые скрипты
по действующей .coveragerc. Нельзя исключать новый сборщик или композицию
для достижения 90%. Архивные интеграционные subprocess-проверки подтверждают
состав и запуск приложения, но не считаются источником покрытия сборщика:
для этого обязательны прямые вызовы его функций и точки входа в процессе pytest.
GitHub Actions остаются на Python 3.12: pylint на push,
pytest/flake8/покрытие на PR в master и push в master. Проверка GitHub не
подменяется локальными командами; публикацию отдельного PR ведёт родитель.

## После реализации

Действия внешних систем, без отметок выполнения в этапах кода:

- По разрешению пользователя создать отдельный PR из feature/composite-strategy,
  выполнить публикацию и проверить оба GitHub workflow. Исполнитель этапа
  делает локальный коммит; push/PR выполняет родитель. Merge не разрешён.
- Пользователь выбирает реальные доли и источники, при необходимости меняет
  ACCOUNT_CONFIG_PATH, COMPOSITE_CONFIG_DIR и индексные пути в окружении.
- После этапа 7 облачный запуск без query/environment выбора использует
  COMPOSITE/BALANCED. Для другого источника явно задать algoritm/src в query
  либо ALGORITM/SRC_ACCOUNT в окружении; прежний режим задаётся INDEX/TMON явно.
  Локальный CLI требует оба параметра.
- При использовании внешних конфигов добавить обязательные reserve; внешние
  каталоги не появляются в архиве автоматически.
- Любая проверка с API требует нового явно предоставленного токена и отдельного
  согласования режима. Не использовать исторический токен из переписки,
  не выполнять реальные сделки для проверки плана или автоматических тестов.
