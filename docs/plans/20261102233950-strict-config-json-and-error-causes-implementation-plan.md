## Архитектура и владение проверками

```text
файл UTF-8 -> общий config_json parser -> обычные Python-объекты
          -> отдельный validator ACCOUNT / INDEX / COMPOSITE
          -> общий config_catalog: кандидаты и точный выбор
          -> prepare_strategy -> прежние чистые стратегии и исполнение
```

- Новый небольшой `autorepeater/config_json.py` владеет только чтением и
  неоднозначностью JSON. Предлагаемая функция `read_config_document(path) -> object`
  читает файл один раз и применяет `json.load(..., object_pairs_hook=...)`.
  Внутренний hook возвращает dict или выдаёт ValueError при повторном ключе.
  Имя helper не является новым публичным пользовательским API.
- Алгоритмические `read_*_document` сохраняются как точки входа и делегируют чтение.
  Схемы остаются чистыми: validate_* не обращаются к файлам, env, SDK или каталогу.
  Parser не проверяет Decimal, резерв, валюту, поля стратегии или имена источников.
- INDEX владеет списками своих ключей и проверяет их после проверки типа dict,
  до построения экономических DTO. Не импортировать `_check_keys` COMPOSITE:
  схемы алгоритмов независимы, малый локальный helper допустим.
- `config_catalog` владеет отложенной диагностикой кандидатов и выбором причины
  при отказе. Нельзя проверять этот инвариант повторно в Runner, серверном handler
  или финансовом исполнителе.
- Не переиспользовать parser из `scripts/runtime_lock.py` импортом scripts в
  runtime приложения. Не менять глобальные настройки json или Decimal.

Публичные методы стратегий, SDK-порты/DTO, расчёты target, пути/env-контракты,
предупреждения о чужих файлах и число чтений не меняются. C31: `_account_paths`,
`_index_paths`, `_composite_paths` и различия их error translation не рефакторить.

## Точные контракты PR A — C29/C30

### Parser

Повтор определяется по декодированному имени ключа в одном объекте JSON.
Объект внутри списка или extra-поля также проверяется. Одинаковый ключ в двух
разных объектах допустим; одинаковые значения повторного ключа не делают вход
допустимым. Экранированные написания одного имени считаются тем же ключом.
Не менять обычные типы JSON и порядок корректных объектов, не вводить parse_float
или другой способ разбора чисел вместо последующей проверки decimal-строк схемой.

Прямой loader отвергает документ с дублем через ValueError. Ошибка сообщает о
повторном ключе, но не выводит весь документ или значения. Полный JSON Pointer
вложенности не обещать: stdlib hook сам его не предоставляет. Путь файла остаётся
в существующей диагностике каталога. Обычные ошибки I/O/JSON-синтаксиса не скрывать.

При ошибке parser документ не разобран и имя кандидата недоступно. Не извлекать
name из сырого текста, частично разобранного dict или имени файла. Поэтому при
каталожном выборе возможен прежний UnsupportedSourceError с problematic files,
а корректный отдельно выбранный конфиг не блокируется повреждённым чужим файлом.
Файл с неразобранным JSON не участвует в подсчёте дубликатов name как валидно
распознанный документ. Это сохраняет действующий контракт повреждённого JSON.

### Закрытая схема INDEX

Разрешённые ключи корня:

| Обязательные по существующей схеме | Необязательные с прежними defaults |
| --- | --- |
| name, reserve, max_lot_weight_error, instruments, allocation_drift_limits | min_position_value, reference_capitalization_currency, preferred_currency |

Разрешённые ключи инструмента:

| Обязательные по существующей схеме | Валютные поля с существующими условиями |
| --- | --- |
| ticker, effective_quantity, free_float, weight_limit, reference_price, reference_weight, reference_index_capitalization | reference_price_currency, reference_fx_rate |

Список разрешённых ключей закрыт: любой ключ вне него отвергается, без эвристики
«экономическое/описательное имя». Проверка обязательности и допустимости значений
остаётся существующей. Не делать необязательные поля обязательными и не менять
условия reference_fx_rate: default 1 сохраняется только в предусмотренном нынешним
кодом случае; межвалютные требования не ослабляются.

Drift-таблица INDEX уже проверяет точный набор budget_from/budget_to/upper_inclusive/
limit — сохранить. COMPOSITE уже строгий на двух уровнях — сохранить. ACCOUNT
принимает только name/source_account_id/reserve/allocation_drift_limit.
Неизвестное поле отвергается с именем ключа, без значений и warning-only режима.

Отсутствующий min_position_value по-прежнему даёт 0. Если присутствует опечатка
min_position_vaule, теперь ошибка unknown field; не угадывать правильное имя,
не исправлять значение и не продолжать с default. Ошибка поля содержит контекст
корня или instruments[i] и имя неизвестного ключа; не дамп всего объекта.

## Точные контракты PR B — C32

Внутреннюю модель `Candidate` расширить исходной причиной отдельно от нынешнего
`error: ValueError | None`: например, `cause: OSError | ValueError | None = None`.
Причина — тот же объект исключения, пойманный при чтении/валидации, с его исходной
цепочкой. Default None сохраняет корректность существующих четырёхпозиционных
конструкторов Candidate в тестах; успешный кандидат не получает причину.

Это обоснованное изменение внутренней модели каталога: текст и обёрнутый ValueError
не позволяют восстановить исходный тип/цепочку. Не добавлять exception в DTO стратегии
или конфигурации алгоритмов. Если при реализации выбран другой эквивалентный способ
хранения, отразить его в плане до расширения изменений.

В discover_candidates сохранить причину и продолжить сбор кандидатов. Не поднимать
ошибку немедленно. При единственном точном совпадении name с ошибкой
select_candidate делает `raise candidate.error from candidate.cause`, сохраняя
нынешний внешний ValueError и диагностический текст. Например:
`ValueError(путь/name) -> ValueError(reserve) -> InvalidOperation`.

| Ситуация | Поведение после PR B |
| --- | --- |
| Единственный точный выбранный кандидат невалиден | Фатальный прежний ValueError с исходным cause, без повторного read |
| Чужой кандидат невалиден, выбранный корректен | Прежнее краткое warning и успешный выбор; cause хранится, но не поднимается |
| JSON не разобран, name неизвестно | Причина сохраняется в Candidate; name не восстанавливается; прежняя политика предупреждения/отсутствующего источника |
| Выбранное name отсутствует или неоднозначно | Прежний UnsupportedSourceError / ошибка duplicate name; не приписывать случайный cause одному из файлов |
| INDEX без name и ровно один ошибочный кандидат | Сохранить внешний UnsupportedSourceError и сообщение существующей ветки select_index_config; связать с причиной единственного кандидата |
| INDEX без name, кандидатов несколько или нет | Прежняя ошибка неоднозначного выбора, без произвольной причины |
| Ручной legacy Candidate(error=..., cause=None) | Сохранить отказ без выдуманной причины; не требовать миграции всех конструкторов |

Для единственного INDEX-кандидата без name причина однозначно известна независимо
от доступности name: поэтому маленькая диагностическая правка его селектора
относится к C32. Она не меняет схему/семантику выбора или поведение прямого loader.
При отсутствии точного совпадения среди нескольких кандидатов нет единственного
исходного исключения для связывания; не вводить ExceptionGroup или новые правила выбора.

Не расширять набор перехватываемых классов до Exception, не скрывать programming
errors и сигналы остановки. Не добавлять traceback/raw JSON к чужим warnings;
хранение причины не требует новых логов или дополнительных чтений.

## Подход к реализации и прогресс

TDD RED -> GREEN. Каждый шаг с изменением поведения включает собственные тесты
и завершается GREEN соответствующего набора до следующего шага. Не писать заранее
все RED так, чтобы незавершённые тесты оставались в готовом промежуточном коммите.
Не ослаблять пороги, exclusions, untracked/diff-покрытие или workflows.
Порты и границы побочных эффектов проверять через autospec(spec_set=True), реальные
валидные DTO/файлы и конечные офлайн-сценарии; сеть и SDK-клиенты не конструировать.

Чекбоксы ниже отражают фактический прогресс разрешённой реализации. При
согласованном изменении объёма сначала обновить план; отмечать фактически завершённые
пункты сразу. Сохранить чужие локальные изменения: продуктовые ветки/worktree от
актуального master, без переключения грязной рабочей папки и без массового staging.
