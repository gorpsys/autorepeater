# Автоматическое создание моков SDK-сервисов

## Цель и согласованные решения

Упростить поддержку тестов разработчиками и агентами: заменить ручной
`FakeClient` и его вложенные сервисы моками, создаваемыми по установленному SDK.
Пользователь согласовал `unittest.mock.create_autospec` и сохранение явных,
детерминированных данных портфелей и заявок.

Рабочая ветка: `feature/mock-generation-research`. Статус: Task 1–4 выполнены,
финальное ревью завершено без замечаний, локальные проверки пройдены;
Python 3.10 остаётся проверить в CI после публикации.
Генерация происходит при создании pytest-фикстуры, отдельных генерируемых
Python-файлов и команды `make generate-mocks` не требуется.

## Контекст

- `test/test_autorepeater.py`: 62 теста, общий `FakeClient`, пять вложенных
  fake-сервисов, фикстуры `client` и `auto_repeater`.
- `FakeInstruments`: поиск и получение инструмента; проверка UID-типа поиска.
- `FakeOperations` и `FakeUsers`: заранее заданные портфели и счета.
- `FakeOrders`: проверяет параметры заявок внутри подменённого метода.
  `test_post_orders` и `test_sync_accounts` сейчас не проверяют вызовы явно.
- `FakeOperationsStream`: два пустых стрима, `RequestError`, затем
  `TestException`; события позиций этот сценарий не проверяет.
- `autorepeater/repeater.py`: потребитель пяти сервисов SDK.
- `requirements.txt`: `t-tech-investments==1.51.0`; новые зависимости не нужны.
- `AGENTS.md`: правила тестирования; `CLAUDE.md` ссылается на него.
- CI использует Python 3.10, pytest, pylint и flake8.

Исходный запуск: 62 теста прошли в `/tmp/autorepeater-install-check` на Python
3.12. Есть существующие предупреждения SDK, python-json-logger и сбора
`TestException`. Совместимость с Python 3.10 должна быть проверена в CI.

## Подход и границы

Использовать обычную последовательную разработку: каждый шаг включает
обновление тестов и их успешный запуск перед следующим шагом. Сохранять
существующие расчётные сценарии и ожидаемые значения. Отмечать выполненные
пункты сразу, обновлять план при изменении объёма работ.

Изменения ограничены тестами и правилами для агентов. Бизнес-логика, локальный
CLI, serverless-обработчик, зависимости и сборка облачного архива не требуют
изменений. Новые модели данных, API, фоновые задачи и интеграции не нужны.
Тесты не создают настоящий SDK-клиент, не требуют токена и не обращаются к API.

`MoneyValue`, `Quotation`, `PortfolioPosition`, ответы сервисов и события
стрима остаются настоящими SDK-объектами с явными значениями. Автогенерация
моков проверяет наличие методов и сигнатуры, но не выводит ответы и
бизнес-ожидания: их задаёт каждый тест или общая фикстура данных.

Скилл `mock-generator`, упомянутый в шаблоне plan-writer, работает с Go и
gomock/mockgen; для этого Python-проекта неприменим.

## Техническое решение

Использовать `InstrumentsService`, `OperationsService`, `UsersService`,
`OrdersService`, `OperationsStreamService` из `t_tech.invest.services`.
В SDK 1.51.0 эти имена экспортируются как обёрнутые декоратором функции.
Перед autospec требуется `inspect.unwrap`:

```python
create_autospec(inspect.unwrap(OrdersService), instance=True, spec_set=True)
```

Проверено на всех пяти сервисах: корректные вызовы принимаются, неизвестный
keyword-аргумент отклоняется. Прямое применение autospec к экспортированному
имени ошибочно сохраняет обязательный `self`.

Контейнер `client` создать через `Mock(spec_set=[...])`, разрешив только
`instruments`, `operations`, `users`, `orders`, `operations_stream`, и
присвоить каждому атрибуту соответствующий autospec. Это небольшой контейнер
сервисов, а не копия реализации SDK. Autospec всего `Client` недостаточен:
атрибуты сервисов появляются при инициализации. Конструкторы SDK не вызывать.

Фикстура имеет function scope, каждый тест получает новые моки. Сценарные
ответы задавать через `return_value` или `side_effect`. Для поиска по UID или
счёту допустимы небольшие таблицы и функции выбора ответа без бизнес-логики.
Не переносить целиком старый fake в универсальный диспетчер вызовов.

Вызовы заявок проверять в тестах через `assert_called_once_with`,
`assert_not_called` или точное равенство `call_args_list` списку `call(...)`.
Последний способ проверяет одновременно параметры, порядок и отсутствие
лишних заявок. `assert_has_calls` без проверки общего числа вызовов слабее.

Стрим задавать конечной последовательностью итераторов и исключений через
`side_effect`. Сохранять `TestException` как явный сигнал остановки и проверять
его через `pytest.raises`, чтобы неожиданное завершение цикла не прошло тест.

## Критерии приёмки

Все пять сервисов автоматически получают спецификацию из установленного SDK.
Ошибки имени метода и сигнатуры обнаруживаются тестами. Проверки, ранее
скрытые внутри fake-методов, сохранены как явные ожидания. Порядок продаж и
покупок, запрет отправки в debug, порог и восстановление стрима проверяются
детерминированно. Тесты и линтеры проходят, рабочий код не затронут.
