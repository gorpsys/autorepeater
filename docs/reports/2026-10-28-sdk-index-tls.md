# Восстановление получения SDK, 28 октября 2026

## Установленные причины

Lint и Offline checks коммита `ad97021` завершились на установке зависимостей
с `invalid SDK TLS`, до анализа кода и тестов. Пятый master E2E выпуска
`ab9f8f0` также остановился на setup: выполнено 0 сценариев, деплой не допущен.

Read-only диагностика на GitHub runner:
[40680900878](https://github.com/gorpsys/autorepeater/actions/runs/40680900878).
Python 3.12.15, OpenSSL 3.0.13; прокси в окружении отсутствовал.
Все три TLS-подключения к opensource.tbank.ru дали verify code 20;
все три подключения к pypi.org прошли проверку.

Сертификат opensource.tbank.ru выпущен Russian Trusted Sub CA и действителен
с 22 сентября до 21 декабря 2026 года. Сервер передаёт только один сертификат:
промежуточный CA отсутствует в цепочке. Добавления одного корня из SDK
недостаточно — проверка всё ещё возвращает code 20.

Промежуточный сертификат получен по AIA самого сертификата сервера:
`http://nuc-cdp.voskhod.ru/cdp/subca_ssl_rsa2024.crt`.
Его подпись и срок действия проверены `openssl verify` с корнем
Russian Trusted Root CA из закреплённого SDK wheel. С полной цепочкой
TLS к opensource.tbank.ru проходит с проверкой имени хоста.

SHA-256 полученных байтов промежуточного сертификата:
`6f9d829c8e6712444fce3624658d8788672849c5d5b7b53fd9cf7e83eac4193e`.
SHA-256 отпечаток корня из SDK:
`D2:6D:2D:02:31:B7:C3:9F:92:CC:73:85:12:BA:54:10:35:19:E4:40:5D:68:B5:BD:70:3E:97:88:CA:8E:CF:31`.
Сами сертификаты не добавляются в Git.

После исправления TLS выявлена вторая причина: все 18 ссылок официального
индекса используют upstream-домен `tbank-restore.gitlab.yandexcloud.net`.
Прежний загрузчик правильно отклонял его как неразрешённый origin.
Тот же путь файла через opensource.tbank.ru возвращает HTTP 200 без перехода
на другой домен: файл размером 316190 байт имеет SHA-256
`f0fe22cbed727cecd9971200032d893c19702838b971c08abc2831fe25fa2856`.
Он совпадает и с хешем в официальном индексе, и с закреплённым wheel.

## Узкое исправление

TLS-контекст только загрузчика SDK дополняется корнем из wheel после его
проверки и промежуточным сертификатом с проверкой приведённого SHA-256.
Загрузка промежуточного сертификата ограничена пятью секундами и 32768 байтами,
без прокси и редиректов. Изменение байтов, URL или ошибка проверки фатальны.
Общий deadline worker остаётся прежним. HTTP AIA используется как транспорт
публичных данных с закреплённым хешем, не как источник произвольных доверенных CA.

Только точный upstream-origin из официального индекса нормализуется обратно
на https://opensource.tbank.ru с прежним путём. Сам `official_url` не расширен:
все запросы индекса и wheel остаются на прежнем официальном HTTPS-домене.
Другие origin, HTTP-ссылки, credentials, порты и редиректы не разрешаются.

Системное хранилище CA, зависимости, SDK 1.51.0, правила резерва и approval,
проверки wheel/RECORD/лицензии, торговый код и workflows не меняются.
Проверка публичных CA размещена в транспортном коде SDK; упаковщик использует
те же проверенные байты. Облачный pip получает отдельный бандл, как описано ниже.

## Реальная сборка YC и default-архив

По логу ручного деплоя владельца default-архива из master `ab9f8f0` сборка YC
также упала с `CERTIFICATE_VERIFY_FAILED: unable to get local issuer certificate`
на официальном индексе SDK. PyPI работает. После пяти повторов pip сообщение
`No matching distribution found` скрывает исходный TLS-сбой. Сопутствующий
`failed to send builder logs: [500]` — отдельная ошибка доставки логов.

Владелец проверил четыре локальных тестовых архива из той же базы:

| Кандидат | Результат реальной сборки YC |
| --- | --- |
| build.sh с CA-настройками | TLS-сбой; маркеров запуска пользовательского hook нет |
| PIP_CERT/REQUESTS_CA_BUNDLE/SSL_CERT_FILE в environment версии | Тот же TLS-сбой |
| PIP_CONFIG_FILE в environment версии | Тот же TLS-сбой |
| Исполняемая обёртка pip3.12 в корне ZIP | Успешный деплой; перехват через PATH сработал |

Успешный тестовый ZIP кандидата 04 имел SHA-256
`e3cad3e554a32117f23fe6c880cb9afdfb42b3bc719d8c9586cb1f84677fd12d`.
Это сообщение владельца о реальном ручном деплое, не локальная имитация YC.
Настройки runtime CA из документации YC не гарантируют таких же настроек
dependency builder; три первые проверки не изменили его поведение.

Поэтому default-упаковщик добавляет обёртку pip3.12 с правами 0755 и
cloud-ca/: полный CA-бандл, манифест происхождения/хешей и лицензию certifi.
Mozilla CA получаются из wheel certifi, закреплённого в runtime lock;
существующий загрузчик проверяет размер, SHA-256, метаданные и RECORD.
Корень из SDK и промежуточный сертификат проверяются прежним общим helper.
Файлы сертификатов не попадают в Git, а генерируются только при сборке ZIP.

Обёртка проверяет хеш бандла и вызывает `python3.12 -m pip --cert ...`,
сохраняя все исходные аргументы и код возврата. Экспорт CA-переменных происходит
внутри реально запускаемой обёртки, до pip, и не зависит от environment версии.
Маркеры AUTOREPEATER_PIP_TLS показывают ENTER, BUNDLE_OK и EXEC_PIP.
Системный CA-store не меняется; отключений проверки TLS нет. Default сохраняет
T-Bank extra-index, исходные requirements и их хеши; SDK wheel в ZIP отсутствует.
Лицензия certifi включается рядом с производным бандлом. Vendored/offline и
workflows не меняются. Ошибка подготовки CA не заменяет прежний готовый ZIP.

## Проверка инструкции банка

[Страница Python SDK](https://developer.tbank.ru/invest/sdk/python_sdk/faq_python)
на дату проверки рекомендует:

```text
pip install t-tech-investments --index-url https://opensource.tbank.ru/api/v4/projects/238/packages/pypi/simple
```

Адрес индекса актуален и отвечает. Однако страница не описывает наблюдаемые
проблемы цепочки CA и upstream-ссылок; эта команда сама по себе не доказывает
работоспособность установки в чистом Ubuntu runner.
