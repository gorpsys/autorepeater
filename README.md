# autorepeater

Приводит счёт назначения в Т-Инвестициях к портфелю другого счёта или к цели,
рассчитанной по JSON-конфигу. Состав стратегий определяется конфигами,
а не отдельным Python-кодом для каждого имени.

## Запуск

```bash
pip install -r requirements.txt
# INVEST_TOKEN передаётся через окружение
python main.py --algoritm INDEX -s IMOEX -d <id_назначения> --debug
python main.py --algoritm ACCOUNT -s <номер_источника> -d <id_назначения> --debug
```

`--debug` рассчитывает действия без отправки заявок; без него включена торговля.
Обязательны `--algoritm` (именно такое написание) и `-s`/`--src`.
Имя алгоритма выбирается из реестра; источник трактует только этот алгоритм.
Для ACCOUNT это строка ASCII-цифр с сохранением ведущих нулей, для INDEX это
точное поле `name` в JSON. Цифровое имя JSON допустимо, в том числе `"00123"`;
оно не переключает INDEX на счёт. Имена конфигов могут совпадать с именами
алгоритмов. Регистр и пробелы не нормализуются. Пустой, неизвестный или
неподходящий выбранному алгоритму источник отклоняется до чтения токена и SDK.

Резерв берётся из `reserve` выбранного конфига. Для повторения счёта без
конфига исходное значение равно 0.01 (1%). Явный `-r`/`--reserve` переопределяет
резерв только на этот запуск, в том числе `-r 0` отключает его.
Каждая стратегия обязана предоставить конечный Decimal `default_reserve`
в `[0, 1)`. CLI сохраняет диапазон переопределения `[0, 1]`, включая `-r 1`;
резерв JSON и калибратора остаётся в `[0, 1)`. Bool, неконечные и отрицательные
значения недопустимы. Движок получает резерв из контракта стратегии.
`-t`/`--threshold` задаёт минимальный объём синхронизации, по умолчанию 0.004.
Он не связан с ограничением ошибки веса `max_lot_weight_error`.
В подсказке CLI для threshold пока указано старое значение; рабочая константа
находится в `constants.py`.

## Загрузка конфигов

Все нескрытые `*.json` непосредственно из `autorepeater/configs/` загружаются
по полю `name`. Имя файла не влияет на выбор. Вложенные каталоги не читаются.
Чтобы добавить вариант стратегии, добавьте полный конфиг с уникальным именем;
регистрация в Python не нужна. Пример исходной базы:
[imoex.json](autorepeater/configs/imoex.json).

`INDEX_CONFIG_DIR` заменяет каталог целиком. Совместимый `IMOEX_CONFIG_PATH`
выбирает единственный файл вместо каталога, тоже по его `name`.
Одновременно задавать обе переменные нельзя. Относительные пути считаются
от рабочего каталога; встроенный путь считается относительно Python-модуля.
Пустой каталог, неверный путь и конфликт переменных вызывают ошибку внутри
INDEX без подстановки встроенного конфига или другого алгоритма.

При выборе INDEX каждый файл читается и проверяется независимо один раз.
Ошибка чужого файла или дубликат чужого имени даёт предупреждение с путём
и причиной, сохраняя запуск однозначного исправного источника. Ошибка выбранного
файла, дубликат выбранного имени или отсутствие имени останавливают запуск
до SDK. Файл с читаемым `name` и неверным телом участвует в проверке дубликатов.
Из синтаксически повреждённого JSON имя не восстанавливается; такой файл
получает предупреждение, а при отсутствии выбранного имени его путь входит
в ошибку выбора. Единственный исправный сосед не заменяет запрошенный источник.
`load_index_configs()` остаётся отдельной строгой проверкой всего набора.

Импорт модулей не читает конфиги. ACCOUNT и независимые алгоритмы не читают
индексные файлы и настройки путей. Подготовленный конфиг фиксируется на запуск;
следующий запуск увидит изменения, долгоживущий процесс нужно перезапустить.

## Контракт и адаптер

CLI и облако вызывают `prepare_strategy(algoritm, src)` ровно один раз до
чтения токена. Результат `PreparedStrategy` хранит фабрику, непрозрачные
подготовленные данные и подпись источника. Runner принимает этот результат,
вызывает `create_strategy(prepared)` и проверяет контракт до открытия Client.
Фабрика не повторяет подготовку, чтение файлов или предупреждения. Прямой запуск:

```python
from autorepeater.runner import Runner
from autorepeater.strategies import prepare_strategy

prepared = prepare_strategy('INDEX', 'IMOEX')
Runner(token=token, prepared_strategy=prepared, dst=destination).run_sync()
```

Стратегия предоставляет обязательный `default_reserve` и три метода:

```python
strategy.load_snapshot(data)                  # свежий снимок
strategy.build_target(snapshot, budget)       # TargetPortfolio, чистый расчёт
strategy.events(data, dst_account_id)          # ленивый Iterable[bool]
```

`budget` уже очищен от резерва; снимок локален одному пересчёту и непрозрачен
движку. Общий структурный Protocol `Strategy` не требует наследования.
`validate_strategy` проверяет вызываемые методы и резерв после фабрики и при
прямом создании движка, не начинает чтение событий. `True` означает пересчёт,
`False` пропуск. Рабочий поток может оставаться открытым неограниченно.

`TargetPortfolio` содержит словари UID → конечный Decimal: `quantities` в штуках,
`prices` в деньгах за штуку. Ключи количеств непустые строковые UID; каждому
нужна цена, даже при нулевом количестве. Отрицательные/дробные количества
и конечные неположительные цены допустимы общему контракту; INDEX требует
положительные котировки. Лишние цены игнорируются. Цель проверяется целиком
до расчёта заявок, включая debug, без молчаливого исправления значений.

`StrategyData` в `strategy_data.py` предоставляет только чтение:
`get_portfolio`, `find_instruments`, `get_instrument`, `get_last_prices`,
`position_events`. Его собственные DTO не содержат SDK-объектов или enum SDK.
`PortfolioSnapshot` сохраняет порядок `PortfolioEntry`; количество измеряется
в штуках, цена в деньгах за штуку, оба значения Decimal. `InstrumentMatch` содержит
краткие метаданные поиска без валюты и лотности; `InstrumentInfo` добавляет
лотность и валюту после отдельного UID-запроса. `PriceQuote` хранит цену и время,
`PositionEvent` упорядоченные блокировки и диагностический текст. Собственные
`InstrumentType` различают акции, фонды, валюты и прочие инструменты.

Runner собирает `TInvestStrategyData(client)` рядом с Client и передаёт
`AutoRepeater(client, strategy, data)`. Адаптер переводит units/nano в Decimal,
SDK-ответы в собственные модели и сохраняет порядок и дубликаты. Он не определяет
цель и не торгует. Стратегии используют только порт и общие модели; исполнитель
продолжает использовать SDK для назначения, статусов и заявок. Reporting имеет
отдельный путь собственных моделей без повторного чтения портфеля.

Ошибки конфигурации и данных имеют тип `ValueError`, включая
`UnsupportedSourceError` при ошибке источника. Отсутствующие/ошибочные числа
адаптера указывают поле и UID; правила положительной цены, лотности и совпадения
метаданных проверяет INDEX. `ValueError` завершает вызов без переподписки и без
заявок текущего ошибочного пересчёта. Транспортный `RequestError` адаптер переводит
в `DataAccessError`, включая открытие подписки и чтение следующего события.
Локальный цикл восстанавливается после `DataAccessError` и SDK `RequestError`
исполнителя; `run_sync` пробрасывает ошибки. Ошибки программирования не маскируются.

Для нового алгоритма добавьте плоский модуль и одну регистрацию в `strategies.py`:

```python
register_algorithm('NAME', AlgorithmDefinition(prepare_source, create))
```

`AlgorithmDefinition` находится в `strategy_contract.py`. `prepare_source(src)`
проверяет собственный формат источника без SDK и создания стратегии;
`create(prepared_source)` создаёт стратегию без I/O. Имя регистрации непустое,
без пробелов, точное; повторная регистрация запрещена. Исполнитель, Runner,
CLI и облако не требуют изменений. Новый JSON для прежнего алгоритма требует
только уникального `name`, без регистрации. Тесты стратегии используют autospec
порта и собственные DTO, тесты адаптера используют autospec SDK и явные SDK DTO.

## Поля конфигурации

Все десятичные значения задаются **строками** и обрабатываются через `Decimal`
с точностью 28 знаков. JSON-числа, bool, NaN и Infinity недопустимы.
Доля `"0.0005"` означает **0.05%**, `"0.01"` означает **1%**,
`"0.05"` означает **5%**. Исключение по единицам: `reference_weight`
хранит уже проценты, поэтому `"0.25"` означает 0.25%, а не 25%.

Фрагмент IMOEX с одной записью для объяснения схемы, не замена полного состава:

```json
{
  "name": "IMOEX",
  "reserve": "0.01",
  "max_lot_weight_error": "0.05",
  "min_position_value": "3000",
  "instruments": [{
    "ticker": "AFKS",
    "effective_quantity": "1958950000",
    "free_float": "0.29",
    "weight_limit": "0.7",
    "reference_price": "7.079",
    "reference_weight": "0.25",
    "reference_index_capitalization": "13867407050"
  }]
}
```

### Параметры стратегии

| Поле | Формат и ограничения | Назначение и влияние |
|---|---|---|
| `name` | Обязательная непустая строка без пробельных символов, ASCII-цифры допустимы | Имя для CLI `--algoritm INDEX -s` и облачного `algoritm=INDEX&src=...`. Не меняет арифметику. Уникально во всём наборе конфигов; независимо от имён алгоритмов. |
| `reserve` | Decimal-строка в `[0, 1)` | Доля полной стоимости назначения, оставляемая вне бюджета покупок для комиссий и округлений. Чем выше, тем меньше бюджет. При отсутствии используется `"0.01"` для совместимости; в новых конфигах рекомендуется задавать явно. |
| `min_position_value` | Decimal-строка, не меньше 0; по умолчанию `"0"` | Минимальная идеальная стоимость бумаги по весу полного состава **до округления и перенормализации**. Первая бумага ниже минимума и весь хвост исключаются. 0 отключает фильтр. Фактическая стоимость после округления может оказаться ниже минимума. Для исходного состава из одного тикера игнорируется. |
| `max_lot_weight_error` | Обязательная Decimal-строка в `[0, 1)` | Допустимая относительная ошибка доли после распределения лотов. Проверяется только при идеальном количестве меньше одного лота. Не ограничивает ошибку при одном и более идеальных лотах. Порог не задаёт число бумаг в результате. |
| `instruments` | Обязательный непустой массив объектов | Полный исходный состав. Порядок записей не задаёт приоритет: при расчёте бумаги сортируются по текущей индексной капитализации, при равенстве по тикеру. |

Бюджет применяется одинаково для одного и нескольких инструментов:

```text
V = стоимость всех позиций назначения, включая деньги
B = V * (1 - reserve)
```

Например, при V = 154000 и резерве IMOEX 0.01 бюджет B = 152460,
резерв = 1540. При резерве 0.0005 для той же стоимости бюджет = 153923,
резерв = 77. Изменение резерва не меняет теоретические соотношения весов,
но может изменить отбор бумаг и округление лотов. Резерв вычитается один раз;
чистый расчётчик получает уже готовый бюджет. Это запас денег, а не точный
расчёт тарифа брокера: достаточность для комиссии и движения цены не гарантируется.

### Поля инструмента

Все перечисленные поля обязательны. Цены и капитализации должны быть
в согласованной валюте с бюджетом; текущий расчёт ориентирован на рубли.
Специального запрета других валют нет, но конвертации тоже нет.

| Поле | Формат и ограничения | Назначение и влияние |
|---|---|---|
| `ticker` | Непустая строка, уникальная внутри конфига | Точное имя инструмента для поиска в SDK. Не нормализуется. Определяет, какую бумагу включать в цель. |
| `reference_price` | Decimal-строка, цена штуки на дату базы, строго больше 0 | Знаменатель при пересчёте капитализации по свежей цене. При неизменной базовой капитализации увеличение этого поля уменьшает относительный вес бумаги. Это не цена заявки. |
| `reference_index_capitalization` | Decimal-строка, денежная сумма, строго больше 0 | Главная исходная величина веса: капитализация бумаги, уже учитывающая индексные коэффициенты на дату базы. Увеличение при остальных неизменных данных повышает её относительный вес. |
| `effective_quantity` | Decimal-строка, эффективное количество штук, не меньше 0 | Справочное количество из исходной базы с уже учтёнными корректировками. В текущем коде не участвует в расчёте. Ноль допустим, например когда значение неизвестно; он не исключает бумагу. Это не целевое количество на счёте. |
| `free_float` | Decimal-строка в `(0, 1]` | Справочная доля бумаг в свободном обращении на дату базы. Она уже учтена в индексной капитализации; повторно не умножается. Само изменение этого поля не меняет цель. |
| `weight_limit` | Decimal-строка в `(0, 1]` | Справочный ограничивающий коэффициент из базы индекса. Это не максимальная доля бумаги в вашем портфеле. Уже учтён в капитализации; сам по себе не пересчитывает и не ограничивает текущий вес. |
| `reference_weight` | Decimal-строка в процентах `[0, 100]` | Справочный округлённый вес на дату базы для сверки. Не используется как фиксированный целевой вес. Сумма этих процентов не обязана быть ровно 100. |

Важно: справочные поля валидируются и сохраняются, но **источником расчёта
служат капитализация и базовая цена**, а не произведение всех полей JSON.
Например, у AFKS эффективное количество 1958950000 и базовая цена 7.079
дают 13867407050, уже записанные в `reference_index_capitalization`.
Дополнительно умножать эту сумму на `free_float=0.29` и `weight_limit=0.7`
нельзя: коэффициенты будут учтены повторно.

## Расчёт соотношений

Для каждого тикера SDK предоставляет текущую цену штуки P и размер лота L.
Конфиг задаёт базовую цену P0 и индексную капитализацию C0:

```text
C[i] = C0[i] * P[i] / P0[i]
w_full[i] = C[i] / sum(C по всему составу)
```

При ценах из базы C = C0. Отношение долей двух бумаг равно C[i] / C[j];
оно не зависит от размера счёта и резерва до отбора и округления.
Например, по базе IMOEX капитализации AFKS и SBER равны 13867407050 и
674527989054.97: соотношение их долей примерно 0.02056 к 1.
Если цена AFKS вырастет на 10% при остальных неизменных ценах, его C станет
15254147755, а соотношение с SBER тоже вырастет на 10%.
Сама нормализованная доля AFKS вырастет немного меньше, поскольку увеличится
и общая капитализация в знаменателе.

На базовых ценах полного IMOEX сумма C равна 5589472902018.81,
доля AFKS примерно 0.2481%. Справочное `reference_weight="0.25"` округлено;
расчёт использует 0.2481%, а не 0.25%. При бюджете 152460 идеальная стоимость
этой позиции примерно 378.25: ниже `min_position_value="3000"`.
Следовательно, она не войдёт в начальный отобранный состав.

### Отбор и лоты

1. Весь состав сортируется по убыванию C, при равенстве по тикеру.
   Один раз выбирается начальный непрерывный список с
   `B * w_full[i] >= min_position_value`, до первой бумаги ниже минимума.
   Исключается и весь оставшийся хвост. Равенство включается.
2. Веса оставшегося списка перенормализуются:
   `w[i] = C[i] / sum(C оставшихся)`. Если оставлено 80% капитализации,
   бумага с полным весом 10% получит целевой вес 10/80 = 12.5%.
3. Стоимость лота `K[i] = P[i] * L[i]`, идеальные лоты
   `n[i] = B * w[i] / K[i]`. Выбирается ближайшее целое N,
   половины округляются к чётному. Например, при целевой сумме 1000
   и стоимости лота 300 выбираются 3 лота: ошибка 10%, у 4 лотов была бы 20%.
4. Если сумма `N[i] * K[i]` превышает B, отменяются округления вверх:
   первыми те, где округление вниз меньше всего увеличит относительную
   ошибку, при равенстве по тикеру. Процесс идёт до попадания в бюджет.
5. Для распределённых лотов вычисляется
   `error[i] = abs(N[i] * K[i] / B - w[i]) / w[i]`.
   Нулевые N всегда означают отказ. Ошибка выше `max_lot_weight_error`
   означает отказ только при `n[i] < 1`; при `n[i] >= 1` порог не проверяется.
   Проверка использует идеальные лоты, а не округлённые.
6. При первом отказе исключается эта бумага и весь хвост. Оставшиеся веса
   перенормализуются и лоты считаются заново. Предварительный денежный минимум
   повторно не применяется, исключённые бумаги внутри расчёта не возвращаются.

Например, при идеальных 0.8 лота и выделенном одном лоте относительная
ошибка 25%, а не 0.2 процентного пункта. Порог 0.05 её не допускает.
Если бюджетная коррекция вместо этого оставит ноль лотов, позиция всё равно
будет исключена. При идеальных 1.8 лота ограничение ошибки уже не действует.
Ошибка относится к перенормализованной цели, не к исходному полному индексу.

Результат содержит количества **штук** `N * L`, а не лоты и не заявки.
Стоимость цели по ценам снимка не превышает B. Остаток от округления
остаётся деньгами сверх выделенного резерва. Следующая синхронизация заново
берёт весь состав; конкретное число бумаг и его монотонный рост с бюджетом
не гарантируются. Расчёт воспроизводит веса фиксированной базы, не значение
биржевого индекса с делителем.

### Один инструмент

Если в исходном конфиге один тикер, его вес равен 100%, резерв берётся из
того же поля `reserve`. Минимум позиции и фильтр ошибки веса не мешают
покупке: целевое число лотов равно `floor(B / (P * L))`.
Уже имеющиеся бумаги учитываются при расчёте разницы. Если B не хватает
на один лот, цель пустая и торговля пропускается без ликвидации портфеля.
Это правило определяется исходным конфигом, не сокращением многокомпонентного
состава до одной бумаги. Положительные справочные P0 и C0 здесь нормализуются
в единичный вес; актуальная цена и лотность всё равно берутся из SDK.

## Данные и ограничения

Тикер разрешается строго: акции `share` в режиме `TQBR`, фонды `etf`
в `TQTF`. Среди основных режимов требуется одно точное совпадение,
без fallback на другие площадки. `api_trade_available_flag` не фильтрует
выбор. Метаданные по UID повторно подтверждают UID, тикер, тип и режим.
Неоднозначность, отсутствие цены, неположительная цена или лотность
прерывают расчёт, не превращаются в частичную цель. Последняя цена может
относиться к прошлой сессии; её время сохраняется в снимке.

При обновлении базы согласованно меняйте цены, капитализации и справочные
поля. Изменение только `free_float` или `weight_limit` не повлияет на сделки.
Корпоративные действия и обновление состава автоматически не обрабатываются.
Соответствие сохранённого примера IMOEX текущей официальной базе не гарантируется.

Все сравнения выполняются в Decimal без epsilon. На математической границе
точность 28 знаков может изменить включение бумаги; это принятое ограничение.
Веса и бюджет предполагают согласованные валюты. Конвертация и торговля
валютами не реализованы; смешанный валютный портфель может рассчитываться неверно.

Движок рассчитывает продажи, затем покупки, отправляет продажи первыми.
Заявки BESTPRICE отправляются только при нормальном торговом статусе и вне
debug. Цена исполнения не ограничена ценой снимка; даже с резервом брокер
может отклонить заявку из-за комиссии или изменения цены.
Отправка требует `volume > B * threshold`. Существующая оценка `volume`
берёт максимум сумм продаж и покупок по числу лотов и цене штуки, без
множителя лотности. Это отдельное ограничение движка, не правило конфига.

Пустая цель для любой стратегии логируется на уровне IMPORTANT и пропускается
без заявок. Пустая разница при достигнутой непустой цели просто не требует
сделок. Отсутствующий UID в непустой цели означает продажу имеющейся позиции.

## Облако и события

Локальный процесс выполняет первую синхронизацию, затем слушает события.
Для конфигурационных стратегий подписка только на `dst`: пересчёт при наличии
денег или бумаг и отсутствии блокировок во всех позициях. Изменение цены
само по себе пересчёт не запускает, локального таймера нет. После завершения
стрима, `DataAccessError` или SDK `RequestError` движок переподписывается. Повторение счёта сохраняет
свои условия подписки на источник и назначение.

Yandex Cloud Functions использует `handler.handler` и выполняет один `run_sync`
без стрима. Периодичность задаёт внешний таймер. Параметры:

| Параметр | Приоритет источников |
|---|---|
| `algoritm` | query string, иначе `ALGORITM`, затем `INDEX` |
| `src` | query string, иначе `SRC_ACCOUNT`, затем `TMON` только для INDEX |
| `dst` | query string, `DST_ACCOUNT`, `DEFAULT_DST_ACCOUNT` |
| `token` | query string, `INVEST_TOKEN`, совместимый `t_token` |

Присутствующий ключ `algoritm` или `src` имеет приоритет над окружением даже
при пустом, None или пробельном значении: оно отклоняется до чтения токена.
Пустые `ALGORITM` и `SRC_ACCOUNT` также отклоняются, без подстановки значений
по умолчанию. При отсутствии обоих параметров и переменных окружения облако
выбирает конфиг `TMON`: один тикер TMON, резерв 0.05%, максимальное целое число
лотов в бюджете после резерва. Текущая цена и лотность берутся из API.
Для ACCOUNT и других алгоритмов источник необходимо задать явно.
Для выбора конфига задайте `algoritm=INDEX&src=IMOEX` в запросе либо
`ALGORITM=INDEX` и `SRC_ACCOUNT=IMOEX` в окружении; для счёта задайте ACCOUNT
и номер источника. Один `src` без алгоритма в облаке трактуется как имя конфига
INDEX, а не номер счёта. CLI по-прежнему требует оба параметра.
Правила `dst`, токена и формат успешного ответа сохранены.
Облачных параметров reserve/debug нет: используется обязательный резерв стратегии,
токен только для чтения не включает расчёт без торговли.

`make claude-yandex-archive` создаёт `build/yandex-function.zip` с `main.py`, `handler.py`,
`requirements.txt`, модулями `autorepeater/` и всеми нескрытыми
`autorepeater/configs/*.json`. Новые плоские модули и конфиги включаются автоматически.
Тесты, окружения и калибровочная утилита не включаются. Изолированный тест архива
проверяет CLI/облако, два разных конфига, резервы и предупреждения без сети и торговли.
Поместите конфиги в этот каталог до сборки; внешний `INDEX_CONFIG_DIR`
автоматически не копируется.

## Калибровка

Утилита получает только инструменты и котировки, не читает счета и не отправляет
заявки. Токен передаётся через `READ_ONLY_INVEST_TOKEN`, в отчёт не попадает.

```bash
python -m scripts.check_imoex_strategy --src IMOEX --sandbox \
  --gross-values 100000 154000 300000 --budgets 154000 \
  --thresholds 0.02 0.05 0.1 --output /tmp/index-calibration.json
```

`--sandbox` выбирает sandbox API только для утилиты; по умолчанию production.
Алгоритм утилиты фиксирован INDEX, флаг `algoritm` ей не нужен. Явный `--src`
использует тот же изолированный выбор JSON. Без `--src` допустим ровно один
кандидат без ошибок и дубликатов; иначе нужно точное имя. Цифровое `name`
допустимо и здесь означает конфиг, а не брокерский счёт.

`--gross-values` задаёт полную стоимость (по умолчанию 100000, 154000, 300000).
Из неё вычитается резерв конфига; явный `--reserve` переопределяет его, включая 0.
`--budgets` задаёт уже готовые бюджеты без повторного резерва (по умолчанию 154000).
`--thresholds` сравнивает ограничения ошибки веса (по умолчанию 0.03, 0.05, 0.1),
не threshold отправки заявок. Стоимости положительны, резерв и пороги в `[0, 1)`.
Все значения конечны. `--output` необязателен: JSON также выводится в лог.

Отчёт содержит конфиг, время получения снимка, UID, валюту, цену, лотность
и время котировки. Для каждого сценария показаны фактический резерв, бюджет,
стоимость цели, остаток, начальный состав после минимума, итоговые лоты,
полные и перенормализованные веса и причины исключения. `cash` не включает
резерв. `min_position_value` показывает значение конфига, игнорируемое
для единственного инструмента. По отчёту можно воспроизвести расчёт без сети.

Исторический пример IMOEX от 29.09.2026 и независимые ожидания сохранены в
[test/data/imoex_snapshot.json](test/data/imoex_snapshot.json) и
[test/data/imoex_prefix_expectations.json](test/data/imoex_prefix_expectations.json).
Это зафиксированные данные для регрессии, не актуальные котировки и не
гарантия состава результата. Проверка: `pytest -k index_public_snapshot`.
