# autorepeater

Автоповторитель сделок для Т-Инвестиций. Программа рассчитывает, какие бумаги
и в каком количестве должны быть на выбранном счёте, затем покупает недостающие
и, если стратегия разрешает, продаёт лишние. Для обращения к брокеру используется
`t-tech-investments`.

Счёт, который программа приводит к цели, называется **счётом назначения**.
Способ расчёта цели выбирается алгоритмом:

| Алгоритм | Когда выбирать |
| --- | --- |
| ACCOUNT | Нужно повторять пропорции бумаг другого счёта с учётом своего бюджета |
| INDEX | Нужно следовать составу из JSON-конфига с учётом текущих цен и размера лотов |
| COMPOSITE | Нужно распределять деньги между несколькими стратегиями; каждая строит свою цель |

Стратегия решает, разрешены ли продажи. Исполнитель проверяет реальные деньги,
принадлежность бумаг, размер лотов и собственные немаржинальные лимиты API.
Сделка отправляется только после проверок исполнителя,
даже если стратегия её разрешает.
Рабочий режим использует рублёвые оценки и только собственные деньги и бумаги,
без заёмных средств. Брокер дополнительно ограничивает доступные деньги и число лотов.

Сначала можно проверить [запуск](#запуск) и [конфиги](#конфиги).
[Политика и деньги](#политика-и-деньги) описывает расчёты,
[API и слои](#api-и-слои) — устройство программы.
Проверка своего конфига на виртуальных деньгах описана в
[инструкции песочницы](docs/sandbox-manual.md).
Разработка, тесты, калибровки, сборка и деплой описаны в
[техническом README](scripts/README.md), версии — в [CHANGELOG](CHANGELOG.md).

## Ответственность и выбор стратегии

Все риски инвестиций и использования программы несёт пользователь.
Стратегии, составы бумаг, параметры и примеры в этом репозитории
не являются индивидуальными инвестиционными рекомендациями.
Автор — такой же пользователь, без большого опыта инвестиций и без
специального финансового образования. Доходность и сохранность капитала
не гарантируются; автор не отвечает за выбор пользователя и его результаты.

`IMOEX`, `OBLG`, `GOLD` и `BALANCED` в параметре `--src` — имена конфигов,
а не встроенные команды или оценка надёжности вложений. Для своего конфига
можно выбрать другое имя в поле `name`, соблюдая [правила](#общие-правила).
Переименование не меняет состав бумаг; его определяют поля конфига.
Названия алгоритмов ACCOUNT, INDEX и COMPOSITE при этом фиксированы.
Выбирайте состав и распределение денег по собственным предпочтениям,
пониманию рисков и условиям брокера, не по названию примера.

## Запуск

### Локальная установка

Работа проверена на Python 3.12 и Linux x86_64. На других конфигурациях
она возможна, но не проверена и не гарантируется. Проверить конфигурацию:

```bash
python3.12 -c 'import platform; print(platform.system(), platform.machine(), platform.python_version())'
```

Для проверенного варианта ожидаются `Linux x86_64 3.12.x`.
Нужны Python с venv/pip, Make, Git и доступ к PyPI.
Для варианта клонирования ниже также нужен GitHub CLI.
Дополнительные ограничения совместимости пакетов указаны
в [техническом README](scripts/README.md#окружение-и-проверки).
Проверенная установка по runtime lock рассчитана именно на этот профиль.
Для приватного репозитория нужен доступ вашей учётной записи GitHub.
Если планируете хранить личные конфиги в GitHub, используйте
[свой форк](#перенос-своего-конфига-в-облако) и клонируйте его вместо
`gorpsys/autorepeater` в командах ниже.
Если GitHub CLI уже авторизован, выполните:

```bash
gh repo clone gorpsys/autorepeater
cd autorepeater
make setup VENV_PYTHON=python3.12
```

Вместо первой команды можно использовать HTTPS с настроенной GitHub-аутентификацией:

```bash
git clone https://github.com/gorpsys/autorepeater.git
```

`make setup` создаёт окружение `.venv` и устанавливает зависимости приложения
и инструменты проверок. Последующие команды выполняются из каталога проекта
`autorepeater`; активировать окружение не нужно, если используется `.venv/bin/python`.

Установщик проверяет версии, SHA-256 и состав файлов по полному
[runtime lock](runtime-lock.json). SDK `t-tech-investments==1.51.0` берётся
из официального индекса T-Bank. Если ошибка доступа к индексу допускает
переключение на [резервный wheel](vendor/t-tech-investments/README.md),
установщик использует его и выводит WARNING с причиной переключения.
Остальные зависимости скачиваются из PyPI.
Расхождение хешей официального и резервного SDK требует отдельного одобрения.
Лицензия SDK — [Apache-2.0](vendor/t-tech-investments/LICENSE);
ограничения установки, другие лицензии и команды описаны в
[техническом README](scripts/README.md#окружение-и-проверки).

### Токен и счёт

Порядок выпуска и виды токенов описаны в официальной
[документации Т-Инвестиций](https://developer.tbank.ru/invest/intro/intro/token).
Для чтения данных используйте read-only, для реальных сделок нужен full-access
с доступом к выбранным счетам; для песочницы нужен отдельный sandbox-токен.
Для ACCOUNT токен должен видеть и источник, и назначение, не только один счёт.
Программе не требуются права на перевод средств между счетами.

Общие правила: выдавайте только необходимые права, не публикуйте токен
и не добавляйте его в Git, не передавайте его в чатах или логах.
Храните его в защищённом хранилище или файле с ограниченным доступом.
При утечке отзовите токен в Т-Инвестициях и выпустите новый.
Для локального запуска передайте его в `INVEST_TOKEN`; в Bash скрытый ввод
не записывает значение токена в историю команд:

```bash
read -r -s -p 'Токен Т-Инвестиций: ' INVEST_TOKEN
export INVEST_TOKEN
printf '\n'
```

Идентификатор счёта можно посмотреть в адресной строке веб-версии Т-Инвестиций.
Откройте страницу нужного счёта: адрес имеет вид
`https://www.tbank.ru/invest/portfolio/<идентификатор_счёта>/`.
Часть после `portfolio/` передаётся в `-d` для счёта назначения
или в `source_account_id` для источника ACCOUNT.

Программа управляет счётом **целиком**, включая находящиеся на нём деньги
и бумаги. Чтобы доверить ей только 10 000 рублей, заведите отдельный счёт,
пополните его на эту сумму и укажите его ID. Отдельного ограничения
«использовать только часть этого счёта» нет; резерв не защищает остальные
бумаги, купленные вручную, от разрешённой стратегии продажи.

### Первый запуск

Замените `<id_назначения>` своим значением и выполните только одну команду
выбранного алгоритма. INDEX и COMPOSITE ниже используют встроенные конфиги.
Для ACCOUNT сначала подготовьте [свой конфиг MY_ACCOUNT](#свой-конфиг)
с идентификатором своего исходного счёта:

```bash
.venv/bin/python main.py --algoritm INDEX -s IMOEX -d <id_назначения> --debug
.venv/bin/python main.py --algoritm ACCOUNT -s MY_ACCOUNT -d <id_назначения> --debug
.venv/bin/python main.py --algoritm COMPOSITE -s BALANCED -d <id_назначения> --debug
```

| Параметр | Значение |
| --- | --- |
| `--algoritm` | Алгоритм: ACCOUNT, INDEX или COMPOSITE. Параметр обязателен; написание именно `algoritm`. |
| `-s` / `--src` | Точное поле `name` в JSON-конфиге выбранного алгоритма. Обязательно. |
| `-d` | Идентификатор счёта назначения |
| `--debug` | Прочитать API, построить и проверить планы, но не отправлять заявки |
| `--version` / `-v` | Вывести версию программы и завершиться; остальные параметры и токен не нужны |

Версию установленной копии можно проверить отдельно:

```bash
.venv/bin/python main.py --version
```

Сначала проверьте результат по [порядку ниже](#проверка-перед-реальными-сделками).
Чтобы выполнять реальные сделки, запустите ту же команду без `--debug`.
Резерв денег и допуски отклонения задаются в конфиге стратегии.
Для проверки без заявок используйте локальный `--debug`;
облачный запуск такого режима не поддерживает.

`src` всегда выбирает конфиг, даже у ACCOUNT. Настоящий идентификатор исходного
счёта ACCOUNT находится в поле `source_account_id` этого конфига.
Например, если `name = "COPY"`, а `source_account_id = "2193248994"`,
в команду передаётся `-s COPY`, а исходный счёт программа читает из конфига.
Имя конфига может состоять из цифр, содержать ведущие нули или совпадать
с названием алгоритма. Регистр и пробелы не исправляются автоматически.
Ошибка подготовки завершает запуск до чтения токена и создания клиента SDK.

### Выбор прямой валютной пары

Для оценки иностранной валюты и её обмена используется один явно выбранный
прямой маршрут в RUB. Если каталог содержит несколько таких пар, задайте
переменную окружения `FX_PAIR_UIDS`: JSON-объект из кода валюты в UID пары.
Например, замените `UID-CNYRUB-TOM` на проверенный UID нужной пары CNY/RUB:

```bash
export FX_PAIR_UIDS='{"cny":"UID-CNYRUB-TOM"}'
```

Настройка действует для CLI, одного локального прохода и облачной функции
(в облаке задаётся переменной окружения функции). Коды валют нечувствительны
к регистру; повторяющиеся ключи валют запрещены, UID передаётся точно.
Выбранная пара проверяется по полной
валютной идентичности, а торговые разрешения и свои лимиты проверяются отдельно.
Если выбранный UID отсутствует или не соответствует валюте, проход отклоняется.
Порядок каталога и текущая доступность торгов не меняют выбор пары.

Без настройки сохраняется автоматический выбор единственного прямого маршрута;
при нескольких парах проход отклоняется. RUB не требует FX-пары или такой
настройки, существующие RUB-конфиги работают без изменений.
Для программного вызова используйте `RunnerParams(debug=False,
fx_pair_uids={"cny": "UID-CNYRUB-TOM"})`. Явно переданные `RunnerParams`
полностью определяют выбор, включая пустой mapping; для загрузки окружения
служит `RunnerParams.from_environment(debug=False)`.

Для стаканов бумаг и FX-пар действует общий предел возраста рыночных данных:
180 секунд включительно. Время получения ответа не заменяет время стакана;
просроченные, неизвестные или будущие timestamps отклоняются. Перед исполнением
курс снова проверяется на свежесть.

Денежный резерв каждой конечной стратегии делится между валютами по целевой
стоимости бумаг в рублях. Половина доли для иностранных бумаг остаётся в RUB
на комиссию обмена, половина — в валюте бумаги на её комиссию. Общий резерв
не увеличивается, нераспределённые деньги COMPOSITE в него не входят.
Уже имеющаяся валюта используется прежде покупки новой. Обмен выполняется
только при нехватке денег для покупки бумаг, не ради восстановления резерва.
При покупке валюты учитывается её доля резерва, при уже необходимом обратном
обмене — RUB-доля. Свои остатки вычитаются до округления к лоту пары.
Комиссии расходуют тот же резерв, отдельный запас сверх него не добавляется.

### Проверка перед реальными сделками

`--debug` читает реальные данные API и проверяет планы, но не отправляет заявки.
Локальная программа сначала показывает доступные счета и портфели,
затем рассчитывает выбранную стратегию; после этого остаётся ждать событий.
Она не обязана завершиться после первого отчёта. Для окончания проверки
можно остановить этот запуск через Ctrl+C.

`uid` в торговом плане обозначает **бумагу**, а не счёт. Он используется
и на реальном счёте, и в песочнице. Идентификатор счёта API принимает
как строку: для реального счёта используйте номер из адреса страницы,
описанный выше; в песочнице — ID созданного виртуального счёта.

Для INDEX, в том числе внутри COMPOSITE, соответствие тикера и UID видно
в строке `Selected index instrument: <тикер> uid=<UID> class_code=<код>`.
Не путайте её с `Target position`: первая помогает узнать бумагу,
вторая показывает целевое количество и стоимость.
При отображении списка портфелей программа также ищет название и тикер
бумаги по UID.
Отдельной команды поиска в программе нет; произвольный UID можно проверить
через метод `GetInstrumentBy` с типом идентификатора UID в
[API Т-Инвестиций](https://developer.tbank.ru/invest/services/instruments/methods).

| Строка отчёта | Что проверить |
| --- | --- |
| Имя счёта и ID в списке портфелей | Переданный в `-d` ID относится к нужному счёту, а для ACCOUNT в конфиге указан правильный источник |
| `Target position` | Целевое количество каждой бумаги (`quantity`), расчётную цену (`price`) и стоимость (`estimated_value`); `uid` — идентификатор бумаги в API |
| `Target` | Полный бюджет (`budget`), стоимость целевых бумаг и расчётный остаток (`estimated_cash`) |
| `Policy` | Режим стратегии: покупки (`BUY_ONLY`) или ребалансировка (`REBALANCE`), её причина (`reason`) и резерв (`cash_floor`); отдельное правило продажи бумаг вне стратегии описано ниже |
| `Execution money`, `Rules UID` | Доступные деньги, лотность, ограничения и разрешения брокера |
| `Intent` | Будущие направления (`BUY` — купить, `SELL` — продать) и количество лотов (`lots`) |
| `Execution: debug=True sells=... buys=...` | Число запланированных заявок; в этом режиме они не отправлены |

`estimated_cash` — оценка для целевого состава, не гарантированный остаток
после сделок и комиссий. План покупок может измениться после продажи,
обновления данных и проверки фактически поступивших денег.
`BUY_ONLY` относится к бумагам данной стратегии: бумаги, которые вообще
не входят в цель, могут получить отдельное разрешение продажи.
Поэтому сверяйте сами строки `Intent`, а не только название режима.
`SKIP: no executable orders` означает отсутствие исполнимых заявок сейчас,
а не само по себе подтверждение правильности настройки: проверьте причины
пропуска и блокировок в соседних сообщениях.

Перед разрешением сделок сверяйте ID счёта, состав, бюджет, продажи,
резерв и сообщения WARNING/ERROR. Непонятную продажу или ошибку сначала
разберите; не убирайте `--debug` ради обхода ошибки.
Дополнительно можно проверить свою настройку на виртуальных деньгах
по [инструкции песочницы](docs/sandbox-manual.md).
Успех проверки не гарантирует будущую цену, доступность торгов или доходность.

### Один локальный проход

Вместо постоянно работающего `main.py` можно выполнить один проход
и завершить программу. В каталоге проекта, с уже заданным `INVEST_TOKEN`
реального счёта и путём к своему конфигу, выполните:

```bash
ALGORITM=INDEX SRC_ACCOUNT=MY_INDEX DST_ACCOUNT='<id_назначения>' ONE_SHOT_DEBUG=1 \
  .venv/bin/python - <<'PY'
import os

from autorepeater.runner import Runner, RunnerParams
from autorepeater.strategies import prepare_strategy

debug = {"1": True, "0": False}[os.environ["ONE_SHOT_DEBUG"]]
prepared = prepare_strategy(os.environ["ALGORITM"], os.environ["SRC_ACCOUNT"])
Runner(
    token=os.environ["INVEST_TOKEN"],
    prepared_strategy=prepared,
    dst=os.environ["DST_ACCOUNT"],
    params=RunnerParams.from_environment(debug=debug),
    sandbox=False,
).run_sync()
PY
```

Замените алгоритм, имя конфига и ID назначения своими значениями.
`ONE_SHOT_DEBUG=1` только рассчитывает и проверяет планы.
После проверки замена на `ONE_SHOT_DEBUG=0` **разрешает реальные заявки**.
Это переменная данного примера, не параметр `main.py`.
Разовый проход не выводит общий список портфелей и не ждёт событий;
следующий проход требует нового запуска. Для виртуальных денег используйте
отдельный [пример песочницы](docs/sandbox-manual.md), а не sandbox-токен
в этой production-команде.

## Конфиги

### Общие правила

Числовые значения в JSON записываются **строками**, например `"0.01"`,
а не JSON-числами. Программа читает их как Decimal — десятичные числа.
Допускаются только конечные значения: bool, NaN и Infinity не подходят.
Доля `"0.01"` означает 1%. Исключение — `reference_weight`: оно задаётся
в процентах, поэтому `"10"` означает 10%.

Поле `name` — непустая строка без пробельных символов. Оно не зависит
от имени файла.

### Свой конфиг

Например, создайте отдельный каталог рядом с каталогом проекта и скопируйте
конфиг INDEX из одной бумаги. Пример не является рекомендацией покупать GOLD:

```bash
mkdir -p ../autorepeater-configs/index
cp autorepeater/configs/gold.json ../autorepeater-configs/index/my-index.json
```

Откройте `../autorepeater-configs/index/my-index.json` в редакторе.
Поменяйте `name` на `MY_INDEX`; если выбираете другую бумагу, измените её
`ticker` и проверьте остальные параметры по [описанию INDEX](#index).
Сохраните числовые значения строками. Укажите каталог и имя:

```bash
export INDEX_CONFIG_DIR='../autorepeater-configs/index'
unset IMOEX_CONFIG_PATH
.venv/bin/python main.py --algoritm INDEX -s MY_INDEX -d <id_назначения> --debug
```

`INDEX_CONFIG_DIR` — настройка окружения, а не аргумент `main.py`.
Она заменяет встроенный каталог; его конфиги автоматически не добавляются.
Если нужно выбрать только один файл, вместо DIR задайте PATH:

```bash
unset INDEX_CONFIG_DIR
export IMOEX_CONFIG_PATH='../autorepeater-configs/index/my-index.json'
```

Не оставляйте DIR и PATH одного алгоритма заданными одновременно.

Для ACCOUNT подготовьте отдельную копию:

```bash
mkdir -p ../autorepeater-configs/account
cp autorepeater/configs/account/account.json ../autorepeater-configs/account/my-account.json
```

В редакторе задайте `name=MY_ACCOUNT`, свой `source_account_id` и проверьте
параметры [ACCOUNT](#account), затем выполните:

```bash
unset ACCOUNT_CONFIG_DIR
export ACCOUNT_CONFIG_PATH='../autorepeater-configs/account/my-account.json'
.venv/bin/python main.py --algoritm ACCOUNT -s MY_ACCOUNT -d <id_назначения> --debug
```

Для COMPOSITE можно начать с копии встроенного состава:

```bash
mkdir -p ../autorepeater-configs/composite
cp autorepeater/configs/composite/balanced.json ../autorepeater-configs/composite/my-composite.json
```

В редакторе поменяйте `name` на `MY_COMPOSITE`, проверьте веса и параметры
[COMPOSITE](#composite). Этот пример использует встроенные INDEX-конфиги,
поэтому верните их каталог:

```bash
unset INDEX_CONFIG_DIR IMOEX_CONFIG_PATH
export COMPOSITE_CONFIG_DIR='../autorepeater-configs/composite'
.venv/bin/python main.py --algoritm COMPOSITE -s MY_COMPOSITE -d <id_назначения> --debug
```

Если нужны собственные дочерние стратегии, укажите каталоги их конфигов
по таблице ниже. Значение `src` каждого компонента должно совпадать
с `name` соответствующего конфига INDEX, ACCOUNT или COMPOSITE.
При переименовании дочернего конфига обновите ссылки на него в COMPOSITE.

### Выбор каталогов

| Алгоритм | Встроенный каталог | Как выбрать внешний каталог или файл |
| --- | --- | --- |
| ACCOUNT | autorepeater/configs/account/ | ACCOUNT_CONFIG_DIR либо ACCOUNT_CONFIG_PATH |
| INDEX | autorepeater/configs/ | INDEX_CONFIG_DIR либо IMOEX_CONFIG_PATH |
| COMPOSITE | autorepeater/configs/composite/ | COMPOSITE_CONFIG_DIR |

Для одного алгоритма нельзя одновременно задать DIR и PATH.
Относительный внешний путь считается от текущего рабочего каталога;
встроенный — от расположения модуля. У разных алгоритмов настройки путей независимы.

В каталоге рассматриваются только нескрытые `*.json` непосредственно в нём,
без обхода подкаталогов. Если задан неверный или пустой путь либо набор конфигов,
программа не подставляет встроенный набор.

При подготовке стратегии каждый JSON-конфиг из выбранного набора читается
и проверяется один раз. Если стратегия встречается в дереве несколько раз,
для каждого такого компонента конфиги читаются и проверяются отдельно:

- Если выбранного имени нет, оно повторяется или его документ неверен, запуск останавливается.
- Ошибки документов с другими именами и их дубликаты дают предупреждение с путём.
- Если JSON читается, но его содержимое неверно, читаемое `name` всё равно учитывается при поиске дубликатов.
- Если JSON не разбирается, имя не угадывается по тексту или имени файла.
- `load_index_configs()` проверяет весь набор INDEX, а не только выбранный состав.

### Обновление конфигов

При импорте модулей программа не читает файлы и не обращается к API.
Конфиги загружаются и фиксируются при подготовке стратегии; повторная
подготовка читает их заново, без использования общего кеша.
Чтобы уже работающая программа использовала изменённый конфиг, перезапустите её.
Автоматического обновления состава и обработки корпоративных действий нет.

Корпоративные действия — события вроде дробления акций, изменения их количества
или реорганизации эмитента, которые могут менять справочные данные.
Когда обновлять конфиг, решает пользователь по данным организатора индекса.
Для IMOEX состав обычно пересматривают раз в квартал: сверяйте обновления
и даты вступления в силу на сайте Московской биржи, учитывая также внеплановые
изменения. Для другого индекса ориентируйтесь на его собственный календарь.
После обновления состава и коэффициентов проверьте конфиг с `--debug`
и перезапустите программу; автоматического сопровождения этих изменений нет.

### ACCOUNT

ACCOUNT может читать только ваши счета, доступные вашему токену.
По идентификатору чужого счёта повторять его портфель нельзя.
Один из вариантов применения: подключить автоследование на свой счёт
с минимально необходимой суммой, а на другом своём счёте с основным капиталом
повторять первый через ACCOUNT. Это может сократить комиссию за автоследование
на основном капитале, но зависит от тарифа и условий брокера.
Комиссии за сделки остаются; совпадение состава, времени сделок
и доходности не гарантируется.

Пример встроенного [account.json](autorepeater/configs/account/account.json):

```json
{
  "name": "2193248994",
  "source_account_id": "2193248994",
  "reserve": "0.01",
  "allocation_drift_limit": "0.0092"
}
```

Все четыре поля обязательны. Дополнительные поля загрузчик не использует.

| Поле | Что означает |
| --- | --- |
| `name` | Имя, которое передаётся в `--src` |
| `source_account_id` | Идентификатор исходного счёта из API; может отличаться от `name` |
| `reserve` | Доля бюджета, отводимая под расчётный остаток денег; ограничивает покупки |
| `allocation_drift_limit` | Допуск отклонения состава, после которого разрешены внутренние продажи |

`source_account_id` — непустая строка без пробелов и других пробельных символов.
Подходят числовые строки и UUID песочницы. Идентификатор передаётся API
без преобразований; ведущие нули и регистр сохраняются.
Резерв и допуск находятся в диапазоне `[0, 1)`: ноль включён, единица исключена.
Встроенный допуск — 0.0092.

ACCOUNT берёт бумаги исходного счёта, исключая его валютные позиции.
Стоимость каждой исходной позиции отдельно приводится к точности nano
(девять знаков после запятой), затем стоимости складываются.

Количество каждой бумаги в цели считается так:

```text
инвестируемый бюджет = budget * (1 - reserve)
коэффициент масштаба = инвестируемый бюджет / total_src
quantity = source_quantity * коэффициент масштаба
```

Здесь `budget` — выделенный стратегии полный бюджет,
`total_src` — общая стоимость бумаг источника,
`source_quantity` — количество бумаги в источнике.
Цель выражается в штуках и может быть дробной.
При покупке количество не округляется вверх сверх цели.

### INDEX

INDEX получает состав и параметры расчёта из конфига.

#### Тикеры и справочные данные

Тикер — короткое биржевое обозначение бумаги, например `SBER`.
Найдите нужную бумагу в каталоге Т-Инвестиций и откройте её страницу:
тикер указан рядом с названием; например,
[страница Сбербанка](https://www.tbank.ru/invest/stocks/SBER/) содержит `SBER`.
Уточняйте вид бумаги, а не только название компании: обычные
и привилегированные акции могут иметь разные тикеры.

Индекс — показатель выбранной корзины бумаг. Индексная капитализация —
стоимость учитываемой в индексе части бумаг эмитента; по её доле программа
рассчитывает вес бумаги. `free_float` — доля акций в свободном обращении;
`weight_limit` — ограничительный весовой коэффициент индекса,
а не максимальная сумма вашей покупки. Эти справочные значения уже учтены
в сохранённой индексной капитализации; повторно применять их нельзя.

Справочные данные встроенного IMOEX взяты с сайта
[Московской биржи](https://www.moex.com/RU/INDEX/IMOEX/ABOUT): состав,
база расчёта, капитализации и коэффициенты соответствующего снимка.
Это сохранённые данные, а не автоматически обновляемая база.
Для других индексов ищите состав и методику на сайте соответствующей биржи
или организатора индекса. Значения одного индекса нельзя автоматически
переносить на другой. Подробности о тикерах, индексах и коэффициентах
изучайте по специализированной литературе и официальным методикам.
Выбор бумаг и параметров остаётся за пользователем; автор за него не отвечает.

#### Параметры

| Поле | Значение и ограничения |
| --- | --- |
| `name` | Непустое точное имя состава без пробельных символов |
| `reserve` | Доля `[0, 1)`. Уменьшает бюджет для бумаг и задаёт целевой денежный резерв (`cash_floor`), покрывающий в том числе комиссии. |
| `max_lot_weight_error` | Доля `[0, 1)`. Ограничивает ошибку веса, когда идеальное количество меньше одного лота. |
| `min_position_value` | Неотрицательная сумма, по умолчанию `"0"`. Минимальная стоимость позиции, рассчитанная по полному составу. |
| `preferred_currency` | Необязательная приоритетная валюта инструмента, по умолчанию `"RUB"`. Например, `"CNY"`; регистр букв не важен. |
| `allocation_drift_limits` | Обязательная непустая таблица допусков внутренних продаж. Строка выбирается по полному бюджету стратегии до вычета резерва. |
| `instruments` | Непустой массив бумаг с уникальными `ticker`; полная справочная база состава |

У каждой бумаги задаются:

| Поле | Значение и ограничения |
| --- | --- |
| `ticker` | Непустая уникальная строка с тикером |
| `reference_price` | Положительная справочная цена одной штуки |
| `reference_index_capitalization` | Положительная справочная индексная капитализация |
| `effective_quantity` | Неотрицательное справочное количество штук |
| `free_float`, `weight_limit` | Справочные доли `(0, 1]` |
| `reference_weight` | Справочный вес в процентах `[0, 100]` |

`preferred_currency` задаётся для всего INDEX-состава, включая лист внутри
COMPOSITE. Пустое, `null`, неизвестное или нестроковое значение ошибочно;
пробелы не удаляются. Отсутствующее поле означает RUB.
Справочные `reference_price_currency` у бумаги и общая
`reference_capitalization_currency` описывают единицы исходного снимка,
по умолчанию RUB, и не управляют выбором инструмента.
Для явно нерублёвых справочных единиц нужен положительный строковый
`reference_fx_rate`: валюта капитализации за единицу валюты справочной цены;
при совпадающих валютах курс равен 1. Текущий курс его не заменяет.

#### Конфиг одной бумаги

INDEX подходит и для одной акции или фонда; фонд не обязан отслеживать индекс.
При копировании `gold.json` для другой единственной бумаги замените `name`
и `ticker`. Справочные `reference_price`, `reference_index_capitalization`,
`effective_quantity`, `free_float`, `weight_limit` можно оставить равными `"1"`,
а `reference_weight` — `"100"`.
Это условная база для состава из одной бумаги: она получает весь бюджет
для инвестирования после резерва с учётом целых лотов. `reference_price="1"`
не задаёт цену покупки; актуальные цену и размер лота программа получает из API.
Выбирайте поддерживаемую рублёвую бумагу, доступную через API.

Для нескольких бумаг такой шаблон не задаёт нужное распределение:
потребуются согласованные справочные цены и индексные капитализации.
Резерв и допуски проверяйте отдельно для своей настройки.

#### Как выбираются бумаги и лоты

Лот — минимальный пакет штук для одной сделки. Например, при лоте 10
можно купить 10 или 20 штук, но не 7.

1. Для каждой бумаги обновляется индексная капитализация:
   `reference_index_capitalization * current_price / reference_price`.
   Справочные `effective_quantity`, `free_float`, `weight_limit`
   и `reference_weight` повторно в эту формулу не подставляются.
2. Бумаги сортируются по убыванию капитализации, при равенстве — по тикеру.
3. Из полного бюджета вычитается резерв; оставшуюся сумму обозначим `invest_budget`.
   Один раз проверяется минимум по полному составу:
   `invest_budget * full_index_weight < min_position_value`.
   При первом нарушении отсекаются эта бумага и все следующие.
   Равенство минимуму допустимо. Для исходного состава из одной бумаги
   этот минимум не применяется.
4. Веса оставшейся начальной части списка пересчитываются так, чтобы в сумме дать 1.
   Идеальное число лотов округляется к ближайшему целому.
   Ровно половина округляется к чётному: 2.5 до 2, 3.5 до 4.
5. Если округления превысили бюджет, программа отменяет округления вверх.
   Сначала отменяется то, которое меньше всего увеличивает относительную
   ошибку веса; при равенстве выбирается тикер.
6. Для бумаг с идеальным количеством меньше одного лота проверяется ошибка:
   `abs(lots * price * lot / invest_budget - weight) / weight`.
   Она должна укладываться в `max_lot_weight_error`.
   Для идеального количества от одного лота эта проверка не применяется.
   Ноль лотов всегда исключает бумагу.
7. Первый отказ по лотам или ошибке удаляет бумагу и весь список после неё.
   Расчёт повторяется на оставшейся части. Исключённые бумаги в этом расчёте
   не возвращаются; минимум из пункта 3 повторно не применяется.

Здесь `invest_budget = полный бюджет * (1 - reserve)`.
В функции `calculate_index_target` эта сумма передаётся аргументом `budget`.
В этих расчётах `price` — цена штуки,
`lot` — штук в лоте, `lots` — число лотов, `weight` — целевой вес
в оставшемся составе. `full_index_weight` относится к полному исходному составу.

Из-за повторного пересчёта весов увеличение бюджета не гарантирует,
что список бумаг только расширится.

`max_lot_weight_error="0.05"` означает относительную ошибку доли конкретной
бумаги до 5%, а не 5% всего счёта. Например, при бюджете для бумаг после
резерва 100 000 рублей и целевой доле 10% целевая сумма равна 10 000 рублей.
Допуск 5% от неё — 500 рублей: от 9 500 до 10 500 рублей.
Это смысл проверки округления, не разрешение купить дробный лот.
Допуск применяется только при идеальном количестве меньше одного лота;
при количестве от одного лота эта проверка не применяется.
Он не ограничивает инвестиционные убытки и не является порогом ребалансировки.

#### Таблица допусков

Каждая строка `allocation_drift_limits` содержит ровно четыре поля:

```json
{"budget_from": "0", "budget_to": null, "upper_inclusive": false, "limit": "0"}
```

`budget_from` и конечный `budget_to` — неотрицательные конечные Decimal-строки.
Первая строка начинается с 0. Диапазон включает нижнюю границу,
но не верхнюю: `[from, to)`. Диапазоны идут непрерывно, без разрывов
и пересечений; в каждом конечном диапазоне `from < to`.

Только у последней строки `budget_to = null`: верхнего предела нет.
`upper_inclusive` всегда `false`, `limit` находится в `[0, 1)`.
Таким образом, таблица покрывает любой бюджет от 0.

У встроенных INDEX из одной бумаги таблица состоит из одной строки
с `limit = 0`. У IMOEX 95 диапазонов. В их значениях уже есть запас 10%;
дополнительный множитель не применяется.

Строка IMOEX выбирается по полному бюджету самого IMOEX до резерва.
Если IMOEX входит в COMPOSITE, используется бюджет этого компонента,
а не всего счёта.

Допуски могут как увеличиваться, так и уменьшаться между строками.
Таблица задаёт условия ребалансировки, а не гарантирует максимальную ошибку
при любых будущих котировках.

Если бюджета не хватает для непустой основной цели, это ошибка,
в том числе с `--debug`. Пустая цель не является командой продать весь портфель.

#### Как находится инструмент в API

Для каждого тикера проверяются кандидаты типов `share` и `etf`
во всех режимах торговли; если таких совпадений нет, проверяются `bond`.
Полные данные по UID должны подтвердить тикер,
тип, режим, положительное число штук в лоте и `api_trade_available`
строго типа bool.

Среди кандидатов с `api_trade_available = True` приоритет имеют те,
чья фактическая `currency` совпадает с `preferred_currency`.
В выбранной валютной группе берётся первый кандидат в исходном порядке API.
Если нужной валюты нет, берётся первый из всех доступных кандидатов в том же
порядке. При нескольких кандидатах в выбранной группе пишется WARNING
с безопасными UID/режимами не более 20 кандидатов и числом остальных.
Нет доступных — ошибка.
Отсутствующая или некорректная валюта доступного инструмента также ошибочна,
RUB из неё не выводится. UID, валюта и остальные метаданные берутся из API.
Короткий флаг из результата поиска не используется;
доступность проверяется по полным данным.
Белого списка режимов TQBR/TQTF нет.

Котировки должны быть положительными. Их валюта и время сохраняются.
Наличие цены прошлой торговой сессии ещё не означает,
что сейчас можно отправить заявку BESTPRICE.

### COMPOSITE

COMPOSITE объединяет стратегии и распределяет между ними бюджет.
Ребёнок, или компонент, — стратегия внутри COMPOSITE.

Пример встроенного [balanced.json](autorepeater/configs/composite/balanced.json):

```json
{
  "name": "BALANCED",
  "component_drift_limit": "0.20",
  "components": [
    {"algoritm": "INDEX", "src": "IMOEX", "weight": "0.684210526"},
    {"algoritm": "INDEX", "src": "OBLG", "weight": "0.210526316"},
    {"algoritm": "INDEX", "src": "GOLD", "weight": "0.105263158"}
  ]
}
```

Поле `component_drift_limit` обязательно. Запишите долю строкой:
значение должно быть конечным и находиться в диапазоне `[0, 1)`.
В примере порог равен 20%.

`components` — непустой список. У каждого компонента ровно три поля:
`algoritm`, `src`, `weight`.
Алгоритм — непустая строка без пробельных символов.
`src` — непустая строка, не состоящая только из пробелов;
она используется без исправления регистра и пробелов.

Каждый `weight` находится в `(0, 1]`. Веса складываются в порядке объявления
с Decimal-точностью 28; сумма не должна превышать 1.
Неизвестные поля запрещены, в том числе собственный `reserve`
и параметры исполнения у COMPOSITE.

Внутри COMPOSITE может быть другой COMPOSITE. Повторения стратегий допустимы.
Циклом считается повтор пары `(algoritm, src)` в активном пути вложенности.
Такой цикл отклоняется до вызова фабрик и создания Client;
ошибка содержит весь путь. Повторения в соседних ветвях не являются циклом:
каждое готовится заново.

## Политика и деньги

### Бюджет, стоимость бумаг и резерв

Полный бюджет счёта, `B`, — стоимость его бумаг плюс деньги.
У листа бюджет для бумаг — полный бюджет за вычетом его резерва.
Он всё ещё включает стоимость уже купленных бумаг, а не только свободные рубли.
Стоимость каждой исходной позиции отдельно приводится к точности nano
до сложения. Валютные позиции исходного ACCOUNT в его состав не входят.

Стратегия без детей называется **листом**.
Её текущий капитал `C` оценивается через стоимость принадлежащих ей бумаг `V`:

```text
лист:           C = V / (1 - reserve)
вложенный узел: C = V / sum(exposures)
```

Так учитывается и резерв, предусмотренный стратегией.
`C` — оценка капитала, а не сумма рублей, которыми прямо сейчас можно оплатить покупку.

`exposures[UID]` — идеальная доля стоимости инструмента в полном бюджете стратегии.
Этот профиль строится до отсечения хвоста и округления к лотам.
`prices` содержит цены того же снимка данных.
`reserve_fraction` включает только резервы листьев.
COMPOSITE умножает доли на вес компонента ровно один раз на каждом уровне.
Итого это три разные величины: полный бюджет, его часть для бумаг
и оценка текущего капитала `C`. Ни одна из них сама по себе не заменяет
проверку свободных денег перед покупкой.

### Кому принадлежат одинаковые бумаги

**UID** — идентификатор инструмента у брокера.
Для расчёта всего дерева у каждого UID используется одна цена:
цена счёта назначения, если бумага там есть, иначе максимальная оценка
из профилей стратегий. Общая карта этих цен называется `marks`.

Если один UID нужен нескольким компонентам, имеющееся количество делится
между ними по коэффициентам `weight * exposure`.
Деление выполняется в Decimal-штуках, а не в целых лотах.
Например, коэффициенты 0.30 и 0.10 делят 10 штук как 7.5 и 2.5.
Арифметический остаток получает компонент с наибольшим коэффициентом,
при равенстве — первый. Общее количество и стоимость по `marks` сохраняются точно.

Это расчётное, а не исторически установленное владение.
Программа не знает, какая стратегия когда купила общую бумагу,
и не хранит историю владельцев между запусками.
Поэтому оценка может скрыть или преувеличить отклонение состава
и измениться от цены даже без сделки. WARNING показывает UID,
пути компонентов, коэффициенты и выделенные количества.
Это отдельный риск, не ошибка округления к лотам.

### Как COMPOSITE делит бюджет

Обозначения:

| Обозначение | Значение |
| --- | --- |
| `B` | Полный бюджет COMPOSITE |
| `weight_i` | Вес ребёнка из конфига |
| `W = sum(weights)` | Сумма весов детей |
| `M = B * W` | Общий бюджет, предназначенный детям |
| `C_i` | Оценка текущего капитала ребёнка с учётом его резерва |
| `B_i` | Новый бюджет ребёнка |

Оставшиеся `B * (1 - W)` рублей остаются денежным остатком
и не выделяются на бумаги дочерних стратегий.

Текущая доля ребёнка считается по `C_i`, целевая — по `weight_i / W`.
Для каждой доли считается относительное отклонение,
после чего берётся самое большое:

```text
отклонение частей = max(abs(actual_share - target_share) / target_share)
```

Это относительная разница, а не разница в процентных пунктах.
Например, целевая доля 10%, текущая 12% дают отклонение 20%.
При встроенном пороге 20% равенство ещё не разрешает перенос между детьми:
требуется строгое превышение.

Новый бюджет определяется первым подходящим правилом:

1. Если `sum(C) = 0`, дети получают `B_i = B * weight_i`.
2. Если отклонение строго выше собственного порога COMPOSITE,
   дети тоже получают целевые бюджеты `B_i = B * weight_i`.
3. Если порог не превышен, но `M < sum(C)`,
   бюджеты пропорционально уменьшаются: `B_i = M * C_i / sum(C)`.
4. В остальных случаях дети сохраняют `C_i`.
   Добавочные деньги `M - sum(C)` направляются в положительные денежные недовесы
   `max(0, B * weight_i - C_i)`, пропорционально их размерам.

Все новые бюджеты должны быть положительными.
Корректируется только арифметический остаток при суммировании:
поправка рассчитывается в Decimal по однозначному правилу.

Примеры при `B = 100000` и весах 0.6/0.3:

- `C = 80000/20000`: порог превышен, бюджеты становятся 60000/30000.
- `C = 67000/33000`: порог не превышен, пул детей меньше суммы `C`;
  бюджеты становятся 60300/29700.
- При начальном заполнении бюджеты равны 60000/30000.
  С резервами 0.01/0.02 на бумаги идут 59400/29400.

### Когда уменьшение бюджета требует продаж

Не всякое числовое уменьшение бюджета означает потерю уже вложенного капитала:
причиной может быть только нехватка расчётного резерва.

```text
R = sum(C_i * reserve_fraction_i)   # расчётный резерв детей
A = sum(C) - R                     # капитал без этого резерва
```

Если собственный порог COMPOSITE не превышен и
`A <= M < sum(C)`, уменьшение бюджета не требует принудительных продаж.
Если `M < A`, уменьшенные дети обязаны пересчитать план с разрешением ребалансировки.
Явное требование предка продолжает действовать на вложенных уровнях.
Нераспределённая доля вложенного узла не считается резервом.

При этом ребёнок отдельно проверяет собственный внутренний критерий.
Он может разрешить продажи даже при резервном исключении у родителя.

### Как лист решает, нужна ли ребалансировка

COMPOSITE сравнивает доли компонентов между собой.
ACCOUNT и INDEX сравнивают пропорции бумаг внутри своей стратегии —
это другой показатель и отдельный допуск.

Лист строит две цели по одному снимку:

- `main`, основную цель, — от всего выделенного ему бюджета.
- `control`, контрольную цель, — от стоимости уже вложенных в него бумаг.

Контрольная цель нужна для проверки внутреннего состава.
Отклонение `drift` — половина суммы абсолютных разниц между нормированными
денежными весами бумаг. Это половина L1-разницы; деньги в метрику не входят.
Например, если контрольные веса двух бумаг 50%/50%, а фактические 60%/40%,
то `drift = (abs(0.60 - 0.50) + abs(0.40 - 0.50)) / 2 = 0.10`.
При допуске 0.10 равенство не даёт внутреннего разрешения на продажи.

Продажи разрешены, если `drift > limit` либо требуется обязательное
сокращение капитала. Иначе режим — `BUY_ONLY`: докупать без продажи
приписанных этой стратегии бумаг.

Пустая `control` отключает только внутренний сигнал.
В `main` должно быть хотя бы одно положительное количество;
иначе расчёт завершается ошибкой. Если непустая цель уже достигнута
и покупать или продавать нечего, результат — обычный `SKIP`.

Пополнение само по себе не даёт права продавать.
Однако оно может перевести IMOEX в строку таблицы с меньшим допуском.
Пример: бюджет 159000 меняется на 161000, `drift = 0.055`,
а `limit` — с 0.059242183 на 0.052455282.
До пополнения порог не превышен, после него продажи могут быть разрешены.

### Сколько денег должно остаться

`cash_floor` — расчётный целевой резерв денег:

- У листа: `budget * reserve`.
- У COMPOSITE: сумма детских `cash_floor` плюс нераспределённый бюджет.

Остаток, который не удалось потратить из-за размера лота, в `cash_floor` не входит.
Резерв уже учтён в цели и бюджете покупки бумаг. Комиссии могут уменьшить
его фактический остаток; повторно вычитать floor из доступных денег или
собственного денежного лимита брокера перед покупкой не нужно.

Лимит стоимости бумаг расходуется по исполненным штукам и фиксированной
оценке плана. Фактический principal BESTPRICE с комиссией отдельно ограничен
деньгами того же владельца: небольшое изменение цены может использовать
его денежный запас, включая резерв, без доступа к чужим остаткам.

Рост цен при нехватке только расчётного резерва не вызывает принудительных продаж:
резерв восстанавливается последующими поступлениями.
Пример для одной бумаги с лотом 1 и резервом 0.006 (0.6%): есть 9940 штук,
цена выросла с 10 до 10.5, деньгами остаётся 600.
Получается `B = 104970`, `C = 105000`,
`main = 9937` штук, но режим `BUY_ONLY`: продажи не происходит.

### Какие деньги можно тратить

Бумаги, не приписанные ни одной стратегии, учитываются в бюджете ровно один раз.
Для них есть отдельное разрешение продажи. Деньги от продажи этих бумаг нельзя
использовать для покупок, пока продажа не исполнена полностью и новые данные
брокера не подтвердили доступность денег. Исполнитель разрешает такую продажу
независимо от порога COMPOSITE и режима `BUY_ONLY` бумаг, приписанных стратегиям.
Продать можно только общий избыток, оставшийся после объединения потребностей
стратегий, и только в пределах свободного количества бумаг и собственных
лимитов брокера. Счёт должен быть готов к торговле,
а количество — соответствовать размеру лота.

Выручка внутренних продаж остаётся в своей **области** —
части дерева стратегий, для которой разрешено использование этих денег.
Чтобы передать деньги между компонентами, нужно явное
`redistribution_allowed`; запреты вложенных узлов сохраняются.
Например, деньги от продажи внутри GOLD нельзя автоматически потратить
на IMOEX. Родительский план должен разрешить такое перераспределение.

**Netting** — объединение встречных потребностей владельцев одной бумаги
до отправки внешних заявок. Оно не создаёт денег и не даёт права продать
долю владельца с `BUY_ONLY`. Встречные внешние сделки только ради смены
расчётного владельца не отправляются.

Общая доступность денег счёта ограничивает отдельные денежные пулы,
но не доказывает, кому принадлежит выручка.
Если квитанция (`receipt`) не подтверждает денежную сумму продажи,
покупки из изолированных пулов откладываются с INFO.
Общий остаток можно использовать только тогда, когда все владельцы продажи
вправе финансировать всех получателей; вложенные запреты всё равно действуют.
Изолированный пул — деньги, которыми могут пользоваться только получатели
своей области. Общий пул — деньги, разрешённые для всех его получателей.

### Как выбираются сделки

Покупки ограничиваются реальными доступными деньгами,
денежным пределом области, основной целью и собственными лимитами брокера
(`own caps`).
Даже если цели не хватает бумаги, полный лот покупается только при наличии
достаточных свободных денег и разрешённого брокером числа лотов.

Следующим выбирается лот, который сильнее всего уменьшает денежный недовес
в абсолютных рублях. При равенстве сравниваются UID, затем путь стратегии (`path`).
Это жадный выбор одного следующего лота, а не поиск глобально лучшего
сочетания всех лотов. Несколько шагов могут объединяться в эквивалентный пакет,
чтобы ускорить расчёт. BUY не превышает цель.

Количество для SELL округляется после объединения потребностей.
Продажа ограничивается свободными штуками и количеством,
принадлежащим только владельцам, разрешившим продажу.
Например, вклады 7.5 и 2.5 штуки могут собрать один физический лот из 10.
Если 2.5 штуки защищены режимом `BUY_ONLY`, продать их за другого владельца нельзя.

## API и слои

Этот раздел описывает внутренние договорённости программы.
SDK — библиотека для обращения к брокеру. Адаптер переводит её данные
в собственные объекты программы; стратегия работает с этими объектами,
а не с SDK.

### Подготовка стратегии

CLI и облако один раз вызывают `prepare_strategy(algoritm, src)`
до чтения токена. Результат `PreparedStrategy` хранит фабрику создания,
подготовленные данные и имя источника для вывода (`source_display`).

`Runner(token, prepared_strategy, dst, params=RunnerParams(debug=False))`
создаёт стратегию и проверяет, что её методы можно вызвать.
Это происходит до создания Client, без повторной подготовки.
Конструктор стратегии не выполняет ввод-вывод и не получает клиента.

### Договорённости стратегии

Стратегия имеет пять методов. Структурный `Protocol` проверяет этот набор;
обязательное наследование не требуется.

```python
load_snapshot(data) -> object
allocation_profile(snapshot) -> AllocationProfile
build_plan(snapshot, context: StrategyContext) -> StrategyPlan
event_accounts(dst_account_id) -> tuple[str, ...]
should_rebalance(event, dst_account_id) -> bool
```

- `load_snapshot` загружает снимок данных для расчёта.
  Снимок — данные, прочитанные для текущего пересчёта.
  Его внутреннее устройство неизвестно родителю.
- `allocation_profile` строит идеальные доли и цены.
- `build_plan` строит план. Оба расчётных метода чистые:
  без обращений к SDK, чтения API и торговли.
- `event_accounts` сообщает счета для подписки.
- `should_rebalance` решает, нужно ли заново проверить стратегию по событию.

`build_target` у листа — внутренний расчётчик, а не дополнительный общий метод.

| Объект | Поля и назначение |
| --- | --- |
| `StrategyContext` | `path`, `budget`, `previous_budget`, отдельный `budget_reduction_requires_rebalance`, выделенные `positions` и общие `marks` |
| `StrategyPlan` | `path`, `budget`, `target`, `cash_floor`, `decision`, `children`, `unassigned`, `positions` |
| `decision` | `mode`, `redistribution_allowed`, `reason`, `metric`, `limit` |

`positions` закрепляют расчётное владение на один проход.
После продаж оно не распределяется между владельцами заново.

`TargetPortfolio` содержит `quantities`, `prices`, `empty_reason`.
Количество и цена хранятся в словарях UID → конечный Decimal,
в штуках и цене одной штуки. Лишние цены игнорируются.

Общий `validate_target` проверяет форму объекта и допускает отрицательные
количества и неположительные конечные цены.
Проверка финансового плана строже: только длинные позиции,
положительные оценки ненулевых позиций и хотя бы одна положительная цель.
Длинная позиция — уже имеющаяся или покупаемая бумага, без продажи в долг.

Нулевое целевое количество отдельного UID означает полный выход из этой бумаги,
но продавать её можно только по разрешению стратегии.
Это отличается от полностью нулевой или пустой `main`: такая цель ошибочна.

### Данные для исполнения

`ExecutionData.get_readiness(account_id, timeout=...)` читает только признаки
готовности: загрузку, блокировки портфеля и позиций, число активных заявок.
Деньги, цены, источники стратегии и FX для этой проверки не рассчитываются.

`ExecutionData.get_destination(account_id)` возвращает загруженный портфель,
полный `budget`, объединённые количества и `marks`, свободные деньги и штуки,
активные заявки (`active_orders`) и готовность лимитов (`limits_ready`).

`get_trade_rules(account_id, uids)` возвращает размер лота,
валюту инструмента (`native currency`), разрешения API/BESTPRICE
и собственные лимиты `buy_money_amount`, `buy_max_lots`, `sell_max_lots`.
Их источник GetMaxLots и ограничения описаны в
[документе об адаптере](docs/execution-adapter.md).

Поле Money портфеля само по себе не даёт права покупать.
Программа не угадывает доступные деньги формулой `money - blocked`
и не предполагает единицы поля `balance`.
Совместимые записи одного UID складываются; несовместимые вызывают отказ.

Валюта оценки `PortfolioEntry.currency` берётся из `current_price.currency`,
а не из валюты самого инструмента.
Если любая позиция назначения оценена не в рублях и явного пересчёта валют нет,
возникает ValueError до построения плана. Позиция не выбрасывается из бюджета,
чтобы скрыть проблему. Для рублёвых оценок сохраняется отдельное
приведение каждой позиции к точности nano.

### Порядок прохода

Проход — один расчёт и попытка выполнить его сделки:

1. Дождаться готовности счёта назначения.
2. Сбросить кеш прохода, прочитать свежие финансовые снимки и FX.
3. Построить профили, общие цены `marks`, контексты и проверить все планы и цели.
4. Прочитать собственные лимиты и проверить торговый план.
5. Выполнить разрешённые SELL и подтвердить их исполнение.
6. Заново прочитать доступность денег, бумаг и лимитов.
7. Перестроить план BUY и выполнять доступные покупки.

При начальной неготовности программа ждёт до 30 секунд с проверками каждые
5 секунд. В общее окно входят чтения API и повторы по квоте. До ready
не загружаются снимки стратегий и FX, не рассчитывается план и не читаются
торговые лимиты. Если счёт остаётся неготовым, проход завершается
`AccountNotReadyError`, а не пустым успехом. Ошибка чтения остаётся ошибкой доступа.

Окно заканчивается при ready. Обычные финансовые чтения после него сохраняют
прежние тайм-ауты и повторы по квоте; весь проход не ограничен 30 секундами.
Если свежий полный снимок снова неготов, возникает отдельная ошибка
`account became not ready after preflight`: без нового ожидания и расчёта плана,
без утверждения, что истекли 30 секунд.
Разрешения API/BESTPRICE проверяются по полным данным и текущему статусу.
Статус NORMAL_TRADING не является единственным допустимым.

### Подтверждение сделки

Для каждой продажи и покупки нужен статус полного исполнения `FILL`:

```text
requested = executed = отправленное число лотов
```

Адаптер берёт UID, направление, broker order_id, статус и счётчики
только из ответа брокера `PostOrderResponse` или `OrderState`.
Подставлять их из отправленного намерения нельзя: иначе проверка
подтверждала бы собственный запрос, а не фактическую сделку.

Требования к ответу:

- UID и broker order_id — непустые строки.
- Направление и статус — допустимые SDK enum, то есть значения перечислений SDK,
  а не равные им числа, bool или строки.
- Числа лотов — int, но не bool; `0 <= executed <= requested`.
- Все обязательные поля присутствуют и корректны.
  UNSPECIFIED и неизвестные enum вызывают OrderExecutionError
  с фиксированной безопасной причиной.
- REJECTED и CANCELLED означают отказ, а не исполнение.
- Даже корректно оформленный ответ с чужими UID, направлением или лотами
  отклоняется исполнителем при сверке с намерением.

**Request ID** — ключ отправленного запроса.
Он создаётся один раз после проверки намерения, перед PostOrder.
**Broker order_id** — идентификатор заявки из ответа брокера.
Их равенство не предполагается. В INFO записываются связь `request_id`
с проверенным `broker_order_id` и подтверждённые факты ответа.
Одного order_id недостаточно для подтверждения исполнения.

### Ожидание заявки и обновления счёта

Для SELL в статусе NEW или PARTIALLYFILL проверяется тот же broker order_id:
каждые 2 секунды, до 30 секунд. Вместо старой продажи новая не отправляется.
FILL принимается только при совпадении UID, направления и числа лотов.

Отказ, плохой ответ, ошибка чтения или таймаут прекращают оставшиеся заявки с ERROR.
Останавливается текущий проход, а не обязательно вся локальная программа:
её цикл может продолжить ожидание следующих событий.
Неподтверждённый BUY останавливает проход сразу.
Автоматической отмены заявки нет; уже исполненные сделки не откатываются.

После SELL заново читаются позиции, деньги и собственные лимиты.
Цена из ответа и `total_order_amount` не считаются чистой выручкой.

После полного исполнения всех продаж есть отдельное ожидание:
счёт должен стать готовым, а фактические позиции — совпасть с ожидаемыми.
Проверка идёт каждые 2 секунды в отдельном окне 30 секунд.
Если время истекло, пишется WARNING, покупки откладываются.

Совпадение позиций ещё не доказывает зачисление всей выручки.
Для BUY всё равно нужны свежие собственные деньги и лимиты;
поступление не оценивается по цене сделки.

Перед следующими BUY доступность проверяется снова.
После подтверждённой покупки тоже есть ожидание обновления счёта:
до 30 секунд с шагом 2 секунды. Это позволяет продолжить очередь,
если первая покупка временно заблокировала счёт.

Основная цель и источник в этом проходе не меняются.
После обновления пересчитывается вся оставшаяся очередь BUY,
включая UID, которые стали исполнимыми.
Уже отправленный UID в этом проходе повторно не отправляется.

Окна ожидания ограничивают повторные проверки, но не прерывают текущий RPC
или повторы при RESOURCE_EXHAUSTED.
Общий таймаут облака должен учитывать сам расчёт и оба этапа ожидания.

### Чтение API и повторы при квоте

За один пересчёт программа один раз получает полные данные акций через Shares
и фондов через Etfs с `INSTRUMENT_STATUS_ALL`. Это сокращает число запросов.
Во всех режимах кандидаты рассматриваются в порядке поиска;
доступность каждого проверяется по полным данным.

Перед новым пересчётом `StrategyData.begin_snapshot()` сбрасывает кеш.
Это происходит после ready; тогда же начинается свежий FX-снимок прохода.
Проверки готовности не наполняют кеш источников или валютных оценок.
Неизвестный каталогу UID читается через GetInstrumentBy.
Портфели, котировки, текущие торговые разрешения и собственные лимиты
всегда читаются заново.

Один обычный запрос с одним ответом называется unary RPC.
Общая обёртка SDK повторяет его только при `RESOURCE_EXHAUSTED`,
то есть исчерпании квоты API:

1. Пишет WARNING без аргументов и токенов.
2. Ждёт 10 секунд.
3. Повторяет запрос. Число повторов не ограничено.

Исключение — начальная проверка готовности: каждый RPC и пауза по квоте
ограничены остатком общего окна 30 секунд. После его исчерпания новый RPC
не начинается. Ошибка доступа сохраняет исходную причину; локальное истечение
срока чтения не выдаётся за ответ брокера not-ready или `DEADLINE_EXCEEDED`.

Для PostOrder во всех таких попытках сохраняется тот же request ID
в аргументе `order_id`. Фабрика ID вызывается один раз на логическую отправку,
вне повтора по квоте. ID между запусками не хранится.

Deadline (истечение срока отдельного запроса) и любые другие ошибки не запускают повторную отправку:
они сразу передаются вызывающему коду.
Отдельный unary RPC имеет таймаут не более 10 секунд;
если ему уже задан меньший таймаут, он сохраняется.
Общий таймаут облачной функции должен позволять ждать сброса квоты,
но всё равно может прервать запуск.

### Действия после неподтверждённой заявки

Ошибка или тайм-аут не означают, что заявка не была принята или исполнена.
Сначала остановите программу, отключите запуски по расписанию
и автоматические повторы неуспешных вызовов в облаке;
это не отменяет уже отправленные брокеру заявки.

В приложении или веб-версии брокера проверьте активные заявки, историю
исполнения, фактически исполненное количество бумаг, деньги и блокировки.
При частичном исполнении отдельно выясните судьбу оставшейся части:
она может продолжать исполняться. Управление заявками описано в
[справке Т-Инвестиций](https://www.tbank.ru/invest/help/brokerage/account/trade-on-bs/bids/).
Если отменяете оставшуюся часть заявки, дождитесь подтверждения отмены;
это не откатывает исполненные сделки.

Возобновляйте работу после выяснения результата прежних заявок и обновления
состояния счёта. Сначала сделайте новый `--debug` и проверьте план по фактическому
портфелю. Если результат заявки остаётся неизвестным, не пытайтесь исправить
это повторным запуском: обратитесь к брокеру, сохранив время ошибки
и идентификаторы из логов, без токена. Отсутствие заявки в одном просмотренном
списке само по себе не доказывает, что сделка не состоялась.

### Логи и ошибки

При локальном запуске сообщения видны в том же терминале; стандартный
Python logging выводит их в stderr. Файл логов автоматически не создаётся:
его сохранение и просмотр при запуске через сервис настраивает пользователь.
В Yandex Cloud откройте нужный каталог, сервис Cloud Functions, свою функцию
и вкладку логов. Подробности — в
[инструкции просмотра журнала](https://yandex.cloud/ru/docs/functions/operations/function/function-logs).
Логи CI и деплоя находятся отдельно: GitHub > Actions > нужный запуск > задание.
Они не заменяют журнал выполнения торговой функции.

INFO показывает:

- На каком этапе остановилось исполнение.
- Загрузку лимитов, блокировки портфеля, денег и бумаг.
- Активные order_id, UID, статусы и исполненные лоты.
- Фактические и ожидаемые количества.
- Отправку и подтверждение каждой сделки.
- Итоговое число подтверждённых SELL и BUY.

Токены и сырые ответы SDK не выводятся. Дополнительные запросы только ради логов
не выполняются.

| Ошибка | Что происходит |
| --- | --- |
| ValueError / UnsupportedSourceError данных | Вызов завершается без переподписки |
| DataAccessError / ExecutionDataError | Сохраняется исходная причина (`cause`), включая локальный тайм-аут чтения готовности |
| AccountNotReadyError | Ожидание готовности истекло либо полный снимок снова неготов; текущий проход останавливается |
| OrderExecutionError | Текущий проход останавливается |

При транспортном отказе PostOrder или плохом ответе OrderExecutionError
сохраняет `request_id`. ERROR адаптера содержит этот ID,
проверенные UID/направление/лоты намерения и фиксированную причину.
Текст RequestError, его kwargs и строковое представление SDK-объекта не выводятся.
Транспортный RequestError сохраняется как `cause`; при передаче ошибки
контекст остаётся. Broker ID выводится отдельно и только из проверенного ответа.

Локальный `_local_pass` логирует ошибки доступа, неготовность и остановку
исполнения, завершая только текущий проход. CLI продолжает работу.
`run_sync` и облачный handler пробрасывают такие ошибки;
облако при сбое не возвращает Success.
Новое событие может начать свежий расчёт, но не повтор неизвестной заявки.
Программные ошибки не скрываются.
Traceback исходного исключения SDK может содержать данные провайдера.

Если основная цель `main` пуста, расчёт завершается ошибкой даже с `--debug`.
Если цель непустая и портфель уже ей соответствует, покупать и продавать
нечего: результат — `SKIP`.

### События и повторные расчёты

`event_accounts` возвращает непустой tuple уникальных непустых строк
без пробелов. `should_rebalance` возвращает строго bool.

Сначала движок синхронизирует счёт, затем открывает одну подписку
`position_events` на объединённый список счетов дочерних стратегий.
Счета перечисляются в порядке первого появления. Метод `should_rebalance`
вызывается у каждой дочерней стратегии, даже если одна из предыдущих
уже вернула положительный ответ.

Подходящие события непустого счёта назначения запускают проверку,
а не автоматически разрешают сделку. Все блокировки проверяются.

ACCOUNT следит за событиями позиций исходного счёта и счёта назначения;
изменение источника может вызвать новый расчёт. INDEX следит за счётом
назначения, COMPOSITE — за объединением счетов своих детей.
Это уведомления API об изменениях денег и бумаг, а не таймер котировок.
Для событий назначения требуется непустое состояние позиций и отсутствие
проверяемых блокировок. Событие только начинает проверку: решение о сделках
зависит от состава, бюджета, допусков и разрешений брокера.

Работающий `main.py` слушает события API; таймера котировок у CLI нет.
Изменения цен проверяются при следующем событии, сверке после разрыва или перезапуске.
После конца потока или ошибки его открытия/чтения CLI ждёт, выполняет свежий
проход и подписывается заново, даже если нового события ещё нет.
Паузы по умолчанию: 1, 2, 4, 8, 16, затем 30 секунд. Они сбрасываются только
при позиционном событии в подписке, проработавшей не менее 60 секунд;
служебное событие и конец потока сами по себе их не сбрасывают.
Снимок и подписка не атомарны: порт не предоставляет replay или курсор событий,
поэтому доставка каждого события и exactly-once не гарантируются.

Обеспечение постоянной работы — задача пользователя. Возможные решения:
служба systemd, менеджер процессов, контейнер или облачная функция с расписанием.
Их настройка, перезапуск и наблюдение здесь не выполняются автоматически.

## Работа в облаке

Yandex Cloud Functions вызывает `handler.handler`,
который выполняет один `Runner.run_sync()`.
Частоту запусков задаёт внешний таймер.

### Своя облачная инфраструктура

Начните с [документации Yandex Cloud Functions](https://yandex.cloud/ru/docs/functions/).
Чатбот-помощник Yandex Cloud может помочь разобраться с созданием ресурсов,
правами и настройками. Передайте ему
[workflow деплоя](.github/workflows/deploy-prod.yml) и
[скрипт публикации](scripts/yandex_deploy.py) как пример работающей схемы;
для автономного архива есть [резервный workflow](.github/workflows/deploy-prod-reserve.yml).
Не передавайте значения токенов и секретов.

Идентификаторы в этих файлах относятся к инфраструктуре этого репозитория,
не к вашему облаку. Потребуются свои ресурсы, сервисные аккаунты, секреты
и настройки доступа. В обоих workflow укажите `FUNCTION_ID` заранее созданной
функции: деплой проверяет этот ID и сохраняет цель при переименовании ресурса.
GitHub-проверки готовых workflow также привязаны
к `gorpsys/autorepeater`. Инструкции публикации этой инфраструктуры находятся
в [техническом README](scripts/README.md#production-деплой).
Ответы помощника сверяйте с документацией и настройками своего облака.

### Перенос своего конфига в облако

Автор использует проект прежде всего для себя. Конфиги в этом репозитории —
примеры его личных настроек, а не библиотека стратегий, которую предполагается
собирать от пользователей. Для хранения своих конфигов в GitHub сделайте
[свой форк проекта](https://docs.github.com/ru/pull-requests/collaborating-with-pull-requests/working-with-forks/fork-a-repo).
Проверьте видимость форка; токены и другие секреты не добавляйте даже
в приватный репозиторий.

Внешний каталог `../autorepeater-configs` удобен для локальных проверок,
но автоматически в облачный архив не попадает. Перед сборкой включите
проверенные конфиги в соответствующие каталоги своей копии проекта:

| Алгоритм | Каталог в облачном пакете |
| --- | --- |
| INDEX | `autorepeater/configs/` |
| ACCOUNT | `autorepeater/configs/account/` |
| COMPOSITE | `autorepeater/configs/composite/`, вместе со всеми конфигами детей в их каталогах |

Например, после проверки MY_INDEX:

```bash
cp ../autorepeater-configs/index/my-index.json autorepeater/configs/my-index.json
```

Имена конфигов в каждом алгоритме должны оставаться уникальными.
Сборка `make claude-yandex-archive` включит этот JSON автоматически.
Для сборки через GitHub файл должен быть закоммичен в вашем форке
и пройти проверки. Готовые workflow требуют настройки под ваш репозиторий
и облако; их идентификаторы и OIDC-привязка автора не становятся вашими при форке.

Для этого примера в версии облачной функции задайте `ALGORITM=INDEX`,
`SRC_ACCOUNT=MY_INDEX` и `DST_ACCOUNT` реального счёта назначения.
Локальные пути DIR/PATH в облако не переносите: уберите эти переопределения
и используйте встроенные каталоги пакета. Для ACCOUNT/COMPOSITE аналогично
выберите свой алгоритм и имя; все дочерние конфиги должны присутствовать.

Токен хранится отдельно от JSON. Если конфиг проверялся в песочнице,
замените её идентификаторы счетов реальными и повторите локальный `--debug`
с production-токеном перед разрешением реальных сделок. В облаке debug нет.

### Расписание

В Yandex Cloud используйте
[триггер-таймер](https://yandex.cloud/ru/docs/functions/operations/trigger/timer-create);
для другого облака — документацию его планировщика. Для локальных разовых
запусков можно изучить cron. Расписание должно вызывать разовый проход
`Runner.run_sync()`, а не каждый раз открывать ещё один бесконечный `main.py`.
Облачный таймер уже вызывает разовую точку входа `handler.handler`.

Интервал подбирается эмпирически. Автор запускает функцию каждый час;
это ориентир нижней границы интервала для его настройки, не обязательное
требование программы. Для пассивной стратегии не стоит запускать её слишком
часто: по собственным требованиям можно выбрать день или даже месяц.
При этом изменения состава и пополнения будут обработаны позже.
Не допускайте пересечения торговых запусков: общая очередь CI-деплоев
не блокирует вызовы приложения по таймеру. Настройку сериализации
и повторов вызовов выполняйте по документации выбранного провайдера.

Повтор после ошибки — отдельная настройка, не обычное расписание и не
повтор запроса при исчерпании квоты API внутри одного прохода.
Автор настроил облачные повторы с интервалом в один час: по его опыту,
этого достаточно, чтобы разобраться с ошибкой и при необходимости отключить
следующие вызовы. Программа сама не отключает расписание или повторы.
Ожидание часа не отменяет прежнюю заявку и не подтверждает её результат;
при неизвестном результате следуйте
[порядку проверки заявок](#действия-после-неподтверждённой-заявки)
до нового торгового запуска.

Можно настроить облачные оповещения об ошибках, чтобы быстрее их замечать.
Как настроить повторы и уведомления, смотрите в документации своего
провайдера; для Yandex Cloud —
[настройки триггера-таймера](https://yandex.cloud/ru/docs/functions/operations/trigger/timer-create),
[мониторинг функции](https://yandex.cloud/ru/docs/functions/operations/function/function-monitoring)
и [каналы уведомлений](https://yandex.cloud/ru/docs/monitoring/operations/alert/create-channel).

### Параметры функции

В query можно передать `algoritm`, `src`, `dst`, `token`.
Но **не передавайте токен в query**: он становится частью URL и может
сохраниться в истории браузера, журналах прокси и облачной инфраструктуры.
Храните токен в защищённом хранилище облака и подключайте его к функции
через переменную окружения `INVEST_TOKEN` или совместимую `t_token`.
Поддержка `token` в query не делает этот способ безопасным.

Если ключ отсутствует, используются следующие значения:

| Ключ | Порядок выбора |
| --- | --- |
| `algoritm` | ALGORITM, затем COMPOSITE |
| `src` | SRC_ACCOUNT, затем BALANCED только для COMPOSITE |
| `token` | INVEST_TOKEN, затем совместимое t_token |
| `dst` | DST_ACCOUNT, затем DEFAULT_DST_ACCOUNT |

Для ACCOUNT и INDEX источник обязателен.
Пустые `algoritm` и `src` не заменяются значением из окружения.
В отличие от облачного выбора по умолчанию, CLI требует оба селектора.

Начиная с 6.0.0 явно переданный `dst` должен быть непустой строкой.
Пустая строка, строка из пробелов, `null` и значения других типов завершают
запуск ошибкой до создания SDK-клиента. Для прежнего выбора счёта через
`DST_ACCOUNT` / `DEFAULT_DST_ACCOUNT` удалите ключ `dst`, а не передавайте
пустое значение. Непустой ID передаётся без преобразования.
Пустой `token` по-прежнему использует значения из окружения.

Вызов триггером-таймером Yandex Cloud передаёт конверт с массивом `messages`,
а не HTTP query-параметры, поэтому использует тот же выбор из окружения/defaults.
Его `details.payload` не разбирается как параметры запуска.
`event=None`, отсутствие `queryStringParameters` и его значение `null`
также означают отсутствие query-параметров. Неструктурированный `event`
или не объект в `queryStringParameters` отклоняются с ошибкой входных данных.

Облако не поддерживает debug. Токен только для чтения не превращает запуск
в расчётный режим без попыток исполнения.

Сборка архива и публикация — в
[документации технических скриптов](scripts/README.md#production-деплой).

## Ограничения исполнения

Рабочий режим поддерживает длинные RUB-позиции и собственные средства.
Общие схемы могут содержать другие валюты, но исполнять такие сделки
без явного пересчёта валют (FX) нельзя.

BESTPRICE — тип заявки «Лучшая цена»: брокер исполняет её по доступным
рыночным условиям, а не по справочной цене из конфига.
Он не гарантирует цену, использованную при расчёте. Правила типов заявок
описаны в [справке Т-Инвестиций](https://www.tbank.ru/invest/help/brokerage/account/trade-on-bs/bids/).
Комиссии, поступление выручки и снимки данных не образуют одну атомарную операцию:
между ними счёт может меняться. Поэтому `cash_floor` не гарантируется
на каждом снимке.
Частота проверки не означает такую же частоту сделок.

Резервы и допуски встроенных конфигов подобраны эмпирически для конкретных
стратегий, не являются универсальными значениями и не гарантируют покрытие
любой комиссии или движения цены. Для состава из одной бумаги сохранённые
значения можно использовать как исходную настройку с проверкой результата;
для другого индекса параметры нужно подбирать под его состав и бюджет.
В проекте есть [утилита сравнения по котировкам](scripts/README.md#калибровка-по-котировкам-api):
она помогает оценивать состав и `max_lot_weight_error`, но не подбирает
автоматически резерв, таблицу допусков продаж или допуск COMPOSITE.

История расчётного владения между запусками не хранится.
При настройке таймера нужно отдельно контролировать перекрывающиеся вызовы
и заявки, которые ещё не завершились.
