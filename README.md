# autorepeater

Автоповторитель сделок для Т-Инвестиций. Приводит счёт назначения к цели
ACCOUNT, INDEX или COMPOSITE через `t-tech-investments`. Стратегии решают,
когда разрешены продажи; общий исполнитель ограничивает сделки реальными
деньгами, владением, лотностью и собственными немаржинальными лимитами API.

## Запуск

```bash
pip install -r requirements.txt
# INVEST_TOKEN передаётся через окружение
python main.py --algoritm INDEX -s IMOEX -d <id_назначения> --debug
python main.py --algoritm ACCOUNT -s 2193248994 -d <id_назначения> --debug
python main.py --algoritm COMPOSITE -s BALANCED -d <id_назначения> --debug
```

`--debug` строит и проверяет планы без отправки заявок. Чтение API остаётся.
Обязательны `--algoritm` (написание сохранено) и `-s`/`--src`.
Для всех трёх алгоритмов src теперь точное поле `name` собственного JSON:
ACCOUNT больше не принимает произвольный номер счёта в качестве источника.
Цифровое имя, ведущие нули и совпадение имени с алгоритмом допустимы;
регистр и пробелы не нормализуются. Ошибки подготовки завершают запуск
до чтения токена и создания SDK Client.

Флаги `-t`/`--threshold` и `-r`/`--reserve` отклоняются argparse.
Общего порога объёма сделок, `THRESHOLD`, `RunnerParams.threshold`,
`set_threshold` и старого модуля orders.py больше нет.
Резерв и допуски принадлежат конфигам. `--thresholds` отдельного индексного
калибратора по-прежнему означает `max_lot_weight_error`.

## Конфиги

Числа задаются конечными Decimal-строками, bool/JSON-числа/NaN/Infinity
не заменяют строки. Доля `"0.01"` означает 1%; исключение
`reference_weight` хранит проценты. Имя документа непустое, без пробельных
символов и независимо от имени файла.

| Алгоритм | Встроенный каталог | Переопределение |
| --- | --- | --- |
| ACCOUNT | autorepeater/configs/account/ | ACCOUNT_CONFIG_DIR либо ACCOUNT_CONFIG_PATH |
| INDEX | autorepeater/configs/ | INDEX_CONFIG_DIR либо совместимый IMOEX_CONFIG_PATH |
| COMPOSITE | autorepeater/configs/composite/ | COMPOSITE_CONFIG_DIR |

Пары DIR/PATH одновременно запрещены. Относительные внешние пути считаются
от cwd; встроенные от модуля. Каталоги читают только непосредственные
нескрытые *.json. Неверный/пустой путь или набор не подменяется встроенным.
Каждый документ читается и проверяется один раз при подготовке вхождения.
Ошибка выбранного имени, его дубликат или отсутствие имени фатальны.
Ошибки чужих документов и чужие дубликаты дают предупреждения с путём.
Читаемое имя повреждённого тела участвует в дубликатах; из битого JSON имя
не восстанавливается по тексту или имени файла. `load_index_configs()`
остаётся строгой проверкой всего INDEX-набора.

Импорт не выполняет I/O; пути разных алгоритмов независимы.
Конфиги фиксируются при подготовке без глобального кеша: новая подготовка
увидит изменение, долгоживущий процесс нужно перезапустить.
Автоматического обновления состава и корпоративных действий нет.

### ACCOUNT

Встроенный [account.json](autorepeater/configs/account/account.json):

```json
{
  "name": "2193248994",
  "source_account_id": "2193248994",
  "reserve": "0.01",
  "allocation_drift_limit": "0.0092"
}
```

Все четыре поля обязательны; дополнительные поля загрузчик не использует.
`source_account_id` состоит из ASCII-цифр, ведущие нули сохраняются.
Имя может отличаться от номера. Reserve и limit в [0, 1).
ACCOUNT исключает валюты источника, квантует стоимость каждой позиции
до nano перед суммированием и считает
`quantity = source_quantity * (budget * (1 - reserve) / total_src)`.
Цель в штуках может быть дробной; BUY не округляется сверх неё.
Допуск 0.0092 получен модельной калибровкой, не восстановлен из старого
порога и не проверен на позициях реального исходного счёта.

### INDEX

| Поле | Единицы и ограничения | Влияние |
| --- | --- | --- |
| name | Непустая строка без пробельных символов | Точное имя состава |
| reserve | Доля [0, 1) | Уменьшает инвестируемый бюджет; задаёт cash_floor |
| max_lot_weight_error | Доля [0, 1) | Ошибка веса только при ideal_lots < 1 |
| min_position_value | Неотрицательная сумма, по умолчанию "0" | Предварительный минимум стоимости по полному составу |
| allocation_drift_limits | Обязательный непустой массив | Допуск внутренних продаж по полному бюджету листа до резерва |
| instruments | Непустой массив, уникальные ticker | Полная справочная база |

| Поле бумаги | Единицы и ограничения |
| --- | --- |
| ticker | Непустая уникальная строка |
| reference_price | Положительная цена штуки |
| reference_index_capitalization | Положительная индексная капитализация |
| effective_quantity | Неотрицательное справочное количество штук |
| free_float, weight_limit | Справочные доли (0, 1] |
| reference_weight | Справочный процент [0, 100] |

Рабочая капитализация равна
`reference_index_capitalization * current_price / reference_price`.
Справочные количество, free_float, weight_limit и reference_weight
не применяются повторно. Весь состав ранжируется по капитализации,
при равенстве по тикеру. После резерва один раз отсекается хвост с
`budget * full_index_weight < min_position_value` (равенство включается).
Минимум не применяется к исходному одноинструментному составу.

Префикс перенормализуется; идеальные лоты округляются к ближайшему целому,
половины к чётному. При превышении бюджета отменяются округления вверх
по наименьшему увеличению относительной ошибки, затем тикеру.
Ошибка `abs(lots * price * lot / budget - weight) / weight` проверяется
только при ideal_lots < 1; ноль лотов всегда исключает бумагу.
Первый отказ удаляет бумагу и весь хвост; расчёт повторяется без возврата
исключённых. Предварительный минимум повторно не применяется.
Простой рост бюджета не гарантирует монотонного расширения состава.

Каждая строка таблицы имеет строго четыре поля:

```json
{"budget_from": "0", "budget_to": null, "upper_inclusive": false, "limit": "0"}
```

Границы конечные неотрицательные Decimal-строки; первый from=0.
Интервалы [from, to) непрерывны, без перекрытий, from < to.
Только последний to=null, это отсутствие верхней границы; upper_inclusive
всегда false, limit в [0, 1). У одноинструментных встроенных INDEX одна
строка с limit=0. В IMOEX сохранены 95 диапазонов и исходные limit * 1.1;
запас уже включён и повторно не применяется. Таблица выбирается по полному
бюджету самого IMOEX, в COMPOSITE по бюджету компонента.

[Историческая калибровка](docs/plans/20261002-imoex-drift-envelopes.md)
проверяла бюджеты 50000..1000000 с шагом 1000. Таблица не обязана быть
монотонной. Промежуточные бюджеты и произвольные цены не имеют гарантированной
ошибки; крайние строки расширены до 0/null как принятая экстраполяция.
При слишком малом бюджете основная цель может быть пустой: это ошибка,
включая debug, а не разрешение продать портфель.

Снимок разрешает точный ticker типа share/etf по всем режимам:
полные UID-метаданные подтверждают ticker/тип/режим, положительную лотность
и строгий bool api_trade_available. Выбирается первый доступный кандидат
в порядке поиска; несколько дают WARNING, ни одного означает ошибку.
Короткий флаг поиска не используется, белого списка TQBR/TQTF нет.
Котировки положительны; валюта и время сохраняются. Котировка прошлой
сессии не доказывает текущую доступность BESTPRICE.

### COMPOSITE

Встроенный [balanced.json](autorepeater/configs/composite/balanced.json):

```json
{
  "name": "BALANCED",
  "component_drift_limit": "0.20",
  "components": [
    {"algoritm": "INDEX", "src": "IMOEX", "weight": "0.684210526"},
    {"algoritm": "INDEX", "src": "OBLG", "weight": "0.210526316"},
    {"algoritm": "INDEX", "src": "GOLD", "weight": "0.105263158"}
  ]
}
```

Порог обязателен, конечная строка в [0, 1). Components непусты,
каждый содержит только algoritm/src/weight. Алгоритм непустой без
пробельных символов; src непустая строка, не только пробелы, без нормализации.
Weight в (0, 1], сумма в порядке объявления при точности 28 не больше 1.
Неизвестные ключи запрещены, включая reserve и параметры исполнения.
Вложенность и повторения допустимы; циклы активных пар (algoritm, src)
отклоняются до фабрик/Client с полным путём. Соседние повторения готовятся заново.

## Политика и деньги

Корневой бюджет B включает бумаги и деньги назначения; стоимость позиций
квантуется до nano по каждой исходной записи. Валюты источника ACCOUNT
исключены. Профиль состава строится до хвоста и лотного округления:
`exposures[UID]` задаёт идеальную долю стоимости в полном бюджете,
`prices` оценки того же снимка, `reserve_fraction` только резервы листьев.
У COMPOSITE коэффициенты умножаются на веса на каждом уровне ровно один раз.

Текущий капитал листа C = V / (1 - reserve), вложенного узла C = V / sum(exposures).
Это оценка, не наличные рубли. Общая цена UID: цена назначения при наличии
позиции, иначе максимум оценок профилей дерева. Общие UID виртуально
распределяются по `weight * exposure`, в Decimal-штуках, без округления
к лотам. Например, претензии 0.30/0.10 делят 10 штук как 7.5/2.5.
Остаток получает наибольший коэффициент, затем первый компонент.
Количество и стоимость в общей карте marks сохраняются точно.

История владельцев неизвестна: атрибуция общих UID может скрывать или
преувеличивать drift и меняться от цены без сделки. WARNING показывает UID,
пути, коэффициенты и количества. Эта принятая неоднозначность отличается
от ошибки округления лотов; хранения истории нет.

Для COMPOSITE W = sum(weights), пул M = B * W; B * (1-W) остаётся деньгами.
Отклонение частей = max(abs(actual_share - target_share) / target_share),
доли actual по C, target по weight/W. Ровно 20% не разрешает перенос.
Бюджеты выбираются в таком порядке:

1. При sum(C)=0: B_i = B * weight_i.
2. При строгом превышении собственного порога: B_i = B * weight_i.
3. Ниже/на пороге при M < sum(C): B_i = M * C_i / sum(C).
4. Иначе C сохраняются, M-sum(C) распределяется по положительным
   денежным недовесам max(0, B*weight_i-C_i).

Все новые бюджеты положительны; суммы исправляются только детерминированной
Decimal-коррекцией арифметического остатка. При B=100000, weights=.6/.3:
C=80000/20000 даёт 60000/30000, C=67000/33000 даёт 60300/29700.
При начальном заполнении и резервах .01/.02 инвестируемые суммы 59400/29400.

Резервный дефицит отделён от сокращения капитала:
R = sum(C_i * reserve_fraction_i), A = sum(C)-R.
Ниже/на пороге при A <= M < sum(C) числовое уменьшение бюджета
не требует продаж; при M < A уменьшенные дети обязаны пересчитаться.
Явное обязательство предка сохраняется через вложенность.
Нераспределённая доля вложенного узла не считается резервом.
Внутренний критерий ребёнка действует независимо от резервного исключения.

Лист строит main от полного бюджета, control от стоимости вложенных бумаг
по тому же снимку. Drift = половина L1-разницы нормированных денежных весов
бумаг; деньги в этой метрике не участвуют. Продажи разрешены при drift > limit
либо обязательном сокращении капитала. Иначе BUY_ONLY. Пустой control
отключает только внутренний сигнал, main без положительных количеств фатален.
Пополнение само по себе не разрешает продажи. Принят риск: переход
IMOEX в строку с меньшим limit после пополнения может разрешить их
(159000 -> 161000, drift .055, limit .059242183 -> .052455282).

`cash_floor` листа = budget * reserve; у композиции сумма детских floor
плюс нераспределённый бюджет. Лотный остаток не входит в floor.
Рост цен при нехватке только расчётного резерва не вызывает принудительных
продаж; резерв восстанавливается поступлениями. Одноинструментный пример:
9940 штук по 10 -> 10.5 при cash=600 даёт B=104970, C=105000,
main=9937, но BUY_ONLY и продаж нет.

Неприписанные бумаги входят в экономический бюджет один раз и имеют отдельное
разрешение продажи. Их стоимость не доступна для BUY до полного исполнения
и свежей подтверждённой доступности. Выручка внутренних продаж остаётся в
области; межкомпонентный перенос требует явного redistribution_allowed,
вложенные запреты сохраняются. Netting не создаёт деньги или право продать
долю BUY_ONLY. Встречные внешние сделки ради смены владельца не отправляются.
Свежая глобальная доступность ограничивает отдельные денежные пулы, но не
устанавливает принадлежность выручки. Если receipt не подтверждает денежную
сумму продажи, покупки из изолированных пулов откладываются с INFO. Общий
остаток используется только когда все владельцы продажи вправе финансировать
всех получателей; вложенные запреты по-прежнему обязательны.

Покупки используют реальные деньги после корневого cash_floor, денежный предел
области, цель и own caps. Выбор: лот с наибольшим абсолютным уменьшением
денежного недовеса, при равенстве UID, затем path. Эквивалентные пакеты
ускоряют расчёт; глобальный оптимум не обещается. BUY не превышает цель.
SELL округляется после объединения, ограничен свободными штуками и владением
только разрешивших продажу областей. Дробные вклады 7.5/2.5 могут собрать
физический лот 10; защищённые 2.5 нельзя продать за другого владельца.

## API и слои

`prepare_strategy(algoritm, src)` вызывается CLI/облаком один раз до токена.
`PreparedStrategy` сохраняет фабрику, данные и source_display.
`Runner(token, prepared_strategy, dst, params=RunnerParams(debug=False))`
создаёт стратегию и проверяет вызываемость методов до Client, без повторной
подготовки. Структурный Protocol не требует наследования:

```python
load_snapshot(data) -> object
allocation_profile(snapshot) -> AllocationProfile
build_plan(snapshot, context: StrategyContext) -> StrategyPlan
event_accounts(dst_account_id) -> tuple[str, ...]
should_rebalance(event, dst_account_id) -> bool
```

Конструктор без I/O/клиента, snapshot непрозрачен родителю.
Profile/build_plan чистые; leaf build_target остаётся внутренним расчётчиком.
StrategyContext содержит path, budget, previous_budget, отдельный
budget_reduction_requires_rebalance, выделенные positions и общие marks.
StrategyPlan содержит path/budget/target/cash_floor/decision/children/unassigned/positions.
Positions сохраняют владение одного прохода; после продаж оно не атрибутируется
повторно. Decision хранит mode, redistribution_allowed, reason, metric и limit.

TargetPortfolio остаётся общим DTO quantities/prices/empty_reason:
словарь UID -> конечный Decimal, штуки и цена штуки. Общий validate_target
допускает отрицательные количества и неположительные конечные цены; финансовый
план нового режима отдельно требует длинные позиции, положительные оценки
ненулевых позиций и хотя бы одну положительную цель. Лишние цены игнорируются.
Нулевой UID в непустой main сохраняет смысл удаления.

Стратегии/общие DTO/политика/движок не импортируют SDK или конкретные адаптеры.
Стратегии не импортируют друг друга или реестр; COMPOSITE создаёт сохранённых
детей через strategy_contract.create_strategy. Reporting не читает API ради
расчётной диагностики; явный просмотр счетов остаётся в Runner.run().

ExecutionData.get_destination(account_id) возвращает уже загруженный портфель,
полный budget, агрегированные количества/marks, свободные деньги/штуки,
active_orders и limits_ready.
get_trade_rules(account_id, uids) возвращает лот, native currency,
API/BESTPRICE flags, own buy_money_amount/buy_max_lots/sell_max_lots.
Источник денег GetMaxLots и ограничения документированы в
[доказательствах адаптера](docs/execution-adapter.md). Money портфеля не является
самостоятельным разрешением BUY; формула money-blocked и единицы balance
не угадываются. Совместимые дубликаты UID агрегируются; несовместимые отклоняются.
Валюта оценки `PortfolioEntry.currency` берётся из `current_price.currency`,
а не из native currency инструмента. Нерублёвая оценка любой позиции назначения
без явной конвертации вызывает ValueError до построения плана; позиция не
исключается из бюджета. Рублёвые оценки сохраняют nano-квантизацию каждой позиции.

Проход: свежие снимки -> profile/marks -> context -> все планы/цели ->
лимиты/readiness -> SELL -> FILL -> свежая availability -> новый BUY-план.
Loading, активные заявки, числовые и depository/exchange блокировки откладывают
торговлю с INFO. API/BESTPRICE проверяются по полным данным и текущему статусу,
без ограничения только NORMAL_TRADING.

Каждая продажа и покупка требуют FILL и requested=executed=отправленные лоты.
Order_id сам по себе недостаточен. Для продажи с NEW/PARTIALLYFILL исполнитель
проверяет статус по тому же broker order_id каждые 2 секунды в течение 30 секунд.
Новая продажа вместо старой не отправляется. FILL требует совпадения UID,
направления и числа лотов; отказ, повреждённый ответ, ошибка чтения или таймаут
останавливают оставшиеся заявки с ERROR. Неподтверждённые покупки по-прежнему
немедленно останавливают проход. Автоматической отмены нет.
Уже исполненное не откатывается. После SELL перечитываются позиции/own caps/
деньги; цена и total_order_amount ответа не считаются чистой выручкой.
После подтверждения всех продаж исполнитель отдельно ожидает готовности
счёта и совпадения фактических позиций с ожидаемыми: повторное чтение каждые
2 секунды, окно 30 секунд. При таймауте WARNING и покупки откладываются.
Это не доказательство зачисления всей выручки: покупки всё равно ограничены
свежими собственными деньгами и лимитами, без оценки поступлений по цене сделки.
Перед дальнейшими BUY доступность снова проверяется; после подтверждённой BUY
также действует окно ожидания обновления счёта 30 секунд с шагом 2 секунды.
Это позволяет продолжить очередь после временной блокировки первой покупкой.
Цель и источник не меняются.
После refresh пересчитывается вся оставшаяся очередь BUY, включая новые
исполнимые UID; уже отправленные UID повторно не отправляются в этом проходе.

INFO-диагностика показывает этап остановки, загрузку лимитов, блокировки
портфеля/денег/бумаг, активные order_id/UID/статусы и исполненные лоты,
фактические и ожидаемые количества, отправку и подтверждение каждой сделки,
а также итоговые числа подтверждённых SELL/BUY. Токены и raw SDK-ответы
не выводятся; ради логирования дополнительных запросов нет.
Окна ожидания ограничивают повторные проверки, но не прерывают текущий RPC
или ранее согласованные повторы при RESOURCE_EXHAUSTED. Общий таймаут облака
должен учитывать обычный пересчёт и оба этапа ожидания.

Для защиты от лимитов API метаданные кандидатов читаются пакетно через полные
справочники Shares/Etfs (`INSTRUMENT_STATUS_ALL`), один раз на тип за пересчёт.
Порядок поиска, все режимы и полная проверка доступности сохраняются.
Перед следующим пересчётом `StrategyData.begin_snapshot()` сбрасывает кэш;
для неизвестных каталогу UID остаётся GetInstrumentBy. Портфели, котировки,
текущие торговые разрешения и собственные лимиты всегда читаются заново.

Общая SDK-обёртка повторяет unary-запрос только при `RESOURCE_EXHAUSTED`:
WARNING без аргументов/токенов, ожидание 10 секунд, новая попытка без лимита
числа повторов. Другие ошибки немедленно передаются вызывающему коду.
Для PostOrder повторяется тот же `order_id`, а не создаётся новая заявка.
Тайм-аут отдельного RPC остаётся 10 секунд; общий тайм-аут облачной функции
должен позволять ожидание сброса квоты и всё равно может прервать запуск.

ValueError/UnsupportedSourceError данных завершают вызов без переподписки.
DataAccessError и ExecutionDataError сохраняют транспортную cause.
OrderExecutionError означает остановку прохода. Локальный цикл ловит
транспортные ошибки/остановку, продолжает подписку; run_sync пробрасывает их,
облако не возвращает Success при сбое. Пустая main фатальна также в debug;
достигнутая непустая цель с пустыми дельтами даёт обычный SKIP.

Event_accounts возвращает непустой tuple уникальных непустых строк без пробелов,
should_rebalance строго bool. Движок сначала синхронизирует, затем открывает
один position_events по объединению детей в порядке первого появления.
Все детские решения вызываются без короткого замыкания.
Подходящие события непустого dst инициируют проверку, все блокировки проверяются.
CLI не имеет таймера котировок: изменения цен проверяются на следующем событии
или перезапуске. Конец стрима и транспортный сбой вызывают новую подписку.

## Облако и архив

Yandex Cloud Functions использует `handler.handler` и разовый Runner.run_sync().
Query: algoritm/src/dst/token. При отсутствии ключа алгоритм берётся из
ALGORITM, затем COMPOSITE; источник из SRC_ACCOUNT, затем BALANCED только
для COMPOSITE. Для ACCOUNT/INDEX источник обязателен. Присутствующий пустой
ключ не заменяется окружением. Token fallback: INVEST_TOKEN и совместимый
t_token; dst: DST_ACCOUNT и DEFAULT_DST_ACCOUNT. CLI требует оба селектора.
Облако не поддерживает debug; read-only token не превращает его в расчётный режим.
Периодичность задаёт внешний таймер.

`make claude-yandex-archive` создаёт build/yandex-function.zip:
main.py, handler.py, requirements.txt, все плоские Python-модули autorepeater
и нескрытые JSON дерева configs. Списка новых модулей вручную нет.
Внешние каталоги, тесты, утилиты и окружения не копируются.
Тесты извлекают архив вне репозитория и запускают CLI/облако с подменённым SDK
и заблокированной сетью, включая независимый алгоритм с одной регистрацией.

## Офлайн-приёмка и ограничения

```bash
python -m scripts.check_rebalance_policy --output /tmp/rebalance-policy-report.json
pytest test/test_rebalance_calibration.py -q
pytest --cov --cov-report=term-missing --cov-report=xml -q
coverage report --fail-under=90
diff-cover coverage.xml --compare-branch=origin/master --fail-under=90
pylint $(git ls-files --cached --others --exclude-standard '*.py')
flake8 . --count --select=E9,F63,F7,F82 --show-source --statistics
git diff --check
make claude-yandex-archive
```

Офлайн-утилита не импортирует SDK, не читает токены, не обращается к API.
[test/data/rebalance_scenarios.json](test/data/rebalance_scenarios.json)
фиксирует seeds, 12 месячных пополнений по 2000, размеры, амплитуды цен,
допуск и условную ставку комиссии 0.05%. В отчёте SHA-256 входов/модулей,
число заявок, оборот в штуках по marks, оценка комиссии, половина L1-ошибки,
повторные проверки, хвост, границы, вне сетки и резервные/общие UID-сценарии.
`--repetitions 1` даёт сокращённую проверку; основной holdout 24000 случаев.
Отчёт не содержит текущего времени; одинаковые байты входов дают одинаковый JSON.

ACCOUNT 0.0092 подтверждён на независимом seed 20261003:
tp=13540, tn=8381, fp=1355, fn=724, совпадение 91.3375%.
Публичный [snapshot](test/data/imoex_snapshot.json) содержит реальные сохранённые
котировки и лотности 44 бумаг от 2026-09-29, но составы ACCOUNT модельные.
Снимка позиций реального ACCOUNT нет, отличие на таком счёте не измерено.
Офлайн-oracle старого 0.004 сохраняет цену * число лотов без множителя лотности.
Метрики ACCOUNT сравнивают условные ближайшие лотные намерения двух критериев,
не исполнимые заявки и не фактическую комиссию. Последовательный INDEX replay
использует новый bounded executor и модельные FILL по фиксированным marks.
В этом holdout старый критерий даёт 181237 условных заявок, новый 200032;
оборот 384482833.62333 и 389237673.58951 рублей соответственно. При условной
ставке 0.05% оценка комиссии 192241.416811665 и 194618.836794755 рублей,
средняя ошибка следования 0.041497055 и 0.041425231. Эта выборка не подтверждает
экономию: безусловная покупочная ветка добавляет намерения, ранее отсечённые
общим порогом. Это совокупность независимых сценариев, не один счёт или год.
Приёмка воспроизводит 95 рабочих limit из сохранённых максимумов с запасом
1.1 и проверяет выбор диапазонов новым API. Исходные 951951 случаев подбора
IMOEX заново не запускались; произвольная новая цена не имеет гарантии таблицы.
Исторические calibration JSON/docs/assets сохраняются неизменными;
первоначальные даты/хеши описывают прежний код, не текущий runtime.

Отдельный `python -m scripts.check_imoex_strategy` с явным READ_ONLY_INVEST_TOKEN
читает публичные котировки; это сетевой калибратор, не часть офлайн-приёмки.
Опции --src, --gross-values (полный бюджет), --budgets (после резерва),
--thresholds (max_lot_weight_error), --sandbox, --output сохранены.
По умолчанию production endpoint; счета и сделки он не запрашивает.
Исторические результаты не подтверждают текущую доступность площадок.

Рабочий режим ограничен длинными RUB-позициями и собственными средствами.
Общие схемы не запрещают другие валюты, но исполнения без явного FX нет.
BESTPRICE не гарантирует оценочную цену, комиссии/settlement/снимки не атомарны,
cash_floor не гарантирован на каждом снимке. Частота проверки не равна
частоте торговли. Модель и один публичный snapshot не дают обещаний годовой
экономии или точного следования для любого рынка.

Локальная приёмка не является live sandbox или GitHub CI. Внешние проверки
требуют отдельного разрешённого запуска/push и здесь не выполнены.
Перед промышленным частым таймером отдельно проверяются перекрывающиеся
вызовы и незавершённые заявки; кеша владения или внешнего хранилища нет.
CI-пороги общего и diff-покрытия остаются 90%, workflows/.coveragerc не изменены.
