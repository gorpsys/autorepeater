# Технические скрипты

Инструменты разработки, проверок, калибровок и публикации autorepeater.
Команды выполняются из каталога проекта. Запуск и конфигурация приложения
описаны в [основном README](../README.md).

## Окружение и проверки

Проверенный набор зависимостей приложения рассчитан на CPython 3.12
и Linux x86_64/amd64 с glibc >=2.17.
CPython — обычная реализация Python; glibc — системная библиотека
Linux, с которой совместимы выбранные готовые пакеты с нативным кодом.
Это ограничения проверенного набора зависимостей, не отдельные шаги установки.
Текущий lock-файл не рассчитан на musl/Alpine, PyPy и другие конфигурации.
Нужны Python с venv/pip, Git, Make и доступ к PyPI. Сборка из исходников и Docker
не используются.

```bash
make setup VENV_PYTHON=python3.12
make check-runtime-lock
make lint
make typecheck
make test
make coverage
git diff --check
```

`VENV_PYTHON` создаёт `.venv`; `PYTHON` выбирает интерпретатор остальных целей.
По умолчанию Make выбирает `.venv/bin/python`, затем `python3` из PATH.
Для уже выбранного внешнего окружения:

```bash
/path/to/venv/bin/python -m scripts.install_dependencies --development
make test PYTHON=/path/to/venv/bin/python
```

До установки скрипту нужны только стандартная библиотека Python
и вспомогательные модули проекта. Сначала он принудительно переустанавливает
зависимости приложения из проверенных wheel-пакетов (`--force-reinstall`),
затем устанавливает инструменты разработки с ограничениями версий из constraints.
При неудачной установке подтверждение успеха (`receipt`) не сохраняется.
Цели Make `lint`, `typecheck`, `test`, `coverage` и `e2e` проверяют набор
зависимостей приложения и подтверждение установки (`receipt`) формата schema2,
включая состав установленных файлов и их хеши. Если пакет заменён другими
байтами, даже при той же версии, проверенную установку нужно выполнить заново.
Подтверждения прежнего формата schema1 недействительны.
Повторная установка через вспомогательный скрипт также нужна, если подтверждение
отсутствует, устарело или установленные зависимости отличаются от проверенного
набора. При конфликте с посторонними пакетами используйте чистое окружение:
скрипт их не удаляет.

Чтобы установить только зависимости приложения, выполните
`python -m scripts.install_dependencies`. Для явного выбора резервного SDK
добавьте `--sdk-source vendored`. В этом режиме доступный индекс по-прежнему
проверяется, а расхождение хешей требует одобрения. На установку отводится
300 секунд, на этап работы с SDK — 60 секунд.

В `requirements.txt` указаны точные версии и хеши зависимостей приложения,
а также официальный источник SDK. Командой `pip install -r requirements.txt`
можно установить этот набор, но она не выполняет предусмотренные вспомогательным
скриптом проверку индекса и процедуру одобрения; SDK с хешем вне lock-файла
она не принимает. В `requirements-dev.txt` перечислены точные версии
зависимостей приложения без хешей и инструменты разработки. Прямая установка
через pip не гарантирует получение именно проверенных пакетов и соблюдение
процедуры одобрения, а также не создаёт подтверждение установки (`receipt`),
необходимое целям Make. Для проверенной установки, включая использование
резервного SDK, применяйте Make или вспомогательный скрипт.
И прямая установка через pip, и установка через скрипт проверяют TLS.

`make lint` запускает строгие проверки Pylint, два этапа Flake8 и Mypy.
`make typecheck` отдельно запускает Mypy для модулей, перечисленных
в `pyproject.toml`. `make coverage` запускает pytest один раз и требует
не менее 90% общего покрытия и покрытия изменённых исполняемых строк.
`make test` запускает только офлайн-тесты из `test/`.
Эти команды не устанавливают пакеты автоматически и не обращаются к брокеру.
`make e2e` обращается к API песочницы, требует отдельного согласования
и sandbox-токена; подробности — в [разделе песочницы](#песочница-в-github).
Проверка готового пакета (`package smoke`) не заменяет E2E.
Проверка приложения со своим конфигом и своими виртуальными счетами описана
в отдельной [ручной инструкции](../docs/sandbox-manual.md);
она не запускает готовый набор E2E-тестов.

| Цель | Проверки |
| --- | --- |
| `make lint` | Pylint, два строгих прохода Flake8, Mypy; любое замечание завершает цель с ошибкой |
| `make typecheck` | Mypy для модулей, перечисленных в `pyproject.toml` |
| `make test` | Офлайн-свита `test/` |
| `make coverage` | Та же свита, отчёт coverage и проверка diff-cover; один прогон pytest |
| `make e2e` | Сценарии реальной песочницы Т-Инвестиций |

`make coverage` запускает инструменты одним интерпретатором. Общее покрытие
и покрытие изменённых исполняемых строк должны быть не ниже 90%.
Тестовые файлы E2E и unit-тестов исключены из измерения рабочего кода.
В PR сравнение выполняется с SHA базы, на push master — с предыдущим SHA;
diff без исполняемых строк проходит без измерения процента.

`make_environment.py` проверяет зависимости; `make_offline.py` формирует
и запускает команды проверок. GitHub Actions использует те же цели Make.

## Источники и резерв

Основной источник SDK — официальный индекс T-Bank;
остальные wheel-пакеты скачиваются из PyPI.
Резервный SDK используется при ошибке DNS или сети, тайм-ауте,
HTTP 401/403/404/429/5xx либо отсутствии нужной версии SDK в корректном индексе.
При переключении выводится WARNING с именем пакета, версией,
безопасным описанием причины и путём. При явном выборе резервного SDK
указывается причина `explicit_vendored_mode`.
Сырые ответы, данные аутентификации и stderr pip не публикуются.
Ошибки сертификата TLS, формата URL или индекса, отозванная публикация пакета
(`yanked`), неоднозначность выбора, ошибки хеша, метаданных, тегов совместимости
или ZIP, а также ошибки разрешения зависимостей и установки завершают работу.
Произвольная ошибка pip не служит основанием для переключения на резерв.

Общий установщик и сборщик автономного архива могут использовать резерв
для отдельного пакета, только если сохранён разрешённый wheel-пакет
с проверенными версией и хешем файла. В текущем
[перечне](../vendor/inventory.json) такой пакет один:
[SDK 1.51.0](../vendor/t-tech-investments/README.md).
Для остальных пакетов наличие соответствующих исходников на GitHub исключает
хранение бинарных пакетов в Git, даже если готового wheel на GitHub нет.
Если PyPI недоступен и резервного пакета нет, установка или сборка завершается
ошибкой. Чужие проекты из исходников автоматически не собираются.
Созданный облачный ZIP может включать бинарные пакеты из PyPI,
но это не означает, что они добавлены в Git.
Бинарник `yc` в репозитории не хранится, резервного источника для него нет.
Если штатная загрузка недоступна, деплой завершается ошибкой.

## Runtime lock и одобрения SDK

[runtime-lock.json](../runtime-lock.json) фиксирует полный набор зависимостей
приложения, включая транзитивные: их версии, целевую платформу, хеши и источники.
Сформированные файлы requirements проверяются на соответствие этому набору.
Обычная установка и сборка не обновляют lock-файл; инструменты разработки
не могут менять зависимости приложения. Чтобы явно сгенерировать файлы
по перечню пакетов, прошедшему ревью, выполните:

```bash
make update-runtime-lock
python -m scripts.install_dependencies --write-file-lock
make check-runtime-lock
```

Генератор использует поддерживаемый отчёт pip о пробной установке (`dry-run`)
для CPython 3.12 с точными ограничениями из перечня пакетов.
Последние доступные версии автоматически не выбираются, одобрения не добавляются.
Отдельный [runtime-file-lock.json](../runtime-file-lock.json) содержит хеши
и размеры исходных файлов каждого конкретного wheel-пакета, включая `RECORD`.
Режим `--write-file-lock` скачивает wheel-пакеты по действующим хешам
и правилам выбора источника SDK, проверяет ZIP и `RECORD`, затем записывает
только сведения об этих файлах. Пакеты при этом не устанавливаются,
подтверждение установки (`receipt`) не создаётся.
Оба lock-файла требуют ревью; если сведения о файлах устарели,
установка и офлайн-проверка блокируются.

Для проверки подготовленного отчёта выполните
`python -m scripts.update_runtime_lock --report /tmp/pip-report.json`:
команда также записывает lock-файл и сформированные requirements.
Перед изменением версии согласуйте состав пакетов, их источники и лицензии.
Затем сгенерируйте файлы, проведите ревью изменений, заново выполните
проверенную установку, lint, coverage и проверку готового пакета (`package smoke`).

Если официальный индекс доступен, но SHA-256 официального и резервного SDK
различаются, установка или упаковка останавливается с `approval_required`.
Это правило действует и при явном выборе резервного SDK.
Одобрение конкретной версии и пары хешей вручную записывается в
[манифест SDK](../vendor/t-tech-investments/manifest.json): `version`,
`reserve_sha256`, `index_sha256`, `approved_by`, `approved_at_utc`, `evidence`.
После одобрения официальный пакет можно использовать только после явного
обновления lock-файла с проверкой метаданных и полного набора зависимостей.
Изменение версии или любого из хешей требует нового одобрения.
Универсального способа обойти проверку нет; одобрения автоматически не записываются.
Повреждение пакета всегда завершает работу ошибкой.
Сейчас `approvals=[]` и `official_hash_verified=false`:
независимая сверка хеша официального wheel-пакета не выполнена.

## Песочница локально

Этот раздел относится к автоматическим тестам с временными счетами.
Для своего конфига используйте [ручную проверку приложения](../docs/sandbox-manual.md).

Токен задаётся через `SANDBOX_TOKEN` либо одной строкой в `.sandbox_token`
в каталоге проекта. Файл исключён через `.gitignore`, не входит в облачный
архив и не должен добавляться через `git add -f`. Ограничьте его права:

```bash
chmod 600 .sandbox_token
make e2e
```

`sandbox_token.py` передаёт токен дочерней команде через окружение,
не через аргументы или вывод Make. Непустой `SANDBOX_TOKEN` имеет приоритет.
Без него читается файл, путь которого задаётся `SANDBOX_TOKEN_FILE`.
Отсутствующий или пустой файл вызывает скрытый ввод в терминале.
Нечитаемый либо некорректный файл, а также отсутствие токена без терминала
завершают запуск с ошибкой. Введённый токен на диск не сохраняется.
Для этих тестов нужен токен песочницы, а не production-токен.

`sandbox_e2e.py` запускает полный набор ACCOUNT/INDEX/COMPOSITE с временными
счетами: первоначальные покупки, пополнение, повторный проход, изменение долей,
внутренняя и межкомпонентная ребалансировка, вложенность и общие UID.
Отдельный RUB/CNY-набор использует SBER, РУСАЛ БО-05 (`RU000A105104`)
и прямую пару CNYRUB_TOM, проверяя native-деньги/блокировки, комиссии,
FX-лоты, существующую валюту и владение средствами. Перед заявками он
проверяет актуальные метаданные, двухсторонние книги и разрешения.
При ошибке сохраняются диагностические дампы; счета удаляются после сценария.

Полный набор дополнен диагностическим CNY-кейсом: два одинаково пополненных
временных счёта сравнивают одну BUY на два лота и две BUY по одному.
Он сохраняет native balances и raw units/nano суммы/комиссии OrderState,
отдельно проверяет историю BUY/BROKER_FEE без двойного счёта комиссий.
Различие моделей шестизначного округления ответа и списания отмечается только
при согласованных независимых фактах; иначе выводится inconclusive.
Runtime округление и денежный oracle 1e-9 не меняются. Идентичность, native
бюджет, own caps и read-back очистки обязательны. Коллекция полного SHA
содержит 26 сценариев (прежние 17+8 и этот probe).
После незавершённых запусков оставшиеся временные счета тоже нужно удалить.

Общий тайм-аут `E2E_TIMEOUT` составляет 1800 секунд, максимум — 3600.
Частичный локальный прогон и потоковый вывод:

```bash
make e2e E2E_ARGS="-k INDEX"
make e2e E2E_ARGS="-s"
```

Частичный прогон не является полной CI-приёмкой. Не запускайте локальные
и GitHub-прогоны одновременно с общим sandbox-токеном: их блокировки
и пространства имён независимы.

При `DEADLINE_EXCEEDED` или `UNAVAILABLE` допускаются до трёх дополнительных
попыток только упавших сценариев, с паузой 10 секунд. Все попытки входят
в общий тайм-аут. Каждая запускает свежий pytest и создаёт новые счета;
успешные сценарии не повторяются. Нетранспортная ошибка останавливает повторы
всего прогона. Ошибки проверок, авторизации, закрытые торги, `INTERNAL`,
ошибки коллекции/очистки, отмена и общий тайм-аут не разрешают повтор.

Перед повторной попыткой все временные счета должны быть успешно удалены.
Если открытие счёта завершилось тайм-аутом и его ID неизвестен, сначала
найдите счёт по имени, содержащему идентификатор запуска (`run ID`).
Такой поиск не требуется, если до начала сессии завершился ошибкой первый
запрос, который только читает данные. Перед аварийным удалением счетов
супервизор проверяет, что остановлена вся группа процессов, включая дочерние
процессы контроллера. Для этой проверки нужен Linux `/proc`.
Если остановку подтвердить не удалось, счета не удаляются,
а прогон завершается ошибкой. Для остановки процессов и аварийного удаления
счетов предусмотрены отдельные короткие тайм-ауты; в GitHub необходимое время
зарезервировано внутри задания E2E с обращением к API.

## Песочница в GitHub

Добавьте repository secret `SANDBOX_TOKEN`:
**Settings > Secrets and variables > Actions > New repository secret**.
Значение передаётся только live-заданию через окружение; в аргументах,
статусах и артефактах его нет. Форки не получают секрет.

Ручной запуск PR: **Actions > Sandbox live E2E > Run workflow**,
ветка workflow `master`, поле `pr_number` — номер открытого PR.
Workflow фиксирует head SHA, проверяет репозиторий и права инициатора,
затем запускает на GitHub Runner `make e2e`.

Открытие PR и новые коммиты не запускают песочницу автоматически.
До ручного запуска обязательный `Sandbox E2E` отсутствует и блокирует мерж.
Красный workflow означает ошибку запущенного прогона либо его инфраструктуры.
Успех относится к точному SHA; новый коммит требует нового полного прогона.
Ошибка, отмена, неполное выполнение и отсутствие запуска не дают успеха.
После мержа workflow автоматически проверяет новый SHA master;
неуспешный результат не отменяет выполненный мерж.

PR- и master-прогоны используют общую очередь без отмены активного запуска.
Очистка CI-счетов и сбор диагностики выполняются внутри её блокировки.
Ночь, выходные и закрытые торги не преобразуются в skip:
для приёмки должны пройти все сценарии независимой полной коллекции SHA.

Перед подготовкой каждого теста выводится строка прогресса;
буфер вывода сразу сбрасывается, чтобы строка была видна без задержки:
`Sandbox E2E attempt 1 [index/selected_count] e2e/test_sandbox.py::test_...`.
В повторной попытке знаменатель отражает число выбранных упавших тестов.
Дампы и JUnit доступны в артефактах, срок хранения — 7 дней.

Формат `retry-v2` содержит независимый `collection.json` с SHA и полным
списком node IDs, `retry.json`, один итоговый `junit.xml`
и каталоги `attempts/01` ... `attempts/04` с исходным JUnit,
очищенным от чувствительных данных `report.json`, дампами и `cleanup.log`,
подтверждающим удаление счетов. Сырой `run.log` не публикуется.
Независимая проверка на отдельном GitHub Runner сверяет точный набор сценариев
и параметры запуска, основания повторных попыток, удаление счетов после каждой
попытки, совпадение SHA и соответствие итогов исходным отчётам. Число passed
не участвует в решении о статусе: успех выводит trusted verifier.
Коллекция выполняется до передачи sandbox-секрета, отдельным collect-only
процессом без фильтров и автоматической загрузки внешних pytest plugins.
Первая попытка должна содержать точный полный набор, независимо от того,
какие тесты успели завершиться; повторы содержат только допустимый failed subset.

Инициатор явно выбирает `E2E_EVIDENCE_PROTOCOL=retry-v2` и `E2E_TESTED_SHA`.
Trusted verifier получает `--evidence-format retry-v2 --collection
sandbox-results/collection.json --sha <tested SHA>`. Без выбора producer
сохраняет прежний `retry-v1`: ровно прежние поля report.json, без sha,
и фиксированный набор 17 сценариев. Поэтому инфраструктурный PR проверяется
старым master workflow и его неизменённым verifier; после мержа новый workflow
включает v2 для произвольного полного набора. V2 не принимает legacy reports,
отсутствующий SHA или подмену коллекции завершившимся subset.
Формат отчёта для одной попытки выбирается явно через
`--evidence-format single-v1`.

Подготовлен `retry-v3`: независимая коллекция, точный SHA, максимум четыре
попытки, общий deadline и подтверждённая очистка остаются обязательными.
V3 повторяет только failed API timeout и подтверждённый `market_time_stale`,
даже рядом с постоянными ошибками. Постоянные сценарии сохраняются failed
в итоговом JUnit и не запускаются повторно; их нельзя скрыть общим success.
Stale требует исключения из известной загруженной точки валидации, совпадающих
UID, двух timezone-aware timestamps и возраста строго больше 90 секунд.
Trusted verifier независимо проверяет эти факты. Assertions, произвольный
ValueError, будущее/отсутствующее время и UID mismatch не дают retry.
Auth запрещает любые повторы. Цикл или непрочитанный остаток после восьми
исключений, как и заполненный восьмиэлементный буфер сохранённых API-фактов,
тоже запрещают все повторы: отсутствие auth в остатке не доказано.
Collection/teardown/cleanup/отмена/deadline
и ошибки протокола сохраняют прежние стоп-условия.

Поддержка v3 вместе с auth-fix выпущена в master `1b015c6` (5.2.2, PR #42),
но его trusted workflow остаётся на `retry-v2`. В candidate workflow PR #40
подготовлены `E2E_EVIDENCE_PROTOCOL=retry-v3` и trusted команда
`--evidence-format retry-v3 --collection sandbox-results/collection.json
--sha <tested SHA>`. Это не активирует v3 при dispatch с ref master:
оба выбора и verifier берутся из trusted master, а не из checkout PR.
Для активации до мержа PR #40 нужен отдельный согласованный PR в master,
меняющий оба выбора в `.github/workflows/sandbox-e2e.yml`; обязательные checks
и merge выполняются без обхода защиты. Затем отдельно разрешённый dispatch
с ref master проверяет точный новый SHA PR #40 по v3. До этого PR #40
при выборе master продолжает производить совместимый v2 evidence.
V1/v2 сохраняют прежние поля и поведение. Новые app-модули и зависимости
для подготовительного выпуска не нужны; брокерские запросы классификатор
не выполняет. Полная live-приёмка каждого будущего SHA по-прежнему обязательна.

`sandbox_collection.py` фиксирует полный набор без исполнения fixtures;

`sandbox_github.py` реализует GitHub-обвязку;
`sandbox_lifecycle.py` управляет жизненным циклом счетов;
`sandbox_evidence.py` и `sandbox_retry_evidence.py` проверяют отчёты
и подтверждения выполнения тестов; `sandbox_retry.py` и `sandbox_retry_report.py`
отвечают за повторы и итоговые отчёты;
`sandbox_support.py` содержит общие DTO и средства диагностики.

## Сборка облачного архива

Во всех режимах используется цель `make claude-yandex-archive`;
готовый архив записывается в `build/yandex-function.zip`:

```bash
# Обычный: зависимости устанавливаются при подготовке функции
make claude-yandex-archive
# Локальный SDK, остальные пакеты устанавливаются из PyPI
make claude-yandex-archive USE_VENDORED_SDK=1
# Архив с готовыми зависимостями приложения, без установки пакетов в облаке
make claude-yandex-archive USE_VENDORED_SDK=1 OFFLINE_ARCHIVE=1
```

`build_yandex_archive.py` включает `main.py`, `handler.py`, плоские Python-модули
`autorepeater` и нескрытые JSON дерева `autorepeater/configs`. Модули выбираются
автоматически; внешние конфиги, тесты, технические скрипты и окружения не копируются.
Обычный архив дополнительно содержит корневой `requirements.txt`; резервные
режимы включают зависимости и лицензионные материалы по правилам ниже.
Тесты извлекают архив вне репозитория и проверяют CLI/облако с подменённым SDK
и заблокированной сетью.

Оба флага принимают только значения `0` и `1`.
Сочетание `OFFLINE_ARCHIVE=1 USE_VENDORED_SDK=0` тоже допустимо:
оно создаёт архив с готовыми зависимостями и автоматическим выбором источника SDK.
Обычный сборщик использует только стандартную библиотеку Python,
не обращается к сети и не проверяет источник SDK.
Сборщик с резервным SDK проверяет только индекс, с ограничением времени
и без скачивания SDK. В архив включаются локальный wheel SDK, его лицензия
и манифест, а также requirements с хешами зависимостей приложения,
устанавливаемых только из PyPI. Исходные requirements не изменяются.

До обращения к сети сборщик автономного архива проверяет совместимость
Linux, CPython и glibc. Затем он скачивает в отдельный каталог wheel-пакетов
(`wheelhouse`) полный набор зависимостей приложения, зафиксированный
в lock-файле. Команда `pip download` с ограничением времени проверяет локальный
набор, после чего `pip install` устанавливает его в изначально пустой каталог
назначения. На получение пакетов и на установку отводится по 300 секунд.
Сборка из исходников, включая компиляцию нативного кода, не выполняется.
Допускаются нативные wheel-пакеты с тегами manylinux2014/2_17,
а также совместимые пакеты с тегами universal/abi3.

Содержимое чужих `site-packages` не копируется. В корень архива входят
каталоги `.dist-info`, данные пакетов, лицензии и `dependency-manifest.json`
с хешем lock-файла, хешами пакетов и отдельных файлов. Корневые requirements
для установщика, каталог wheel-пакетов и зависимости, нужные только
для разработки, в архив не входят. При этом iprotopy, grpcio-tools,
mypy-protobuf, ANTLR и setuptools включаются, поскольку они требуются SDK.
Публикуемый набор файлов точно соответствует проверенным wheel-пакетам;
созданные pip точки входа и служебные файлы в него не включаются.
Повторная офлайн-проверка до импорта модулей сверяет полный состав файлов
и их байтовое содержимое с независимым `runtime-file-lock`,
без доступа к сети и запуска установщика.

Режимы сборки с резервным SDK и готовыми зависимостями проверяют CRC,
состав файлов и точное совпадение их байтового содержимого.
ZIP заменяется атомарно; при ошибке предыдущий архив сохраняется.
Сборщик автономного архива проверяет импорт модулей в изолированном процессе
до публикации ZIP. Скрипт можно запускать напрямую или через `runpy`,
в том числе из другого рабочего каталога:

```bash
python /path/to/autorepeater/scripts/build_yandex_archive.py --project-root /path/to/autorepeater --output /tmp/function.zip
```

Для резервных режимов при прямом запуске скрипта используйте параметры
`--use-vendored-sdk` и `--offline-archive`. Лицензии включённых в архив пакетов
и оговорка для iprotopy описаны в
[vendor/README.md](../vendor/README.md#лицензии-и-payload).

## Проверка готовых архивов

```bash
make check-cloud-package CLOUD_PACKAGE_SHA="$(git rev-parse HEAD)"
```

Если `CLOUD_PACKAGE_SHA` не задан, проверка использует текущий HEAD;
CI передаёт полный SHA. Нужны CPython 3.12, Linux и доступ к сети
для скачивания wheel-пакетов из PyPI. Проверка создаёт собственные временные
каталоги для содержимого пакета. Зависимости архива с резервным SDK
устанавливаются по включённым в архив requirements без использования T-Bank
как источника установки. При этом сборщик всё равно проверяет официальный
индекс, не скачивая оттуда SDK. Автономный архив повторно проверяется
и импортируется без pip и скачивания пакетов.

JSON-результат содержит SHA извлечённого коммита и хеш канонического
представления lock-файла. Если в рабочем дереве есть незакоммиченные изменения,
этот результат не доказывает, что проверен именно указанный коммит.

В обоих режимах импортируются `main`, `handler`, SDK, нативные модули
grpc/protoc и protobuf в изолированном процессе Python с флагами `-I` и `-S`.
Пути, из которых загружены пакеты пространства имён, проверяются через `__path__`.
Обработчик `handler` не вызывается, клиенты не создаются, RPC не выполняются;
токены не нужны. Защита на уровне Python socket не доказывает блокировку
нативных системных вызовов средствами ОС. Проверка пакета не подтверждает
холодный старт в Yandex Cloud, импорт нативных модулей в облаке
или прохождение E2E с обращением к API.

В GitHub Actions та же цель Make используется в двух случаях:

- Обязательная проверка [Offline checks](../.github/workflows/python-app.yml):
  после одного прогона с измерением покрытия выполняется отдельный обязательный
  шаг с доступом к сети. Шаг не пропускается, а его ошибка завершает проверку.
- Ручной запуск: Actions → [Cloud package check](../.github/workflows/cloud-package-check.yml)
  → Run workflow. Он выполняет `Cloud package smoke` без облачных секретов
  и токена песочницы. Workflow появляется в интерфейсе GitHub после добавления
  в основную ветку репозитория. Ручной результат не заменяет обязательные
  `Offline checks` или `Sandbox E2E`.

## Production-деплой

Master защищён: изменения через PR, обязательны `Lint`, `Offline checks`
и `Sandbox E2E` на актуальном head SHA. Проверки строгие, правила действуют
и для администраторов; обязательных одобрений PR нет.

[deploy-prod](../.github/workflows/deploy-prod.yml) запускается после успешного
E2E на коммите, отправленном в master, либо вручную:
**Actions > deploy-prod > Run workflow > master**.
Обычный workflow использует стандартный архив: зависимости устанавливаются в облаке
из индексов, указанных в `requirements.txt`. Он не переключается на резерв автоматически.

Для резервного деплоя: **Actions > deploy-prod-reserve > Run workflow > master**.
Поле `mode`: `vendored` включает локальный SDK и установку остальных пакетов
из PyPI в облаке; `offline` включает готовые зависимости без установки в облаке.
Это отдельный [workflow](../.github/workflows/deploy-prod-reserve.yml),
запускаемый только вручную после отдельного согласования.

Все варианты допускают только `gorpsys/autorepeater/master` и требуют всех трёх
успешных проверок текущего master.
`deploy_gate.py` проверяет SHA и доверенные источники статусов проверок.
Непосредственно перед получением данных аутентификации он выполняет проверку
ещё раз. Для события `workflow_run` проверяется путь
`.github/workflows/sandbox-e2e.yml`, а не меняющееся название запуска.
Деплой устаревшего SHA пропускается.

`yandex_deploy.py` получает короткоживущий IAM-токен через GitHub OIDC.
Окружение GitHub (`environment`) и постоянный облачный ключ не используются.
Значение `audience` для GitHub — `https://github.com/gorpsys`;
для обмена в Yandex IAM — идентификатор сервисного аккаунта деплоя.
Если `audience` отсутствует или пуст, работа завершается до запросов
на получение токенов.

Технический интерфейс `python -m scripts.yandex_deploy` требует `FUNCTION_ID`
существующей функции; прежний `FUNCTION_NAME` больше не поддерживается.
В обоих workflow задаётся один проверенный ID. Чтение текущей версии,
создание новой и проверка `$latest` используют `--function-id`.
Переименование функции или каталога не меняет цель деплоя.
Неверный формат или отсутствие `FUNCTION_ID` останавливает работу до OIDC.
До загрузки архива `functionId` текущей версии сверяется с ожидаемым ID;
ответ создания и итоговый `$latest` независимо проходят ту же проверку.
Совпадения ID между ответами недостаточно. Если функция не найдена,
деплой завершается: поиска по имени и автоматического создания ресурса нет.

Архив загружается под уникальным ключом SHA/run ID/attempt;
SHA-256 проверяется при создании версии. Оба workflow используют общую очередь
`deploy-prod`, `cancel-in-progress=false`, `queue=max` и checkout точного SHA.
`yc 1.40.0` скачивается из официального источника; резервного бинарника нет.
Недоступность этой загрузки останавливает деплой.
При деплое сохраняются текущие переменные окружения, другие ссылки на секреты
и поддерживаемые настройки работы функции. Неподдерживаемые настройки
монтирования, асинхронного выполнения и устаревшей подсети приводят к отказу
до загрузки архива. После создания версии читается `$latest`: проверяются
статус `ACTIVE`, ожидаемый ID функции, ID созданной версии, ресурсы, окружение
и фактические ссылки на секреты.
Торговый обработчик для проверки не вызывается.

Статус `ACTIVE` и настройки подтверждают публикацию версии,
но не выполнение Python-кода при холодном старте. Проверка только импорта
модулей в облаке требует отдельного согласования. Проверка готового пакета
(`package smoke`) также не подтверждает холодный старт и не заменяет E2E
с обращением к API. Операции, изменяющие облачные ресурсы, автоматически
не повторяются. После сетевого тайм-аута сначала нужно выяснить,
была ли создана версия.

IAM-права на бакет, функцию и сервисные аккаунты настраиваются в Yandex Cloud.
Deployment SA нужна роль `iam.serviceAccounts.user` на runtime SA либо
эквивалентное унаследованное разрешение. При `service_account_unavailable`
проверьте этот доступ; runtime SA и секрет должны присутствовать в команде.
Деплой не меняет IAM-привязки автоматически.

`yc 1.40.0` получает на каждый вызов изолированный временный профиль `ci`
с cloud/folder ID и endpoint `api.cloud.yandex.net:443`. JSON-конфиг совместим
с YAML-парсером CLI; передаются явные `--config`/`--profile`.
IAM-токен передаётся только через `YC_IAM_TOKEN` в окружении дочернего процесса.
Токен в профиле и argv отсутствует; окружение родителя не меняется.
`YC_TOKEN` не используется; `--token` выбирает OAuth-конвертацию,
а не готовый IAM-токен. Профиль удаляется и при ошибке или тайм-ауте.

Данные аутентификации маскируются. Полные аргументы команд, stdout, stderr
и описания ошибок провайдера в логи не записываются.
`deploy_support.py` ограничивает время HTTP-вызовов, проверяет ответы
и формирует безопасные категории ошибок. При ошибке получения токена сообщение
указывает этап — GitHub OIDC или обмен токена в Yandex IAM, — HTTP-статус
и стандартный код OAuth. При ошибке CLI выводятся фиксированная причина
(`reason`) и полные UUID `x-request-id` и `x-client-trace-id`, если они доступны.
Произвольные значения и UUID, содержащие токен, отбрасываются.

Если категории ошибки недостаточно для диагностики, получите полный ответ
создания версии и журнал сборки в облачной консоли. Перед передачей удалите
из них данные аутентификации. Workflow не сохраняет эти материалы;
идентификаторы запроса и трассировки не заменяют текст ошибки.

## Офлайн-калибровка политики

```bash
python -m scripts.check_rebalance_policy --output /tmp/rebalance-policy-report.json
python -m scripts.check_rebalance_policy --repetitions 1 --output /tmp/rebalance-policy-short.json
```

Утилита не импортирует SDK, не читает токены и не обращается к API.
[rebalance_scenarios.json](../test/data/rebalance_scenarios.json) задаёт
начальные значения генератора случайных чисел, месячные пополнения,
размеры портфелей, амплитуды изменения цен, допуск и условную ставку комиссии.
Основная выборка для независимой проверки (`holdout`) содержит 24 000 случаев.
Отчёт содержит SHA-256 входных данных и модулей, число заявок, оборот
по расчётным ценам `marks`, оценку комиссии и половину L1-ошибки.
Также в нём отражены результаты повторных проверок и сценариев с отсечением
хвоста состава, на границах таблицы допусков, с бюджетами вне сетки,
нехваткой резерва, вложенными стратегиями и общими UID.
Одинаковое байтовое содержимое входных данных даёт одинаковый JSON;
текущее время в отчёт не включается.

Измерения от 2026-10-06 сохранены в [историческом отчёте](../docs/reports/2026-10-06-calibration.md).

Модель использует RUB, исполнение FILL по фиксированным marks и оценочную
комиссию. Оценки комиссии и ошибки следования относятся к модельным сценариям.
Офлайн-проверки работают без API; Sandbox E2E выполняют реальные запросы.
Оба вида проверок запускаются в GitHub Actions,
и их результаты относятся к конкретному SHA.

## Калибровка по котировкам API

```bash
python -m scripts.check_imoex_strategy --src IMOEX --output /tmp/imoex-calibration.json
```

`READ_ONLY_INVEST_TOKEN` предоставляется через окружение. Скрипт читает
публичные котировки, не запрашивает счета и не отправляет сделки.
По умолчанию используется production endpoint; `--sandbox` выбирает песочницу.
`--gross-values` задаёт полный бюджет, `--budgets` — бюджет после резерва,
`--thresholds` — `max_lot_weight_error`. Также поддерживаются `--src` и `--output`.
Доступность котировки не подтверждает текущую доступность торговли.

Чтобы проверить свой INDEX, сначала укажите его каталог или файл
[как для приложения](../README.md#свой-конфиг), а в `--src` передайте `name`.
Токен для чтения предоставьте отдельно в `READ_ONLY_INVEST_TOKEN`:

```bash
read -r -s -p 'Токен для чтения: ' READ_ONLY_INVEST_TOKEN
export READ_ONLY_INVEST_TOKEN
printf '\n'
.venv/bin/python -m scripts.check_imoex_strategy --src MY_INDEX \
  --gross-values 10000 50000 100000 --thresholds 0.03 0.05 0.1 \
  --output /tmp/my-index-calibration.json
```

Отчёт сравнивает число выбранных бумаг, лоты, стоимость, расчётный остаток
и ошибки весов при разных бюджетах и `max_lot_weight_error`.
`--thresholds` меняет именно этот допуск лотного округления, не таблицу
`allocation_drift_limits`, не резерв и не допуск компонентов COMPOSITE.
Утилита не выбирает параметры за пользователя и не меняет конфиг.
При отсутствии бумаг для выбранного бюджета расчёт может завершиться
ошибкой; это основание пересмотреть бюджет/состав/параметры, не обходить проверку.

## Версии и выпуск

Версия имеет формат `X.Y.Z` (SemVer), Git-тег — `vX.Y.Z`.
Версия приложения записана в `autorepeater/__init__.py` как `__version__`;
CLI выводит её по `--version` или `-v`. В PR эта версия должна совпадать
с первым разделом выпуска в CHANGELOG. После мержа на этот коммит ставится тег.
Изменения описываются в [CHANGELOG](../CHANGELOG.md).
В нём оставляются краткие записи по выпускам: версия, дата, значимые изменения
и инструкции перехода для несовместимых версий. Перечень всех коммитов,
обоснования исторических тегов и сведения о том, какие изменения объединены
в один выпуск, находятся в
[истории версий](../docs/history/versioning.md), измерения — в [отчётах](../docs/reports/2026-10-06-calibration.md).

| Часть | Когда повышать |
| --- | --- |
| MAJOR (`X`) | Изменение существующих параметров запуска CLI/облака, новые обязательные параметры, несовместимая схема конфигов |
| MINOR (`Y`) | Новый необязательный параметр, совместимый алгоритм или возможность приложения |
| PATCH (`Z`) | Совместимые исправления, внутренние рефакторинги, тесты, документация и техническая обвязка без изменения функциональности приложения |

Workflow, CI/CD, Make, тестовая, сборочная и деплойная обвязка относятся к
PATCH, включая новые технические Python-скрипты. В смешанном выпуске уровень
определяется изменениями приложения, а не новыми возможностями обвязки.
Все изменения одного PR образуют один выпуск с наиболее значимым уровнем,
а не отдельные версии каждого коммита. Тег ставится на SHA мержа.
Для истории без PR последовательные PATCH-изменения объединяются в один выпуск,
пока пауза между коммитами не превысит восемь часов; календарные сутки не учитываются.
Связанные изменения, работа над которыми ещё не завершена, могут относиться
к одному выпуску и после более длинной паузы. Такие исключения объясняются
в истории версий. Один выпуск может объединять несколько связанных PR.
Промежуточные коммиты сохраняются в истории версий без отдельных тегов;
тег ставится только на последний коммит завершённого пакета. История Git
не переписывается. Merge-коммит сам по себе не повышает версию.

Переименование и перенос исполняемого файла, смена импортов, SDK и
зависимостей сами по себе не требуют MAJOR, если сохраняются параметры
и поведение запуска. Изменение внутренних сигнатур Runner/движка также
не является самостоятельным основанием для MAJOR приложения.
Изменение умолчаний для устранения проблем и тонкой настройки относится к
PATCH, если не меняет экономический контракт. Новая возможность приложения в том же
выпуске повышает MINOR. Промежуточные этапы рефакторинга могут оставаться
без версии, с записью в истории версий; возврат CLI с прежними параметрами
не требует MAJOR.

При повышении MAJOR сбрасываются MINOR и PATCH; при повышении MINOR — PATCH.
Для выпуска с несколькими изменениями выбирается наиболее значимый уровень.
Несовместимые изменения перечисляются отдельно с инструкцией перехода.
Теги опубликованных версий не перемещаются и не переиспользуются.

1. В PR выбрать следующий номер по SemVer и обновить `__version__`
   в `autorepeater/__init__.py`.
2. В начале CHANGELOG добавить раздел с номером версии, ссылкой на сравнение
   и датой в формате существующих заголовков. Перечислить изменения
   и инструкцию перехода, если она нужна. Пустой раздел
   «Не выпущено» перед ним допустим. Номер должен быть строго больше всех
   опубликованных тегов `vX.Y.Z` и версии базовой ветки PR.
3. Дождаться `Lint`, `Offline checks` и ручного полного `Sandbox E2E`
   на последнем SHA PR; смержить через PR.
4. Проверить, что выполнены все условия завершения выпуска. Если требуется проверка
   production-деплоя, использовать согласованный workflow из master через
   GitHub Actions; локальный деплой не заменяет проверку OIDC. Результаты
   завершённых выпусков записывать в историю версий.
5. Проверить workflow [Release tag](../.github/workflows/release-tag.yml).
   После мержа в master он создаёт аннотированный тег на SHA мержа;
   текст аннотации берётся из соответствующего раздела CHANGELOG.
   Если задание не прошло, повторите исходный запуск через Re-run failed jobs:
   так сохранится SHA того же мержа. Actions → Release tag → Run workflow
   на master проверяет текущий master, а не прежний неуспешный запуск.
   Тег на том же SHA можно опубликовать повторно;
   тег другой версии или на другом коммите автоматически не заменяется.

Проверка версии входит в обязательный `Offline checks` и выполняется
до установки зависимостей. Некорректный номер, отсутствие записи, пустой список
изменений, расхождение с CLI или недостаточное повышение версии завершают
проверку ошибкой. Компоненты сравниваются как числа: `1.10.0` больше `1.9.0`.
Проверка версии базовой ветки действует и тогда, когда тег предыдущего выпуска
ещё не успел появиться. Защита master требует актуальной базы PR.

Создание тегов выполняется отдельной очередью только для master, с правом
`contents: write`. Проверка PR имеет только `contents: read`.
Проверить версию локально после получения тегов можно так:

```bash
git fetch origin master --tags
python -m scripts.release_version check --base "$(git rev-parse origin/master)"
```

Тег означает версию исходников, а не подтверждение работы на production.
Результат автоматического Sandbox E2E master и production-деплоя проверяется
отдельно в Actions. Push тега не запускает production-деплой.
